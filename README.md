# hojokin

hojokin は、専門家に頼めない中小企業の社長と担当者が、補助金の申請と報告を、Claude と話しながら自社で進めるための Claude Code のプラグインです。手間のかかる手続きを手伝い、社長と担当者が本業に力を注げるようにします。

**デモ動画**：準備中（提出のときにここへリンクを入れます）。

この README は、ハッカソン「Built with Claude: Japan 2026」の期間（2026年11月2日〜8日）の終わりの形を書いています。

## 3分で分かる要約

- **誰の、どんな課題か**：補助金は、効率化・新しい事業・販路開拓の力になります。それでも、専門家に頼めない会社は、「どれが使えるか分からない」から「採択の後も大変」まで、5つの壁にぶつかり、手続きを本業の合間に手探りで進めています。作者は、こうした経営者の相談を100件以上受けてきました。ハッカソンのテーマ「本来、誰にでも届くべきものを。」に沿い、専門家に頼める会社でなくても補助金を使えるようにします。
- **何を作ったか**：探す → 公募要領を読む → 書類を整える → 申請書を書き、別の目（審査役）が確かめる → 電子申請の画面に入れる → 採択後の報告、までを手伝う Claude Code のプラグインです。社長は、ふだんの言葉で話しかけるだけです。提出のボタン、パスワード、確認・誓約・同意のチェック欄は、hooks とコードで止め、人が行います。
- **Claude Code をどう活かしたか**：段階ごとの skill、目的の違う3つの subagent、守りと知らせの hooks、ブラウザの MCP の道具、計算と書き込みをする道具のコードを使い分けています。守るべき所はコードと hooks で固め、書き方は Claude に任せる、という線を引きました。作るときも、仕様・テスト・振る舞いのテストを正本にして、Claude Code で作りました。
- **どう確かめたか**：
  - 自動のテスト（pytest）は、11月8日の版で全部を流し、2369件が通りました（落ちたものは0件）。
  - 振る舞いのテスト（`claude plugin eval`）は77のケースを流し、74が合格しました（1回目は66。揺れの流し直しと、採点・手順の直しの後）。残る3つの理由は、下の9章に書いています。
  - 9つのケースで、プラグインあり・なしの合格率を比べると、あり 23/26（88%）、なし 6/26（23%）で、差は 65 ポイントでした。
  - 架空の町工場で、1件目（省力化）の申請書を、審査役の要修正0件まで書き上げました。
- **どの補助金で確かめたか**：「省力化投資補助金（一般型）」と「小規模事業者持続化補助金（一般型・通常枠）」の2つです。ほかの補助金の申請書には、まだ使っていません。これから制度ごとに確かめます。

## 1. 解決する課題

### 社長と担当者がぶつかる5つの壁

作者は、補助金の申請や報告に困る経営者の相談を、100件以上受けてきました。中小企業がやりたいことはさまざまで、補助金はその後押しになります。けれども、専門家に頼めない会社では、社長や担当者が本業の合間に、手探りで進めています。そこには、次の5つの壁があります。

| 壁 | 中身 |
|---|---|
| どれが使えるか分からない | 国・都道府県・市区町村の制度があり、今の公募と、例年の公募の見込みを調べる手間がかかる |
| ルールが多すぎて分からない | 公募要領は数十ページあり、要件・義務・返還の条件・締切が散らばっている |
| 書類が膨大 | 決算書・見積書・様式などを集め、期限切れ・名義の違い・交付決定の前の発注のような不備を見つける必要がある |
| 採択される計画書が書けない | 審査の観点に沿い、数字の根拠と財務の計画をそろえた計画書は、慣れないと書けない |
| 採択の後も大変 | 交付申請・実績報告・効果報告と、手続きが続く（制度によっては5年先まで） |

hojokin は、この5つの壁に1つずつ応えます（下の2章）。作者が実務で見てきた不備の型・審査の観点・計画書の構成の型は、同梱の知見（`knowledge/`）として組み込んでいます。

### ハッカソンの後も、誰がどんな場面で使うか

- 社長と担当者が、公募のたびに使います。補助金を探すところから、申請、採択後の報告まで、同じ会社のフォルダで続けます。
- 会社のフォルダを開くたびに、hooks が締切と次の作業を示します。採択後の報告の期限（省力化の効果報告は5年先まで）も、同じ画面に並びます。
- 2件目からは、1件目で覚えた会社の事実を使い、聞き直しを減らします。

## 2. できること

### 5つの壁と、hojokin の段階

| 壁 | 段階（skill） | hojokin がすること |
|---|---|---|
| どれが使えるか分からない | 探す・決める（`sagasu`） | 選択肢の画面で会社のことを聞き、国と都道府県・市区町村の補助金・助成金を「公募中」「公募予定」「例年公募がある」に分けて、出典つきで示す。要件・義務・返還の条件・自己負担・二重受給を説明し、「補助金の候補.docx」にまとめる |
| ルールが多すぎて分からない | 準備（`junbi`） | 公募要領を読み、出典のページ付きの「制度データ」を作る。何を・いつまでにするかを、概要と流れ（概要と流れ.docx）・書類の一覧・日程にまとめる。制度の質問には資料の文とページで答え、資料になければ推測せず、事務局への問い合わせ文の案を作る。外の機関に頼む書類の依頼と待ち、公募要領の改訂も追う |
| 書類が膨大 | 書類（`shorui`） | 社長がフォルダに入れた決算書や見積書を原本の置き場へ移し、名前を付け直し、提出に合わせた写しを作る。不備（期限切れ、名義や金額の違い、交付決定の前の発注など）を、重さを付けて示す。見積書・請求書・納品書の金額も照らし合わせる |
| 採択される計画書が書けない | 書く・確かめる（`kaku`） | 構想役が投資の効果の筋書きを3つ（堅実・標準・積極）示し、社長が選ぶ。前提を変えれば試算し直せる財務モデルを作り、そこから数字を取って、公式の Word・Excel の様式に書式を崩さず書き込む。前後の比較・数値計画・工程表の図と、会社のフォルダの写真も入れる。書いたのとは別の文脈の審査役が確かめ、直してから完成にする。審査の受け答えの練習もできる |
| 採択の後も大変 | 準備・書く（`junbi`・`kaku`） | 採択の通知から交付申請の期限を出し、採択後の段階へ切り替える。差し戻しには、指摘と提出版を照らして直す。実績報告・効果報告の書類も作る |

ほかに、次のことをします。

- **電子申請の入力**（`nyuryoku`）：担当者が `/hojokin:nyuryoku` を呼んだときだけ、Claude のブラウザで申請画面に入力し、一時保存まで進めます。ログイン、確認・誓約・同意のチェック欄、最後の「提出」は、担当者が行います。
- **記録**（`kiroku`）：会社について覚えたこと（事実、社長が直した言い回し、指摘）を会社のフォルダに残します。書類の前の版を見る・戻すこと、提出版を残すこともできます。
- **今の状態**：締切、書類の揃い具合、不備、申請書の進み具合、採択後の報告の期限を、「今の状態.html」と「今の状態.xlsx」でいつも見られるようにします。

skill の名前には、プラグインの名前が前に付きます（例：`/hojokin:sagasu`）。ふだんは名前を呼ばずに、「機械を入れたいけど、何かお金が出ない？」「いつまでに出せばいい？」「申請書を書き始めて」のように話しかければ、Claude が選びます。

## 4. Claude Code の活かし方

### 製品の中で：機能を目的で使い分ける

| 機能 | 何に使うか | なぜその機能か |
|---|---|---|
| skill（6つ） | 探す・準備・書類・書く・記録・入力の段階ごとの手順と道具 | 社長の言葉から、Claude が段階を選べるように（申請画面への入力だけは、担当者が呼ぶ） |
| subagent：審査役（`shinsa`） | 書き終えた申請書を、書いたのとは別の文脈で確かめる | 書いた本人の文脈では、自分の思い込みに気づきにくいため |
| subagent：読み取り役（`yomitori`） | 公募要領・様式・書類を読み取る。量と難しさで haiku・sonnet・opus を使い分ける | 量の多い読み取りで、本体の文脈を守るため |
| subagent：構想役（`kousou`） | 少ない情報から、投資の効果の筋書きと財務モデルの式の案を出す | 筋書きを考える所だけを、別に考えさせるため |
| hooks | 開いたとき・社長が送ったとき・道具を使う前と後・応答を終えたとき・審査役が終わったときに動く。原本と公式資料を守る、提出ボタンを押させない、会社のフォルダの外を読まない。開いたときに締切と次の作業を知らせる。応答の終わりに、公募要領からの引用を本文と照らす | Claude の判断に任せられない決まりを、確実に止めるため |
| 選択肢の画面（AskUserQuestion） | 社長に1問ずつ、勧める案と聞く理由を添えて聞く | 社長が迷わず答えられるように |
| ブラウザの MCP の道具（Claude in Chrome・Claude のブラウザ） | 電子申請の画面に入力し、一時保存まで進める。hooks は、この道具の名前で守りを掛ける | 入力の手間を減らし、提出は人が押す形にするため |
| 道具のコード（Python） | 財務モデルの計算、Word・Excel への書き込み、書類と数字の照合 | 数字を作らず、様式の書式を壊さないため |

### 守る所はコードで固く、書き方は Claude に任せる

「必ず守っていること」（下の7章）だけを、道具のコード・hooks・公式の設定で止め、ほかはできるだけ Claude の判断に任せています。モデルが進むほど、細かい指定は、かえって書く力を縛るためです。

2026年11月7日に、計画書の書き手と審査役に渡していた決まりを洗い出し、「守るもの」と「書き方を縛っているだけのもの」に分けました。

- **守るもの**：事実を作らない、本文の数字に出典を付けて財務モデルと合わせる、様式の項目と欄を書く、上限を超えない。これらは、コードの確かめと審査役で守り続けます。
- **任せたもの**：段ごとに入れる事実の並べ方、書き出しや文の長さの指定、図を置く目安、文体の観点を書き方の型として当てること。これらは「目的と観点」に替え、書き方は Claude に任せました。
- **分量**：公募要領に上限や目安がある所はそれを守ります。ない所は字数を決めず、審査役が読んで「足りない」「長すぎる」を判断します。
- **制度ごとの知見**：その制度で書くときだけ渡し、ほかの制度の計画書に混ぜません。

直す前のデモの会社では、数値計画を書けずに【空欄】9か所で止まり、審査役まで進めませんでした。直した後は【空欄】0か所で書き切りました。審査役の要修正11件は、すべて中身についての指摘で、書き方の好みによる要修正は0件でした。そこから要修正0件まで直しています。なお、同じときに社長役の答えも足したので、この差は書き方の直しだけによるものではありません。

### 作るときも、Claude Code が中心

補助金の実務家である作者1人が、7日間で、Claude Code と一緒に作りました。

- 要件（[SPEC.md](SPEC.md)）、作り方（[docs/DESIGN.md](docs/DESIGN.md)）、タスクの一覧（[docs/TASKS.md](docs/TASKS.md)）を正本にし、タスクごとに作って、テスト番号で確かめました。
- 作り始める前と作りながら、仕組みが動くかを実験で確かめました（デスクトップアプリでの hook、会社のフォルダの設定、Word・Excel への書き込み、ブラウザの守り、eval の仕組みなど。[experiments/結果.md](experiments/結果.md)）。実験の結果で、画面入力のブラウザを、自作のものから Claude のブラウザに替えるなど、作り方を変えました。
- 開発用の Stop hook（`tests/dev_stop_hook.py`）が、Claude が応答を終えるたびに構成の検査と速いテストを流し、落ちたら直すまで続けさせました。主な変更では、開発用の subagent（`.claude/agents/spec-check.md`）で、変更を仕様と照らしました。
- 重ならない作業は、worktree の別のセッションで並べて進め、日ごとのブランチにまとめました。
- `claude plugin eval` で振る舞いを採点し、プラグインあり・なしの差を測りました。
- 期間中（2026年11月2日〜8日）のコミットは、マージを除いて350件を超えました。

## 5. 磨いた経過と、確かめたこと

### 主な試行錯誤

- **欠陥がないだけの計画書を、完成にしてしまった**（11月6日のリハーサル）：審査役の要修正0件を完成の条件にしていたため、浅い計画書が完成になりました。作者の知見（構成の型・審査の観点）と、財務モデルの投資の効果の見え方を審査役に渡し、事実が欠けた段、点数が2以下の審査項目、投資の効果が少なく見える所を要修正にしました。
- **決まりが細かすぎて、Claude の書く力を縛っていた**（11月7日）：上の4章のとおり、守るものと任せるものに分けました。
- **公開の前の点検**（11月8日）：ハッカソンの公開前のチェックリストに沿って、秘密とその履歴（gitleaks で全部の参照を検査し、0件）、GitHub の設定、コードを点検しました。使われていないコードと古いコメントを片付け、守りが掛かる範囲を、下の7章に正直に書きました。

### 自動のテスト（pytest）

SPEC 6章の自動のテストを、テスト番号ごとのファイル（`tests/test_T*.py`）で確かめています。

- 2026年11月8日に、コミット 9a4f142 の版で全部を流し、2369件が通りました。落ちたものはありません（ほかの7件は skip。デスクトップでの画面入力の記録、振る舞いのテストで残したフォルダ、本物の通信を渡したときだけ流れるもの）。11月7日の夜（コミット cf02e16）にも全部を流し、2357件が通っています。
- 原本と公式資料を変えないこと（T0-7）と、会社のフォルダでないフォルダでの動き（T0-13）は、`skills/*/scripts/` のすべての道具の、すべての小さな命令と、hooks のすべての場面で確かめています（`tests/test_T0_7.py`・`tests/test_T0_13.py`）。

### 振る舞いのテスト（`claude plugin eval`）

架空の会社のフォルダを段階ごとに保存し（`evals/状態/`）、その状態から Claude に頼んで、結果を採点します（`evals/<ケース>/`）。物差しには、デモの町工場とは別の架空の会社（惣菜の製造）を使い、デモの会社だけに合わせた作りにならないようにしています。

- 2026年11月7日に、77のケースを1回ずつ流しました。1回目は 66 が合格しました（費用は約 $84）。
  - 落ちた11のうち5つは、1回だけの揺れや混んだ時間帯の時間切れで、流し直して合格しました。
  - 2つは、振る舞いは合っていて、採点の正規表現が材料や答えの言い方に合わなかったもので、採点を直して合格しました。
  - 1つは、Claude の手順の抜け（制度の可否を聞かれて資料に定めがないとき、問い合わせ文の案を付けなかった）で、skill を直して合格しました。
  - 流し直しの中で、計画書を書く skill（kaku）が、同梱の知見を Read で読もうとして守りに拒まれていたことが分かり、道具で出す形に直しました。
  - 残る3つ（T8-8・T8-9、T13-9、T2-1）は、下の9章に理由を書きました。
- 11月8日の未明に、全部のケースを3回ずつ流し始めました。26のケースを3回流したところで、Claude の週の利用枠に達し、残りは流せませんでした。3回流れた26のうち、3回とも合格したのは15です。ほかに7つのケースは、準備（保存した状態を戻す処理）が、同時に流した負荷で時間の上限を超え、3回がそろいませんでした。

### プラグインあり・なしの差（Δ）

同じケースを、プラグインを入れた側と入れない側で流した合格率と、その差です。2026年11月7日の夜から8日の未明に、9つのケースをそれぞれ3回ずつ流しました（`claude plugin eval --ablation with-without`、コミット cf02e16）。合わせて、あり 23/26（88%）、なし 6/26（23%）で、差は 65 ポイントでした。プラグインありで3回とも合格したのは6ケースです。

## 6. 確かめた補助金と、これから

- **確かめたのは2つです**：「省力化投資補助金（一般型）」と「小規模事業者持続化補助金（一般型・通常枠）」。テストの材料とデモには、省力化の第8回・第9回と、持続化の第20回の公募要領を使いました。
- **補助金を足しても、プログラムは変えない作りです**：1件目の省力化で作ったプログラムに、持続化の制度データを足すだけで、段階ごとの道具が動くことを確かめました（T0-1）。持続化の制度データを足したコミット（件名が「B1a 持続化：」「B1b 持続化：」のもの）には、プログラムの変更がありません（`tests/test_T0_1.py` がこの件名でコミットを探して確かめます）。
- **その前に入れた一般化の直しは1つです**（コミット b6cae95、lib/kakunin.py）：持続化の様式は画面に入力するので、書き込む位置を持ちません。確かめの注意の「書き込む位置をまだ対応づけていない」に、入力先が画面の様式を挙げないようにしました。制度の名前ではなく、制度データの様式の「入力先」（画面かファイルか）で分ける直しで、省力化の動きは変わりません。
- **ほかの補助金の申請書には、まだ使っていません**：公募要領から制度データを作れば、プログラムを変えずに動く作りにしていますが、品質は確かめていません。AI モデルが進むのに合わせて、国のほかの補助金、都道府県・市区町村の補助金、厚生労働省の助成金に、どこまで対応できるかを、制度ごとに確かめていきます。

## 7. 必ず守っていること

Claude の判断に任せられない決まりだけを、道具の中のコード、hooks、公式の設定で止めています。すり抜けたものは、結果の確かめ（ハッシュや書式の比較）で見つけて戻します（DESIGN 5章）。

- **提出ボタンを押さない**：「提出」「送信」「申請する」「確定」「完了」などを含むボタンは押させません。押してよいボタン（次へ・一時保存・戻るなど）だけを通します。
- **確認・誓約・同意のチェック欄に入れない**：これらの欄は担当者が入れます。ツールが入れる欄（加点の選択など）でも、名前が読み取れない欄には入れません。
- **パスワードを扱わない**：ログインは担当者がブラウザで行います。
- **添付するのは、決まった写しだけ**：申請書類のフォルダの「添付する書類」にある写しのうち、入力シートの添付する書類に当たるものだけです。
- **画面入力は、担当者が呼んだときだけ**：`/hojokin:nyuryoku` を呼んだ記録がないと、ブラウザの道具のクリック・入力・添付を止めます。
- **Word・Excel の様式と書式を壊さない**：書いてよい範囲だけに書き、範囲の外が1か所でも変わっていたら保存しません。その場のコードで書き換えた場合も、応答の終わりに比べて戻します。
- **原本と公式資料を1バイトも変えない**：読み取り専用にし、開いたときと応答の終わりに、置いたときのハッシュと照らします。変わっていたら版の履歴から戻し、社長に知らせます。
- **版のファイルを増やさない**：「_v2」「最終」「修正版」「コピー」などの名前のファイルを作らせません。
- **会社のフォルダの外を読まない・書かない**：ファイルの道具は、会社のフォルダの外（別の会社のフォルダや認証情報など）を読み書きしません。外の書類は、社長が場所を伝えたものだけを写して取り込みます。
- **書類と履歴を外に送らない**：会社のフォルダの版の履歴は、送り先を持ちません。
- **補助プログラムが動かないときは止める**：Python が動かない・時間内に終わらないときは、書き込み・Bash・ブラウザの道具を止めます（守りが気づかないうちに外れないように）。
- **会社のフォルダでないフォルダでは何もしない**：hooks は何も止めず何も書かず、道具も、補助金を探すことと会社のフォルダを作ること以外は動きません。

### 守りが掛かる範囲

- hooks が使う前に見る道具は、書き込みの道具（Write・Edit・NotebookEdit）、Bash、ブラウザの道具（Claude のブラウザ〈内蔵ブラウザ〉・Claude in Chrome・computer-use）、読む道具（Read・Grep・Glob など）です（`hooks/hooks.json`）。道具は、名前に `Claude_Browser`・`claude-in-chrome`・`computer-use` の文字が入るかで見分けます。名前に `computer-use` を含む画面操作の道具は、会社のフォルダではすべて止めます。
- Bash は、コマンドの中身を見ていません。止めるのは、補助プログラム（Python）が動かないときだけです（`hooks/pre_tool_use.py`・`hooks/run.sh`）。会社のフォルダの中で Bash が変えたものは、応答の終わりの確かめ（原本と公式資料のハッシュ、様式の書式の比べ、版の名前のファイル）で見つけます。Bash で会社のフォルダの外を読み書きすることや、外へ送ること（curl など）は、hooks では見ていません。Claude Code の許可の確認に任せます。
- 名前に上の文字を含まない道具（たとえば、別の JavaScript を動かす道具や、ターミナルに打ち込む道具）でブラウザを操作したときは、この守りは掛かりません。Claude Code の許可の確認に任せます。Claude のブラウザと Claude in Chrome の中での JavaScript の実行は止めています。
- 「書類と履歴を外に送らない」は、版の履歴（Git）に送り先を持たせないことです。ブラウザでどのページに移るか（http・https のページへの移動は、どこでも通します）と、Web から取るときの行き先、Bash で送る先は、hooks では絞っていません。Claude Code と、ブラウザ側のサイトの許可に任せています（`lib/browser_guard.py`）。
- 「パスワードを扱わない」は、画面の欄の種類が password の欄と、名前に「パスワード」を含む欄に入れないことです。ほかの名前の欄（認証コード・暗証番号など）は見分けていないので、担当者が入れてください（`lib/browser_guard.py`）。
- 守りが相手にしているのは、協力的な Claude と、Git を知らない社長のうっかりです（DESIGN 5章）。書類や画面に書かれた文に Claude が乗せられる場合までは、止めきれません。

## 8. 入れ方と使い方

### 入れ方（Claude のデスクトップアプリ）

1. デスクトップアプリの「設定」→「プラグイン」→「＋ 追加」→「リポジトリから追加」を選びます。
2. このリポジトリ（GitHub の公開のリポジトリ）の場所を入れて、hojokin を足します。リポジトリの根の `.claude-plugin/marketplace.json` が、根にあるプラグインを指しています。
   - 画面からは、手元のフォルダを足せません（実験 E4）。

ターミナルでは、次のコマンドで入ります（Claude Code 2.1.317 の `claude plugin install --help` に `--marketplace` があることは確かめました。このコマンドで実際に入れることは、期間中は確かめていません）。

```sh
claude plugin install hojokin --marketplace tetsuroikeda/hojokin-oss
```

### 使い方

1. 会社のフォルダにする、新しい空のフォルダを作ります（下の「初回の準備」と「使うときの注意」を先に読んでください）。
2. デスクトップアプリで、そのフォルダを開きます。モードは auto を選ぶよう勧めます（会社のフォルダの中の読み取りと編集が、確認なしになります）。
3. 「うちで使える補助金ってある？」のように、ふだんの言葉で話しかけます。どの段階の skill を使うかは、Claude が選びます。
4. 申請画面への入力だけは、担当者が `/hojokin:nyuryoku` を呼びます。「申請画面に入れて」と頼んでも、Claude は自分では始めず、このコマンドを案内します。

### 初回の準備

- **Mac の開発ツール**：補助プログラムは、Mac に入っている `/usr/bin/python3` で動きます。開発ツールが入っていない Mac では、「ターミナル」で `xcode-select --install` を実行し、出てきた画面に従って入れてから、Claude を開き直してください。補助プログラムが動かないときは、プラグインが書き込み・Bash・ブラウザの道具を止め、同じ案内を Claude に渡します。
- **ライブラリの準備は要りません**：使うライブラリ（版の履歴の dulwich、PDF を読む pypdf、Excel を作る openpyxl など）は、Python だけで書かれたものをプラグインに同梱しています（`lib/vendor/`）。初回の通信や pip の準備はありません。
- **LibreOffice（あれば）**：申請書の PDF の写しを作るときと、Excel の数式を計算し直すときに使います。入っていないときは、その操作を案内します。
- **Claude in Chrome（画面入力に勧めます）**：書類の添付までツールが行えます。デスクトップアプリの内蔵ブラウザでは添付ができないので、添付は担当者が行います。ターミナルでは `/chrome` で有効にします。
- **会社のフォルダを作る**：どの skill も最初に、今のフォルダが会社のフォルダか（目印の `.hojokin/` があるか）を確かめ、なければ「このフォルダを〇〇社の会社のフォルダにしますか」と聞きます。了承すると、道具が、目印、フォルダの形、版の履歴、`.claude/settings.json`（外を読み書きさせない設定と、書き換えを止める規則）を一度に用意します。
  - 次のフォルダは、会社のフォルダにしません：ホームのフォルダとそれを含むフォルダ、ディスクの根、前から `.git`・`.gitignore`・`.claude/settings.json` があるフォルダ。そのときは、新しいフォルダを作って始め、元の書類は場所を伝えて取り込むよう案内します。

### 会社のフォルダの形

```
<会社のフォルダ>/
├─ 今の状態.html          まずこれを開く。進み具合の画面（見るだけ。開くたびに作り直す）
├─ 今の状態.xlsx          同じ内容の Excel
├─ 補助金の候補.docx       探した結果
├─ 財務モデル.xlsx         会社の数字の土台（前提と根拠、既存事業・新事業・合算）
├─ 入れ口/                書類をとりあえず入れるフォルダ（ほかの場所に入れてもよい）
├─ 原本/                  受け取った書類。読み取り専用。名前は「<日付>_<種類>_<相手先>.pdf」の形
├─ 案件/
│   └─ <年>_<制度>_<回>/
│       ├─ 概要と流れ.docx     制度の概要、要件と義務、手続きの流れと期限、必要書類
│       ├─ 公式資料/           公募要領・様式・手引き（読み取り専用）
│       ├─ 1_申請/
│       │   ├─ 申請書/         計画書、入力シート、根拠対照表
│       │   └─ 添付する書類/   原本から作った写し
│       └─ 2_交付申請/ … 4_効果報告/1年目/ …（制度データの手続きの段階から作る）
├─ 見るだけ/              前の版や提出版を見たいときだけ出す（開くたびに片付ける）
├─ 記録/                  ツールが管理する（会社の記録、制度データ、書類の台帳、期限の台帳など）
├─ .hojokin/              会社のフォルダの目印と設定
├─ .claude/settings.json  初回に社長の了承を得て作る設定
└─ .git/                  版の履歴（送り先は持たない）
```

- 書類ごとに1つのファイルを直して使います。前の版と提出版は版の履歴に残り、「_v2」「最終」のような名前のファイルは作りません。

### 使うときの注意

- **会社のフォルダは、同期されないフォルダに作ってください。** iCloud Drive・Google ドライブ・OneDrive・Dropbox などで同期されるフォルダに置く形（版をファイルで残す形）は、期間中は選べません。
- **デスクトップアプリでは、会社のフォルダそのものを開いてください。** 目印（`.hojokin/`）は開いたフォルダだけで確かめ、親のフォルダはさかのぼりません。会社のフォルダを含む親のフォルダや、会社のフォルダの下のフォルダで開くと、会社のフォルダと見なされず、守りの hooks も働きません。
- **同じ会社のフォルダを、2つの Claude で同時に開かないでください。** 版の履歴や台帳への書き込みが、ぶつかることがあります。
- **本物の申請画面に入れる前に、制度ごとの規約と遵守事項を、担当者が確かめてください。** 持続化補助金の申請システムの操作手引きには、BOT などによる操作を禁じる定めがあります。本物の画面では、ツールが作った入力シートを見ながら、担当者が自分で入れることを勧めます。
- 書類の作成者と申請者は、事業者自身です。このツールは、事業者が自分で進めるための道具です。申請画面の支援者の欄には、「このツールは支援者には当たりません。人の支援者がいる場合は正直に書いてください」と案内します。

## 9. 確かめていないこと・既知の課題

- **ほかの補助金**：上の6章のとおり、省力化と持続化のほかの補助金での品質は確かめていません。
- **Windows**：守りの仕組み（hook、設定、結果の確かめ）は Mac と同じ形で作り、Windows でも動く形にしていますが、期間中は Mac でだけ確かめました。
- **時間が足りずに後に回したもの**
  - Claude を開いていない間の見回り（予定の作業）と、書類と版の履歴の置き場所の選択肢（期限の一覧だけをクラウドに置く・会社のフォルダごとクラウドに置く）。期間中に選べるのは、パソコンの中だけに置く形です。期限は、開いたときの表示と今の状態の画面で見られます。
  - 部品を1つずつ外したときの効きの測定。
  - 所在地による違いの確かめ。デモは1つの所在地で見せています。
- **全部のケースの3回**：3回とも合格するかの確かめは、Δ の9ケースと、そのほかの26ケースまでで止まりました（Claude の週の利用枠に達したため）。制度データを作る（T3-7）、書類（T5）、聞き取り（T6）、改訂（T7）、計画書を書く（T8）、審査役（T9）、支援者の欄（T10-4）などのケース（Δ のケースを除く）と、skill の選ばれ方（20件）、戻した状態（F0）は、1回だけ流しています。
- **作者の確かめが期間の後になった正解**：省力化の制度データの正解（第8回）、持続化の制度データの正解（下書き）、制度の質問の正解（20問）は、Claude が作った仮の正解で照らしています。作者（補助金の実務の専門家）の確かめは、期間の後に行います。デモで使う省力化の第9回の正解は、期間中は作っていません。
- **まだ合格していない振る舞いのテスト**（2026年11月8日）
  - T8-8・T8-9（計画書の筋立てと分量）と T13-9（不採択の指摘に応える）：11月6日に審査役へ作者の知見を渡した後、テストの材料の計画書（11月5日に作ったもの）に、構成の型の「ほかに考えた手と、選ばなかった理由」や数値目標の組み立てがないと、審査役が指摘するようになりました。審査役の判定の誤りではなく、材料を新しい物差しに合わせて作り直す必要があります。T13-9 は、11月8日の3回でも3回とも落ちました。
  - T2-1（義務と返還の条件の説明）：制度データにない義務を公募要領から足す所で、ちがう1〜2件が抜けることがあります（例：書類の保存の期間、リースで申請したときの返還）。11月8日の3回では、合格は1回でした。
  - T1-2（対象外の判定）：従業員25人の製造業の会社で、候補の一覧（Word と記録）の持続化に「対象外の可能性が高い」の印が付きませんでした（11月8日の3回とも）。会話では、3回のうち2回「対象外」と伝えています。
  - T13-14（手直しから学ぶ）：社長が手で直した言い回しを、すぐに記録に残さず、「次からもそうしますか」と聞き返しました（11月8日の3回とも）。手順（kiroku）では、言い回しの手直しは聞き返さずに残します。
  - 11月8日の3回で、1回か2回落ちたもの：T0-10・T0-11（1/3）、T12-3-契約・T12-3-発注・T13-5・T13-6-数字・T13-8（2/3）。T12-3 の2つは、Δ の3回では3回とも合格しました。
- **制度データを作る精度**（T3-7）：振る舞いのテストの採点（制度データができ、2回の読み取りとまとめを道具で行い、主な値と資料どうしの食い違いがある）は合格しました。ただ、できた制度データを正解と突き合わせた一致率は 57.9%（161/278）で、合格ライン（100%、仮）に届いていません。名前が正解と合わずに数えられなかったものが多いものの、値の読み違い（特例の率と金額）もあります。Claude が作った制度データは、出典のページで確かめてから使ってください。
- **デモ動画を作るときに見つかった、製品の直す所**（`docs/video/README.md` に記録）
  - 会社のフォルダの原本に決算書があるのに、hooks の必須の書類の照らし合わせが拾えず、Claude が「損益計算書・貸借対照表が見当たらない」と答えました。
  - 申請書を書き終えた段階で、準備（junbi）の続きとして概要と流れ.docx を作り直すと、Word の道具が止まりました。書く段階（kaku）が様式の項目に「欄」を足した後の制度データを「形が合わない」とし、補助の対象にする経費も「金額として読めない」としたためです。
- **コードの片付け**：公開の前のレビューで、同じ小さな処理（日付やフォルダ名の扱い、JSON の読み書きなど）がモジュールごとに写してあること、長い関数があることが分かりました。振る舞いを変える直しになるので、期間の後にまとめます。

## 10. リポジトリのフォルダ

| 役目 | フォルダ・ファイル | 中身 |
|---|---|---|
| 製品（プラグインが動くときに使うもの） | `.claude-plugin/` | プラグインの定義（plugin.json）と、入れるときの置き場の定義（marketplace.json） |
| | `skills/` | 段階ごとの skill（sagasu・junbi・shorui・kaku・kiroku・nyuryoku）と、それぞれの道具（`scripts/`） |
| | `agents/` | subagent（shinsa・yomitori・kousou） |
| | `hooks/` | 守りと記録の hooks（hooks.json と、起動用の run.sh、Python の処理） |
| | `lib/` | 道具と hooks が使う共通のコードと、同梱したライブラリ（`lib/vendor/`） |
| | `knowledge/` | 同梱の知見（不備の型・審査の観点・構成の型・制度ごとの注など） |
| | `schema/` | 制度データと会社の記録の形 |
| | `docs/style-criteria.md` | 計画書の文体の基準（製品が動くときに読むデータ） |
| 確かめ | `tests/` | 自動のテスト（pytest。テスト番号ごとの `test_T*.py` など） |
| | `evals/` | 振る舞いのテスト（`claude plugin eval` のケースと、保存した会社のフォルダの状態） |
| | `testdata/` | 架空の会社・書類・回答表・正解など |
| | `mock/` | 模擬の申請画面（架空。省力化と持続化） |
| | `experiments/` | 作る前と作りながら試した実験（E1〜E11）と、その結果 |
| 設計 | `SPEC.md`・`docs/` | 要件（SPEC.md）、作り方（docs/DESIGN.md）、タスクの一覧（docs/TASKS.md） |
| 提出動画の作り方 | `docs/video/` | デモ動画をコードで作る道具と、使った実際の対話の記録 |
| 開発用 | `.claude/` | このリポジトリを開発するときの Claude Code の設定と決まり（CLAUDE.md・settings.json など。プラグインの動きには使わない） |

## 11. 期間中に作ったこと

- ハッカソンの規約に合わせ、コード、同梱の知見（`knowledge/`）、テスト、架空のデータは、すべて期間中に新しく作りました。期間中に作ったことは、コミットの履歴で分かります。実験のコードと結果も `experiments/` に残しています。
- 補助金の申請を手伝う既存の skill や道具、プラグインは使わずに、一から作りました。使ったのは、Claude Code の機能と、補助金に限らない一般のライブラリ（同梱した dulwich・pypdf・openpyxl など。`lib/vendor/README.md`）だけです。
- 公式サイトから取った公募要領や様式は、リポジトリに入れていません（テストのときは、手元の `downloads/` から写します）。テストの正解は、値とページだけにしています。
