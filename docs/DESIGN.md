# 設計：補助金申請を自社で進めるための Claude Code プラグイン（仮称 hojokin-oss）

- 作成日：2026年11月3日。SPEC.md の要件を、どう作るかを決める文書です。
- 公式文書と制度の資料は、2026年11月2日に確かめました（出典は15章）。
- ハッカソンの審査の配点（Impact 30、Demo 25、Claude の使い方 25、深さ 20）を踏まえ、部品の数を増やすより、選んだ理由がはっきりしていて、少ない部品で確実に動く設計にしています。
- SPEC の範囲は削らず、すべて作る前提です。

---

## 1. 設計の前提として決めたこと

設計の初めに作者と決め、SPEC にも書いたこと。決まりの本文は SPEC の該当箇所にあり、ここでは要点だけを示す。

| 項目 | 決めたこと | SPEC |
|---|---|---|
| デモの日付 | 今の公募回（省力化 第9回、持続化 第20回）で申請まで進め、日付を2027年以降に進めて2案件の採択後を見せる。第9回の要領が 11/4 に出なければ、第8回の資料を使う | 4章 |
| 申請者自身が作成・申請する決まりへの対応 | 最後の提出のほかは、ツールが一時保存まで進める。ログイン、確認・誓約・同意のチェック欄（宣誓の欄を含む）、最後の提出は担当者が行う。加点の選択などはツールが入れる。チェック欄は項目名の文字と制度データで見分けるので、確実さは少し下がる（作者の了承済み） | 2.3、4章 |
| ブラウザ | プラグインの専用ブラウザを使う。デスクトップアプリでも、ターミナルの Claude Code でも動く。押してよいボタンか、入れてよい欄かは、ブラウザを動かすコードの中で見分ける | 2.1、F10 |

### 1.1 この文書で使う言葉

SPEC の用語の表にある言葉（制度データ、原本、写し、提出版など）は、そのまま使う。ほかに次の言葉を使う。

| 言葉 | 意味 |
|---|---|
| 担当者 | 電子申請の画面で、ログイン、確認・誓約・同意のチェック、提出を行う人（社長または事務担当者） |
| 本体 | 社長と話している Claude（subagent ではないほう） |
| 審査役 | 申請書を、書いたときとは別の文脈で確かめる subagent。SPEC の F9 にある「書くAIとは別の文脈のAI」で、テストでいう「審査員役」の採点もこの役が行う |
| 読み取り役 | 書類や公募要領を読み取る subagent |
| 道具 | プラグインの MCP サーバーが持つ、答えが1つに決まる処理（計算、書き込み、照合など） |
| 要修正・要確認・助言 | 審査役の指摘の重さ。要修正は直すまで完成にしない。要確認と助言は社長に示し、直すかは社長が決める。書類の不備の重さ（SPEC F5）は、別に「重大・要確認・助言」を使う |
| 「要確認」（値の状態） | 制度データの値や書類の読み取りで、裏付けが取れていないもの。計画書で使う値に残っていたら完成にしない |
| 仮の印 | 決まっていない所に付ける印（SPEC の用語）。文章では【仮：…】、数字の欄では隣の「状態」の欄に書く |
| 書いてよい範囲 | Word・Excel のうち、道具が書き込んでよい所。様式なら制度データの入力欄、ツールが作る書類なら道具のひな形で決める |
| 画面入力の許可 | 担当者が `/hojokin:nyuryoku` を呼んだときに hook が残す記録。これがないと専用ブラウザの道具は動かない |
| 完成の記録 | 確かめの道具が、完成の条件（8章）をすべて満たしたときだけ残す記録 |

## 4. プラグインの構成

### 4.1 部品の使い分け

| 部品 | 使う所 | 理由 |
|---|---|---|
| skill（6つ） | 段階ごとの手順と、判断の物差し | 開いたときに文脈に入るのは、名前と説明だけ。本文は使うときに読まれる。手順は skill に置くよう、公式文書も勧めている |
| hooks（5つの場面） | 必ず守らせる決まり、版の自動の記録、手で直した箇所の検出、開いたときに渡す情報、審査役の結果の保存 | Claude の判断を通らず、必ず動く。文脈も使わない。プラグインの settings.json では deny を設定できない（効くのは `agent` と `subagentStatusLine` だけ）ので、決まりは PreToolUse hook で止める |
| MCP（Python のローカルサーバー1つ） | 答えが1つに決まる処理すべて。計算、日付、様式への書き込み、Word・Excel の作成、照合、書類の整理、版、今の状態の画面、専用ブラウザ | 道具ごとに許可でき、subagent にも渡せる。スクリプトを `bin/` に置く形だと、claude.ai と Cowork がプラグインをインストールしない。`${CLAUDE_PLUGIN_ROOT}` は Bash の環境に入らない。eval でも MCP はそのまま動く |
| subagent（2つ） | 審査役と読み取り役 | 別の目が要るものと、量の多い読み取りで本体の文脈を守るものに絞る。読み取り役は、読むものに合わせて呼ぶときにモデルを替える（7章） |

hooks を使う場面は、次の5つ。

| 場面 | すること |
|---|---|
| SessionStart（開いたとき） | 4.7 の「開いたときの流れ」 |
| UserPromptSubmit（社長が送ったとき） | 社長が手で変えたファイルを「社長」として履歴に残し、申請書の差分を Claude に渡す。指摘らしい言葉に一言添える（10章）。`/hojokin:nyuryoku` が呼ばれたら、「画面入力の許可」を記録する |
| PreToolUse（道具を使う前） | 5章の決まりで止める |
| Stop（Claude が応答を終えたとき） | ツールが変えたファイルを「ツール」として履歴に残す。原本と公式資料のハッシュを照らす。質問の記録を残す。今の状態の画面を作り直す |
| SubagentStop（subagent が終わったとき） | 審査役の結果を、本体を通さずにそのまま保存する（8章） |

**会社のフォルダでは Bash を使わせない。** ファイルの操作は、MCP の道具か Write・Edit だけを通るようにする。こうすると、次の3つをパスを確かめるだけで止められる。

- 原本を書き換えない
- フォルダの外に書かない
- 履歴を外に送らない

公式文書も、Bash の deny はすり抜けやすく、安全の境界にはならないと書いている。

### 4.2 skill

skill の名前には、プラグインの名前が前に付く（例：`/hojokin:sagasu`）。プラグインの正式な名前は14章の課題として残し、ここでは仮に hojokin とする。

| skill | 機能 | 説明（案） | 呼び方 |
|---|---|---|---|
| sagasu | F1, F2 | 使える補助金・助成金を探し、どれに申請するかを決めるときに使う。要件、義務、返還の条件、自己負担、二重受給を説明する | 普段の言葉 |
| junbi | F3, F4, F6, F7、F12 の手続きの切り替え | 申請する補助金を決めた後に使う。公募要領を取り込み、制度データ・概要と流れ・書類の一覧・日程を作る。制度の質問に答える。締切と今の状態、公募要領の改訂、採択後の次の手続きへの切り替えも扱う | 普段の言葉 |
| shorui | F5 | 「書類を入れた」「確認して」「整理して」と言われたときに使う。原本の整理、名前の付け直し、写しの作成、不備のチェック | 普段の言葉 |
| kaku | F8, F9、F10 の入力シート、F11、F12 の差し戻しと実績の比較 | 財務モデル・計画書・入力シート・採択後の報告書を作り、審査役に確かめさせて直すときに使う。差し戻しへの対応と、説明の練習も扱う | 普段の言葉 |
| kiroku | F13 の一覧と手直し、版 | この会社について覚えていることを見る・直すとき、書類の前の版を見る・戻すとき、「提出した」と言われたときに使う | 普段の言葉 |
| nyuryoku | F10 の画面入力 | 電子申請の画面に入力し、一時保存まで進める | **担当者が呼んだときだけ**（`disable-model-invocation: true`） |

- 担当者が呼んだときだけ動かすのは、`nyuryoku` だけにする。
  - 理由：社長の GビズID でログインした国の申請画面を操作するため。
  - ほかの skill が変えるのは会社のフォルダの中だけで、版の履歴から戻せる。
  - 普段の言葉で「入力して」と言われたら、Claude は `/hojokin:nyuryoku` を選ぶよう案内する。
- skill どうしの説明が重ならないように、段階（探す・準備・書類・書く・記録・入力）で分け、社長が実際に言いそうな言葉を説明に入れる。正しく選ばれるかは実験 E10 で確かめる。
- どの段階にも共通の決まり（聞き方、推測しない、指摘を記録するかの判断、平易な説明）は、開いたときに毎回渡す短い文（1,200字ほど）に書く。プラグインは CLAUDE.md を配れないため。
- SKILL.md は500行未満にする。細かい手順は、skill の中の別ファイル（例：kaku の「説明の練習」「差し戻し」）に分ける。

### 4.3 subagent

| subagent | 使える道具 | モデル | 役目 |
|---|---|---|---|
| shinsa（審査役） | Read・Grep・Glob だけ | Opus 5.5 に固定（effort は high） | 申請書を、書いたときとは別の文脈で確かめる（8章） |
| yomitori（読み取り役） | Read・Grep・Glob と、MCP の読み取りの道具 | 読むものに合わせて、呼ぶときに替える（7章。書類の仕分けは Haiku 5.5、金額と明細は Sonnet 5.5、公募要領と様式は Opus 5.5） | 書類の種類・日付・相手先・金額を読み取る。公募要領から制度データの下書きを作る。様式の項目と書き込む位置を対応づける。結果は JSON で返し、保存は本体が道具で行う |

- プラグインの subagent では、hooks・mcpServers・permissionMode の設定が効かない。そのため、読み取りだけに絞るのは `tools` の一覧で行う。
- subagent はふだん裏で動くので、本体は、終わったという知らせを待ってから次に進む。
- これ以上は増やさない。書く作業には社長との聞き取りの流れが要るので、本体で行う。段階ごとに subagent を分けると、流れを渡し直す手間が増えるだけになる。

### 4.4 使わなかった案

| 案 | 使わなかった理由 |
|---|---|
| 機能ごとの skill（14個） | 説明が毎回文脈に入る。説明が重なると、違う skill を読んだり、使うべき skill を見落としたりする、と公式文書にある |
| 会社のフォルダに CLAUDE.md を置く | 毎回全文が文脈に入るうえ、決まりを守らせる力もない。毎回変わる情報は SessionStart で渡す |
| プラグインの settings.json の `agent` で、本体の道具を絞る | プラグインを入れた全部のフォルダで、Claude の動きが変わってしまう |
| Claude Code の自動の memory、subagent の memory | 会社のフォルダの外に置かれる。フォルダを別のパソコンに移すと失われ、会社をまたいで混ざるおそれもある。会社の記録はフォルダの中に持つ |
| Bash のスクリプト（`bin/`） | claude.ai と Cowork がインストールしない。Bash を使わせない方針とも合わない |
| prompt 型・agent 型の hook で決まりを守らせる | 結果がぶれ、費用もかかる。守らせる決まりは、コードの hook と道具の中だけで判定する |
| 書く役や、段階ごとの subagent | 聞き取りの流れが切れる |
| アプリの内蔵ブラウザ、Claude in Chrome | それぞれデスクトップアプリか拡張機能が要る。押したボタンが何かを hooks から確かめられない。画面を出さずに Claude Code を動かすテスト（headless）でも使えない |
| monitors（書類の見張り） | SPEC が求めているのは、「開いたとき」と「頼まれたとき」だけ |
| Output style | 毎回文脈に入る。文体は skill の物差しで足りる |

### 4.5 フォルダの形

**プラグイン（このリポジトリの根）**

```
.claude-plugin/plugin.json
skills/{sagasu,junbi,shorui,kaku,kiroku,nyuryoku}/SKILL.md（と補助ファイル）
agents/{shinsa,yomitori}.md
hooks/hooks.json と hooks/*.py（起動用の hooks/run.sh から動かす）
.mcp.json と server/（Python。uv で起動）
schema/（制度データ・会社の記録の JSON Schema）
knowledge/（同梱の知見：例年公募がある制度の一覧、作者の観点と構成の型、不備の型。例文は入れない）
docs/style-criteria.md、docs/DESIGN.md
evals/<ケース>/、tests/、mock/（模擬の申請画面）
```

**会社のフォルダ**

```
<会社のフォルダ>/
├─ 今の状態.html          まずこれを開く。進み具合の画面（4.6）
├─ 今の状態.xlsx          同じ内容の Excel
├─ 補助金の候補.docx       探した結果。探し直したら、このファイルを直す
├─ 財務モデル.xlsx         会社の数字の土台。前提と根拠、既存事業・新事業・合算（8.3）
├─ 入れ口/                書類をとりあえず入れるフォルダ（ほかの場所に入れてもよい）
├─ 原本/                  受け取った書類。読み取り専用。名前は「2026-10-20_見積書_〇〇機械.pdf」の形
│   └─ 登記・名簿／決算・税／見積・契約・請求／役所からの通知／会社の資料／写真・カタログ
├─ 案件/
│   └─ 2026_省力化（一般型）第9回/
│       ├─ 概要と流れ.docx     制度の概要、要件と義務、手続きの流れと期限、必要書類（4.6）
│       ├─ 公式資料/           公募要領・様式・手引き（読み取り専用）
│       ├─ 1_申請/
│       │   ├─ 申請書/         計画書（その1・2.docx、その3.xlsx）、入力シート.xlsx、根拠対照表.xlsx
│       │   └─ 添付する書類/   原本から作った写し（提出の決まりに合わせたもの）
│       ├─ 2_交付申請/         （同じ形）
│       ├─ 3_実績報告/
│       └─ 4_効果報告/1年目/ …
├─ 見るだけ/              前の版や提出版を見たいときだけ出す。読み取り専用で、開くたびに片付ける
├─ 記録/                  ツールが管理する（会社の記録、制度データ、書類の台帳、作業の記録）
├─ .hojokin/              会社のフォルダの目印、設定（今日の日付の差し替えなど）、専用ブラウザのログインした状態（パスワードは持たない）
├─ .claude/settings.json  初回に社長の了承を得て作る。このプラグインの道具を、毎回確かめずに使えるようにする
└─ .git/                  版の履歴。送り先は持たない
```

- **段階のフォルダは、制度データの「手続きの段階」から作る。** 持続化なら「1_申請」「2_見積書等の提出」「3_実績報告」「4_効果報告」になる。
- どの段階のフォルダも、中は「申請書」（作る書類）と「添付する書類」（写し）の2つにそろえる。採択後の報告書も、同じ所で同じように扱える。
- 役所から受け取った通知（採択の通知、交付決定の通知、差し戻しの文面や画面の写真）は、受け取った書類なので `原本/役所からの通知/` に置く。社長はどこに入れてもよく、ほかの書類と同じようにツールが整理する。貼り付けられた差し戻しの文面も、ここにテキストとして残す。案件とのつながりは台帳に持ち、今の状態の画面に示す。
- 不備を直すときも、ファイルは増やさない。写しは作り直し、申請書はその場で直す（前の版は履歴に残る）。
- `.hojokin/` のログインした状態は、版の履歴に入れない。

### 4.6 社長に渡す文書と、進み具合の画面

| 文書 | 中身 | 作り方 |
|---|---|---|
| 補助金の候補.docx | 3つの区分の候補、それぞれ合う理由、対象外になりそうな点、次の公募の見込み、予算の状況、出典の URL | Claude が調べた結果を、道具が Word にする |
| 概要と流れ.docx（案件ごと） | 制度の概要、自社が満たす要件、義務と返還の条件、自社の補助額の見込み、申請から効果報告までの流れと期限、加点が取れるか、必要書類の一覧、出典 | 数字・期限・一覧は、制度データと会社の記録からコードが入れる。説明の文は Claude が書く |
| 財務モデル.xlsx | 前提と根拠、5年の計画（既存事業・新事業・合算と補助金の指標）、1年目の月次、採択後は実績との比較。シートは3つ（採択後に4つ）（8.3） | 前提は Claude が聞き取りと書類から集める。数字の組み立ては道具が行う |
| 今の状態.html | 下の「進み具合の画面」 | 書類の整理・不備チェック・書き込み・提出のたびと、Claude が応答を終えるたびに、コードが作り直す |
| 今の状態.xlsx | 同じ内容を Excel で。シートは「締切」「書類」「不備」「申請書」「変更の履歴」。複数の案件は1つのファイルにまとめる | 同上 |

**進み具合の画面（今の状態）に並べるもの**

- 今日やること、近い締切、遅れている作業（全案件をまとめて締切順）
- 案件ごとの手続きの流れ（申請 → 交付申請 → 実績報告 → 効果報告1〜5年目）と、今いる段階、次の締切まであと何日
- 書類：必須・任意ごとの揃い具合と、書類ごとの状態（揃った・足りない・不備あり・期限が近い）。原本か写しか、場所、有効期限、元の原本が新しくなっていないか、提出版に入っているか、最後に変えた日
- 不備：重さごとの件数と一覧（直し方、直したか）
- 申請書：様式の項目ごとの進み具合（まだ・下書き・仮の印あり・確かめ中・完成）、文字数と上限、審査役の指摘の数
- 長い期限：効果報告などの5年先までの期限を、年ごとに
- 最近の変更（いつ・何を・だれが）と、会社について覚えていることの件数

開いたときにも、この中から「今日やること」と「近い締切」を会話に出す。

### 4.7 初めて使うときと、開いたときの流れ

**初めて使うとき**

- 目印（`.hojokin/`）のないフォルダでは、hooks は何もしない。MCP の道具も、補助金を探すこと（F1）と、会社のフォルダを作ること以外は動かない。
- どの skill も最初に目印を確かめ、なければ「このフォルダを〇〇社の会社のフォルダにしますか」と社長に聞く。
- 社長が了承したら、道具が一度に用意する：目印、フォルダの形（4.5）、版の履歴（Git）、`.claude/settings.json`。この後は、5章の決まりがすべて効く。
- そのセッションでは SessionStart がもう動いた後なので、どの段階にも共通の決まりは、会社のフォルダを作った道具が結果として返す。`.claude/settings.json` の許可がすぐ効くかは実験 E4 で確かめ、効かなければ開き直すよう案内する。
- デモは、この用意を済ませた会社のフォルダから始める。

**開いたときの流れ**（SessionStart hook。すべてコードで行い、モデルは使わない）

1. 社長が閉じている間に手で変えたファイルを、「社長」として履歴に残す。申請書の手直しがあれば、前の版との差分を作る（10章）。
2. 中身のハッシュで、増えた書類・変わった書類を見つける（移しただけ・名前を変えただけは除く）。原本と公式資料が書き換わっていたら、履歴から戻して知らせる（5章）。版の履歴に送り先の設定がないことも確かめる。`見るだけ/` を片付ける。
3. 今日の日付（差し替えを含む）から、今日やること・近い締切・遅れている作業を締切順に組み立てる。
4. 進行中の案件と次に申請する制度の公式サイトを、短い時間（数秒）で区切って確かめる。間に合わなければ「確かめられなかった」とする。
5. 会社の記録の要約、申請書の手直しの差分、どの段階にも共通の決まりを添え、10,000字以内に切って Claude に渡す。今の状態の画面も作り直す。

- 書類の整理と不備チェック、改訂の中身の読み取りは、Claude が社長の最初の発言のときに行う。hook は情報を渡せるだけで、Claude は社長の最初の発言まで動かないため。社長が別のことを頼んだら、そちらを先にする。

## 5. 必ず守らせる決まりと、Claude に任せること

すべての hook は、最初に会社のフォルダの目印（`.hojokin/`）があるかを確かめ、なければ何もしない。プラグインの hook は、プラグインを入れた全部のフォルダで動くためである。

| 決まり | 止める所 | すり抜けへの備え |
|---|---|---|
| 提出ボタンを押さない | 専用ブラウザの道具の中。押せるのは、表示名が「押してよいボタン」（次へ・一時保存・戻るなど。制度データの画面の定義から作る）に合うものだけ。ただし、表示名に「提出」「送信」「申請する」「確定」「完了」などを含むボタンは、制度データにかかわらず押さない（この禁止の語はコードに固定する） | 制度データは AI が下書きするので、一覧に誤って「提出」が入っても止まるよう、禁止の語を優先する。Enter キーで送る機能と、Claude が書いた JavaScript を動かす機能は、道具に持たせない。会社のフォルダでは、内蔵ブラウザ・Claude in Chrome・画面を操作する道具（computer use）のクリックや入力を PreToolUse で拒む |
| 確認・誓約・同意のチェック欄に入れない | 同じ道具の中。制度データの入力シートで「担当者が入れる欄」としたものと、項目名に「確認」「誓約」「同意」「宣誓」を含むチェック欄には入れない | 項目名の文字に頼る分、確実さは少し下がる（作者の了承済み）。担当者が入れる欄がある画面（最初の誓約や宣誓の画面など）では、道具は入れるべき欄を示して止まる。担当者が「入れた」と伝えたら、チェックが入っていることを読み取って確かめてから続ける |
| パスワードを扱わない | 同じ道具の中。パスワード欄には入れない | ログインは、担当者が専用ブラウザで自分で行う |
| 画面入力は、担当者が呼んだときだけ | `nyuryoku` に `disable-model-invocation: true` を付け、Claude が自分で始められないようにする。加えて、専用ブラウザの道具は、担当者が `/hojokin:nyuryoku` を呼んだときに UserPromptSubmit hook が記録する「画面入力の許可」がないと動かない。許可はそのセッションの間だけ有効 | `disable-model-invocation` は skill が自動で選ばれることを止めるだけで、道具そのものは止めないため、許可の記録で道具を止める |
| Word・Excel の様式と申請書類の書式を壊さない | Word・Excel に書けるのは、MCP の書き込みの道具だけ。Write・Edit で .docx・.xlsx などに書くことは PreToolUse で拒む。道具は、決めた「書いてよい範囲」だけに書く。書いた後に、書式・余白・表の行と列・結合したセル・数式・入力規則・シートの構成・ヘッダーとフッターを、直前の版（社長が手で直した後なら、その版）と比べ、書いてよい範囲の外が1か所でも変わっていたら保存しない | 書いてよい範囲は、様式なら制度データの入力欄（行を足してよい表も、ここで決める）、ツールが作る申請書類なら道具のひな形で決める（例：根拠対照表の行、財務モデルの「実績」シートの追加）。一時ファイルに書いて比べ、問題がないときだけ置き換える。PDF にするときは写しを作り、元は変えない |
| Bash を使わない | PreToolUse で拒む | ファイルの操作は、すべて MCP の道具と Write・Edit を通る |
| 原本・公式資料と、ツールが管理する場所（`記録/`、`見るだけ/`、`.hojokin/`、`.git/`、`.claude/`）を、Claude が Write・Edit で書き換えない | PreToolUse でパスを確かめて拒む。MCP の道具は、原本と公式資料の中身を書き換える機能を持たない（置き場所への移動と名前の付け直しは、書類を整理する道具だけが行う）。`記録/` などへの書き込みは、それぞれの道具が決まった形で行う。原本と公式資料は読み取り専用にする | 原本と公式資料は、開いたときと、Claude が応答を終えるたびに、台帳のハッシュと照らす。変わっていたら履歴から戻し、社長に知らせる。会社の記録は、社長が頼めば Claude が道具で直し、社長がファイルを手で直してもよい（どちらも履歴に残る） |
| 版のファイルを増やさない | PreToolUse で、名前に「_v2」「最終」「修正版」「コピー」などを含む新しいファイルを拒む。MCP の道具は、決まった名前でしか書かない | 前の版は Git に残る |
| フォルダの外に書かない | PreToolUse と MCP の道具の中 | 外のファイルを取り込むときは写すだけで、元のファイルは動かさない |
| 履歴を外に送らない | Git の操作は MCP の道具だけで行い、送る機能を持たせない | 開いたときに、送り先の設定がないことを確かめる |
| 版を自動で残す | UserPromptSubmit で、社長が手で変えた分を「社長」として残す。Stop で、ツールが変えた分を「ツール」として残す。理由には、その応答のもとになった社長の依頼の文を使う | — |
| 開いたときに渡す情報を10,000字以内にする | SessionStart で情報を組み立てるコードが、上限で切る | 超えると、先頭2,000字だけが渡る（すべての hook に共通の決まり） |
| 補助プログラムが動かないときは止める | hook は、起動用の小さなスクリプトから動かす。スクリプトは、まず目印を確かめ、目印がなければ何もしない。目印があるのに Python が動かないときだけ、書き込みとブラウザの操作を拒む | 決まりが、気づかないうちに外れることを防ぐ。Mac では sh で動かす。Windows でも動く形にするが、期間中は確かめない（SPEC 4章） |

**Claude に任せること（強制しない）**

- 文体の「注意」の項目、構成、質問の言い回し、勧める任意書類、記録に残すかどうか、審査の観点の重み。
- 1回の質問を3つまでにすることは強制せず、テストで確かめる。
- 文体の「要修正」（100字を超える文、記号の残り、です・ます調とである調の混在）は、完成かどうかの判定にだけ使い、作業は止めない。

好みの問題は、どれも強制しない。

## 6. コードで処理することと、Claude に任せること

| コード（MCP の道具と hook） | Claude |
|---|---|
| 今日の日付（差し替えを含む）、日本時間での表示、締切から逆算した日程、期限の計算（決まった日付、ある出来事からの期間、いくつかの期限のうち早いほう）、加点が間に合うかの判定 | 聞き取り（答えに応じて次の質問を変える）と、平易な説明 |
| 数値の要件（労働生産性、給与支給総額、最低賃金、補助額、年平均の伸び） | 候補を探し、会社に合うかを判断する（F1）。予算の状況を調べる |
| 二重受給の照合（経費の項目を案件どうしで比べる） | 公募要領を読み、制度データの下書きを作る（読み取り役） |
| 制度データの検査（JSON Schema、すべての項目に出典があるか、出典の裏取り、資料どうしの食い違いの一覧） | 書類の種類・日付・相手先を読み取る（読み取り役） |
| PDF・Word・Excel の読み取り（資料はページごとの文字にし、スキャンした PDF と写真はページの画像にする）。根拠の文と引用がそのページにあるかの照合。見積書などの金額の計算の照合。様式の見出し・表・セルの一覧づくり。様式への書き込みと、書き込み前後の構造の比較。図表の作成と写真の挿入。PDF への変換 | 様式の項目と、書き込む位置の対応づけ（読み取り役） |
| 補助金の候補.docx、概要と流れ.docx、今の状態（HTML と Excel）の作成 | 概要と流れの説明の文 |
| 書類の変化の検出（中身のハッシュで見る。移しただけ・名前を変えただけは変化としない）、同じ中身の検出、整理、写しの作成、元の原本の記録、古い原本から作った写しの検出 | 解釈が要る不備（補助の対象にならない経費など）の判断 |
| 根拠対照表との照合（数字と日付は、「1,500万円」「2027年3月」のような決まった書き方を探して見つける。固有名詞は、会社の記録と書類から作った一覧で見る）、文体の A・B と会社の「避けたい言い方」の数え上げ、仮の印と空欄の数、文字数（画像と表の換算を含む）、入力シートと制度データの照合 | 計画書を書く。構成を決める。図表に何を載せるかを決める |
| 財務モデルの計算（月次と年次、既存事業・新事業・合算、付加価値額などの指標）。計画書・様式・入力シートの数字と、財務モデルとの照合 | 前提を聞き取って根拠を付け、売上と経費の分け方を決める。前提に無理がないかを判断する |
| 社長が申請書を手で直した箇所の検出（前の版との差分） | 直した箇所が、事実・言い回し・方針のどれかを判断し、記録に残すかを決める |
| 会社の記録の追加と、食い違いの検出。記録の一覧と変更の履歴（Git の履歴から作る） | 「次からもそうしますか」と確かめること。審査役の判断（文体の C、筋の通り、審査項目ごとの採点） |
| 版の管理（Git。提出版の記録と、「見るだけ」への取り出し） | 想定問答。差し戻しの文面を読み取ること |
| jGrants の検索、開いたときに渡す情報、専用ブラウザでの入力（入力シートの値を欄の名前で入れ、入れた後に読み取って比べる） | 入力シートと画面の欄が合わないときの判断 |

- 仮の印と空欄は、文章では決まった形（【仮：…】、【空欄：…】）で書き、コードで数えられるようにする。財務モデルの前提や経費明細のような数字の欄には文字を入れず（数式が壊れるため）、隣の「状態」の欄に「仮」と書いてセルに色を付ける。コードはこの「状態」の欄で数える。
- 質問は、普段の文章で「【質問】」と書いた後に、番号と「（理由：…）」を付けて並べる。Stop hook がそれを読み取り、案件と段階を付けて、質問の記録に残す。この形なら、headless のテストでも同じように動く。

## 8. 審査役と、「書く → 確かめる → 直す」の繰り返し

**審査役に渡すもの**（確かめの道具が、1つのフォルダにまとめて作る）

- 計画書の本文（様式の項目ごと）
- 制度データから抜き出したもの（審査項目、加点、様式の項目と分量）
- 根拠対照表と聞き取りの記録
- 会社の記録のうち、書き方の決まりと、過去の審査コメント
- 文体の基準の C
- コードによる確かめの結果

書いたときの考えの経過は渡さない。

**審査役が返すもの**（JSON。SubagentStop hook が、本体を通さずにそのまま保存する。確かめの道具は、審査役に渡すフォルダに「確かめの番号」と計画書のハッシュを書いた控えを置く。hook は、終わった subagent が審査役のときだけ、その控えと結果を結び付けて保存する）

- 聞き取りと食い違う記述（T9-2）
- 文体の C の12の観点ごとに、可か不可かと、その理由。あわせて、数字・単位・固有名詞・期日が1つもない段落（文体の基準 A の「具体性」）（T9-3b）
- 「現状と目標 → 課題 → 解決策 → 効果」の4つの段がそろっているかと、つながりが切れている所（T8-8）
- 目安のない項目の長さ（T8-9）。持続化の4,000字のように上限しかない項目も含め、長すぎないか、足りないか
- 審査項目と加点項目ごとの点数と理由、弱い所（T9-5）
- 過去の審査コメントに応えているか（T13-9）、会社の書き方の方針と構成の決まりに沿っているか（T13-6）
- 指摘ごとの重さ（要修正・要確認・助言。言葉の意味は1.1）

点数は参考として見せるだけで、合否には使わない。本体が指摘を落としたり書き換えたりできないよう、結果は hook が保存する（hook で取り出せるかは実験 E3 で確かめ、だめなら道具で保存し、形をコードで確かめる）。

**確かめの流れ**

1. コードで確かめる（費用はかからない）。
2. 通らなければ直して、1に戻る。このときは審査役を呼ばない。
3. 通ったら審査役を呼ぶ。
4. 要修正の指摘を直して、1に戻る。要修正がなければ完成とする。要確認と助言の指摘は社長に示し、直すかは社長が決める。

**完成とする条件（すべて満たすこと）**

- コードの確かめ：根拠のない記述0、食い違い0、本文に出典の書き込み0、文体 A の要修正0、B と会社の「避けたい言い方」に当たる言い回し0（社長が残すと決めたものは除く。A と B が重なる項目は A に従い、A で「注意」の項目は判定に使わない）、仮の印0、空欄0、文字数の超過0、数値の要件を満たす、計画書・様式・入力シートの数字が財務モデルと一致、財務モデルに仮の前提が残っていない、見積書が要る経費に見積書がある（8.4）、計画書で使った制度データの値と書類の読み取りに「要確認」が残っていない。
- 審査役：今の版の計画書を確かめた結果で、要修正0。
- 完成の記録は、確かめの道具だけが残す。道具は、保存された審査役の結果が今の版のハッシュと合うかをコードで確かめてから残す。

**途中でやめて社長に返す条件**

- 社長に返すまでの間に審査役を3回（仮）呼んでも、要修正が残る。社長の答えをもらって直した後は、数え直す。
- 同じ指摘が2回続く（直しても良くならない）。
- 社長の答えや判断が要る（仮の印、空欄、足りない事実、B の言い回しを残すか）。このときは、3回を待たずにすぐ聞く。
- 文章を直しても通らないコードの確かめがある（例：数値の要件を満たさない。前提や計画そのものを変える必要がある）。このときも、すぐに社長に返す。
- コードの確かめで見つかった問題を直して確かめ直す繰り返しが、5回（仮）を超えた。

返すときは、直したこと、残った指摘と直し方の案、質問（3つまで）を示す。

### 8.1 誤りを見つける仕組み

| 誤りが起きる所 | 確かめ方 |
|---|---|
| 制度データ（読み違い） | JSON Schema で形を確かめ、出典の裏取り、重要な項目の2回の読み取り、資料どうしの食い違いの一覧、作者の正解との突き合わせを行う（9.2） |
| 質問への答え | 答えに付けた引用が、そのページに本当にあるかを道具が確かめる（9.2） |
| 会社の書類の読み取り | 読み取り役は、読めない値を「要確認」として返す。金額は計算で照合し、日付・金額・名義の食い違いは書類どうしで照らす（8.4） |
| 計画書の数字・固有名詞・日付 | 根拠対照表と照らす（根拠なし0、食い違い0）。計算はすべて道具で行い、Claude は計算しない。数字は財務モデルから取り、計画書・様式・入力シートと財務モデルが一致するかを、コードで照らす |
| 財務モデル | 前提すべてに根拠と出典を付ける。Python の計算と、Excel の数式の結果が一致するかを、開発中のテスト（LibreOffice で計算し直す）で確かめる。合算が既存事業と新事業の和になっているか、月次の合計が1年目と合うかも確かめる |
| 計画書の中身と聞き取りの食い違い | 審査役 |
| 様式の崩れ、文字数 | コード（書き込み前後の構造の比較、文字数と換算） |
| 期限・日付 | すべて道具で計算する。今日の日付は差し替えに従う |
| 画面への入力 | 入れた後に画面の値を読み取り、入力シートと比べる |
| 製品全体の振る舞い | テスト（11章）と Δ |

### 8.2 読みやすい申請書にする仕組み

- **構成**：「現状と目標 → 課題 → 解決策 → 効果」を、制度データの様式の項目に割り当てる。各項目の最初に結論を書く。作者の観点と構成の型（例文は入れない）を物差しにする。公開されている採択事例は、作者が観点と構成の要点だけを knowledge/ に書き起こして参考にし、文章は流用しない（どこまで参考にするかは14章）。
- **中身**：会社の資料と聞き取りから、その会社の事実・数字・現場の出来事・社長の判断の理由を使う（文体の基準 C3〜C6）。社名を他社に替えても通じる文にしない。
- **文体**：文体の基準の A・B と、会社の「避けたい言い方」をコードで数える。C は審査役が読んで確かめる。
- **分量**：制度データの上限と目安に合わせる。上限はシステムの上限であって、書くべき長さではない。持続化の4,000字のように上限しかない項目や、指示がない項目は、審査項目を満たすのに必要十分な長さにし、上限まで埋めない（審査役が確かめる）。
- **図表**：作業の前後比較、工程表、数値計画のグラフは、道具が数字から作る（数字は根拠対照表と同じもの）。社長が用意した写真も入れる。
- **最後の確かめ**：作者が、審査役と同じ採点表と文体の基準の C で読む（T9-6）。

### 8.3 財務モデル（計画の数字の土台）

計画書の数字は、表面的なものになりやすい。そこで、前提から数字を組み立てた財務モデルを先に作り、計画書・様式・入力シートの数字はすべてここから取る。後から実績と比べて確かめることもできる。

**大きさの決まり**：財務に詳しくない社長や担当者でも、自分で説明できる大きさにする。ただし、売上を「単価 × 数量」に、人件費を「人数 × 時間 × 単価」に分けることはやめない。ここを省くと、数字の裏付けがなくなるためである。

- **置き場所**：会社のフォルダの直下に「財務モデル.xlsx」を1つだけ置く。2件目の計画は1件目の計画を含めて作るので、案件どうしの数字が食い違わず、同じ経費を二重に数えることもない。2件目を足すと合算は変わるが、提出した案件の数字は、提出版に入れた財務モデルで固定する。計画書と財務モデルの照合（T8-11）は、提出済みの案件ならその提出版の財務モデルと、作成中の案件なら今の財務モデルと行う。
- **シートは3つ**（採択後に「実績」を1つ足す）

| シート | 中身 |
|---|---|
| 前提 | 数字の元になる前提だけを並べる。1社で15個ほどまで（多くても20個）。前提ごとに、値・単位・「この数字は何か」の一言・根拠（決算書・見積書・聞き取り・統計）と出典。決まっていないものには仮の印を付ける。社長が書き換えてよいのは、このシートの色を付けたセルだけ |
| 計画（5年） | 上に「まとめ」として、大事な数字を5つほど言葉で示す（例：5年後の売上、付加価値額の伸び、給与の伸び、要件を満たすか）。その下に、既存事業・新事業（案件ごと）・合算を同じ行の並びで5年度分示す。売上は商品や販路で2〜3区分まで、経費は原材料費・人件費・減価償却費・その他の経費の4区分まで。人件費は「給与支給総額」と「法定福利費など」に分けて持つ（給与の要件に使うのは給与支給総額で、付加価値額に使う人件費とは範囲が違うため）。最後に、補助金の指標（付加価値額、労働生産性、1人当たり給与支給総額、年平均の伸び、補助額など）と、要件を満たすかの判定を置く |
| 月次（1年目） | 1年目の12か月分。売上と経費を月ごとに示し、季節の波や立ち上がりを見えるようにする。合計は計画の1年目とつながる |
| 実績（採択後に足す） | 実績報告と効果報告のときに実績を入れ、年度ごとに計画と比べる |

- **分かりやすくする工夫**
  - 数式には名前を付けたセルを使い、「＝単価_冷凍惣菜 × 数量_冷凍惣菜」のように言葉で読めるようにする。
  - 専門用語には一言の説明を付ける（例：付加価値額は「営業利益＋人件費＋減価償却費。会社が新しく生み出した価値」）。
  - Claude は、財務モデルを見せるときに「売上は〇〇を月〇個、〇円で売る前提です」のように、前提を普段の言葉で説明する。
- **簡単にしすぎないための工夫**
  - 「まとめ」に、数量が計画より2割少なかった場合でも要件を満たすかを1行で示す。要件を満たせないと返還につながるため。
  - 新事業をしない場合（既存事業だけ）と合算を並べて、補助事業の効果を数字で示す。
- **新事業の列の置き方**：持続化のように新しく売るものは、その売上と経費を置く。省力化のように今の事業のやり方を変えるものは、導入による増減を置く（作業時間が減って下がる人件費、空いた人手で増やす生産の売上と原価、設備の減価償却費）。どちらも、合算の列で既存事業と足し合わせる。
- **作り方**：前提は、Claude が聞き取りと書類から集め、根拠を付ける。数字の組み立ては、すべて道具が Python で行う。Excel には数式のまま書き、どの数字がどの前提から来たかを、社長が Excel で追えるようにする。Excel の数式は、開いたときに Excel が計算する。
- **つながり**：計画書の数字は、根拠対照表に「財務モデルの前提 P-07」のように示す。そこから決算書や聞き取りまでたどれる。
- **審査役**：前提が実績・見積・統計に基づいているか（文体の基準 C4）、売上や経費の伸びに無理がないかを確かめる。
- **採択後**：実績報告と効果報告では、実績のシートに数字を入れ、計画との差と、要件（給与支給総額など）を満たせそうかを示す。満たせない見込みなら、返還の条件とあわせて早めに知らせる。

### 8.4 書類と経費を正しく読み取る仕組み

**スキャンした PDF と写真**

- 道具が、PDF に文字が入っているかを確かめる。文字がない PDF（スキャンしたもの）や写真は、ページを画像にし、向きを直してから読み取り役に渡す。Claude は画像をそのまま読める。
- 別の文字認識のソフトは入れない。初回の用意が増えるうえ、読み取りの正しさは次の照合で確かめるため。
- 読み取る項目は、書類の種類ごとに決めておく。見積書なら、発行日、有効期限、宛名、発行者、品名・型番、数量、単価、金額、小計、消費税、合計、税込か税抜か。請求書と納品書は、これに登録番号や納品日などを足す。
- 金額と明細は、Sonnet 5.5 で読む（7章）。

**計算で照合する（コード）**

- 明細ごとに「数量 × 単価 ＝ 金額」、明細の合計 ＝ 小計、小計 ＋ 消費税 ＝ 合計、税率（10%・8%）が合うかを確かめる。
- 合わなければ、読み違いの疑いがある。その部分を拡大した画像で、Opus 5.5 に読み直させる。
- それでも合わなければ「要確認」とし、その部分の画像と読み取った数字を並べて、社長に確かめてもらう。推測で埋めない。
- 書類どうしも照らす。見積書・納品書・請求書の品名と金額、宛名と会社の記録の社名、日付の順（見積 → 発注 → 納品 → 請求。交付決定より前の発注は事前着手）を確かめる。

**経費の読み取り**

- 経費の一覧は、入力シートの経費明細の欄にまとめ、別のファイルは作らない。行ごとに、経費の区分、品名、数量、単価、金額（税抜）、根拠の種類（見積書・カタログ・メモ・聞き取り）と出典を持つ。
- 見積書から読んだ金額は、上の照合を通ったものだけを使う。
- メモや社長の話からの金額（例：「チラシ代は30万円くらい」）は、仮の印を付けて入れ、見積書がそろったら差し替える。制度データで見積書が要る経費（例：50万円以上の設備）は、見積書がないと完成にしない。
- 経費の区分は、制度データにある「補助の対象になる経費」の定義（出典付き）に照らして、Claude が判断する。迷うものや、対象外になりそうなものは「要確認」とし、資料の該当ページを示す。資料に書かれていなければ、問い合わせ文の案を作る。
- コードで確かめるもの：税込と税抜の混在、経費の合計と補助額（上限と補助率）、財務モデル（投資額と減価償却費）や計画書との一致、2つの案件で同じ経費を数えていないか（二重受給）。

確かめ方は T5-1（不備を仕込んだ書類セットに、スキャンした PDF と写真を含める）、T5-8（スキャンした書類の金額と明細が正解と一致するか）、T8-13（スキャンした見積書とメモから作った経費明細が正解と一致するか）。

## 9. 制度データの形

- 置き場所は `記録/制度データ/<制度>_<公募回>.json`。プラグインの JSON Schema で検査する。
- どの値も「値」「出典（資料とページ）」「根拠の文（資料から抜き出した短い文）」「状態（確認済み・読み取れない・資料で食い違い・要確認）」の組で持つ。
- 次の表は、両制度の実際の値で、1つの形が両方を表せることを示したもの。略号は15.3の資料名を指す。

### 9.1 どの補助金でも動く流れ

1. **探す**：jGrants の検索、同梱の「例年公募がある制度の一覧」、所在地の都道府県・市区町村のサイト、厚生労働省の助成金から候補を集める。
2. **制度データを作る**：公募要領・様式・手引きをダウンロードし、読み取り役が制度データの下書きを作る。道具が形を確かめ、出典を裏取りする。読み取れない項目は空けたまま、問い合わせ文の案を付けて社長に示す。
3. **様式を対応づける**：
   - 様式がある制度は、道具が Word・Excel の見出し・表・セルの一覧を作り、読み取り役が様式の項目と書き込む位置を対応づけて、制度データに書く。
   - 様式がない制度は、入力シート（画面の項目）に書く。
   - どちらも決まっていない制度は、様式の項目の一覧から計画書の Word を作る。
4. **あとは制度データで動く**：書類の一覧、日程、段階のフォルダ、書く、確かめる、入力、採択後の手続きのすべてが、制度データで動く。プログラムは変えない（T0-1）。省力化と持続化のほかに、補助金と助成金を1つずつ選んで確かめる（T3-6）。

### 9.2 公募要領を正しく読み、質問に正しく答える仕組み

**資料をページ付きの文字で持つ**

- 公式資料をダウンロードしたら、道具がページごとの文字にして `記録/資料の本文/` に置く。印刷されたページ番号と PDF のページの対応も取る（ずれ方は9章の注のとおり）。出典は、いつも印刷された番号で示す。
- 文字を取り出せないページ（画像だけのページ）や、表が崩れるページは、ページの画像も読み取り役に渡す。

**制度データを作るとき**

- 読み取り役は、一度に全部を読まず、章ごとに読む。値ごとに「根拠の文」（資料から抜き出した短い文）とページを付けて返す。
- 道具が裏取りする。根拠の文がそのページに本当にあるか、値がその文の中にあるかを確かめ、どちらかが外れたら「要確認」にする。
- 重要な項目（締切、補助上限、補助率、数値の要件、必須書類、補助の対象にならない経費）は、読み取り役にもう一度、別の呼び出しで初めから読ませる。2つが食い違えば「要確認」にする。
- Q&A と公募要領で書き方が違うときや、回の違う資料が混ざるときは、両方の値と出典を「資料どうしの食い違い」として持ち、社長に示す。
- 新しい版や Q&A が出たら、変わったページだけを読み直す（F7）。
- 作者が作った正解と突き合わせる（T3-7）。

**質問に答えるとき（F4）**

1. 道具で、資料の本文を言葉で探す（言い換えも含めて何通りか）。制度データにある項目なら、そこから出典をたどる。
2. 見つかった箇所だけを根拠に答える。答えの形は「結論 → 根拠（資料名・ページと、短い引用）→ 注意」。どの回の資料かも書く。
3. 道具が、引用がそのページに本当にあるかを確かめる。なければ答えを出し直す。
4. 見つからなければ「資料には書かれていません」と答え、事務局への問い合わせ文の案を作る。推測で補わない。

確かめ方は T3-7・T3-8（制度データ）、T4-1（答えが資料にある15問と、ない5問）、T4-2（引用がそのページにない答えを道具が見つけるか）。

## 10. 会社の記録と、書類の版

**会社の記録**（`記録/会社の記録.json`。項目ごとに id を持つ）

| 種類 | 持つもの |
|---|---|
| 事実 | 値、変わりうる情報か、出典（原本とページ／質問と答えた日／社長の手直し）、覚えた日、最後に確かめた日、状態（有効・食い違いあり） |
| 書き方の決まり | 区分（直した表現・好む言い方・避けたい言い方・書き方の方針・構成）、内容、きっかけ（案件・社長の発言や手直し・日付） |
| 不備と差し戻し | 案件、手続きの段階、内容、原因、次に注意する書類と照合の決まり、出典（差し戻しの文面や写真の原本）、受け取った日 |
| 申請と採否 | 案件、結果、審査コメント、指摘された審査項目、出典（採否の通知の原本）、通知の日 |

どの種類も、覚えた日と、出典（原本・質問・社長の発言）を必ず持つ。

**学ぶきっかけと、残し方**

| きっかけ | 見つけ方 | 残し方 |
|---|---|---|
| 会話での指摘・訂正 | Claude が判断する。UserPromptSubmit hook が、「直して」「違う」「〜ではなく」などの言葉を見つけたら、「記録に残すか判断する」という一言を添える | 道具で会社の記録に加える。「今回だけ」は残さない。どちらとも取れるときは「次からもそうしますか」と確かめる |
| 社長が Word・Excel の申請書を手で直した | 社長が送ったとき（UserPromptSubmit）と開いたとき（SessionStart、4.7）に、前の版との差分をコードで出す。差分は3,000字（仮）までにし、超えたら直した項目の一覧だけを渡して、中身は道具で読ませる | 差分を Claude に渡す。Claude は、事実の訂正か、言い回しか、方針かを判断して残す。迷えば聞く |
| 差し戻し | 社長が貼った文面や、画面の写真 | 不備の型として残し、次からの不備チェックの照合に加える |
| 採否と審査コメント | 社長が入れた通知 | 指摘された審査項目を残し、次の申請で審査役が応えているかを確かめる |
| 会社の資料・過去の申請書 | 最初に、読み取り役が読む | 事実として、出典と日付を付けて残す |

**学んだことを次に生かす仕組み**

- 開いたとき：記録の要約（変わりうる情報、最近増えた決まり）を渡す。
- 書くとき：`kaku` は書き始める前に、道具でその制度・その項目に関係する事実と書き方の決まりを取り出す。記録から書いた箇所は、根拠対照表に記録の項目として残る。
- 確かめるとき：「避けたい言い方」は、コードの文体の確かめに加わり、出てきたら要修正になる。同じ文字の言い回しは、コードが必ず見つける。活用や語順を変えた言い回し、書き方の方針、構成の決まりは、審査役が確かめる。
- 書類を集めるとき：過去の差し戻しの型が不備チェックに加わり、同じ不備を前もって注意する。
- 記録は会社のフォルダの中にあるので、セッションが変わっても、フォルダを別のパソコンに移しても残る。
- 変更の履歴（いつ・何から何に・だれが）は、Git の履歴を項目ごとにたどって作る。同じ情報を2か所に持たない。
- 記録と違う値が出てきたら、道具が食い違いとして知らせる。Claude は両方を出典付きで示し、社長に決めてもらう。

**書類の版**

- 会社のフォルダの Git で管理する。送り先は持たない。
- git のコマンドがない Mac でも動くように、Python だけで動く Git（dulwich）を第一の候補にする（実験 E5）。
- 書類ごとに1つのファイルを直して使う。履歴の1件ごとに、「書類」「理由」「だれ（ツール・社長）」「案件」「段階」を付ける。
- 前の版や提出版を見るときは、`見るだけ/` に読み取り専用で取り出し、次に開いたときに片付ける。作業のファイルは増えない。
- 戻すときは、戻したこと自体を新しい記録として残す。履歴は書き換えない。
- 「提出した」と言われたら、提出版の記録（Git の印）と、写しを含むファイルのハッシュの一覧を残す。取り出すと、提出したときと同じ中身になる。
- 原本と公式資料は、入れたときの1版だけが残る。

## 11. テストの組み方

`claude plugin eval` には、次の制約がある。

- 自作のコードで採点できない。
- 社長役のような、模擬の利用者を置けない。
- 複数回のやりとりは、過去の会話のファイル（`history_file`）を渡す形だけ。
- `file_exists` が数えるのは、実行中に新しくできたファイルだけ。
- 準備のスクリプト（scaffold）は、`--scaffold` を付けたときだけ動く。

**採点の優先順**

1. `regex`：最後の応答、質問の記録、確かめの結果のファイルの文字を見る。
2. `tool_used`：読み取り役や審査役を呼んだか、道具に何を渡したか。
3. `file_exists`。
4. AI による判定（`llm`）は、T11-1 と T2-3 だけにする。SPEC で審査員役が判定するテスト（T8-8、T9-3b、T13-9 など）は、審査役が保存した結果に、判定と理由がそろっているかを `regex` で見る。

**残した出力を、あとから pytest で調べる**（`--keep-temp`）

- T5-1：仕込んだ不備の一覧と突き合わせる。
- T5-4：ファイルの移動先と名前。
- T3-7：制度データの正解との一致。
- T5-8・T8-13：読み取った金額と明細、作った経費明細が、正解と一致するか。

**Δ（プラグインなしとの差）**

- `--ablation with-without` で測る。
- プラグインなしでも同じ物差しで採点できるケースに絞る。候補は T0-10（推測しない）、T1-1、T4-1、T5-1、T8-5、T9-2、T12-3。
- 採点は最後の応答の文字で行い、プラグインの道具が作るファイルには頼らない（例：T5-1 は、仕込んだ重大な不備がすべて最後の応答に出てくるかで採点する）。制度データのファイルを調べる T3-7 は、Δ の候補にしない。
- 結果は README と動画に載せる。

## 12. 開発中の検証体制

| いつ | 何を | 仕組み | 費用 |
|---|---|---|---|
| ファイルを直したときの、各回の終わり | 構成の検査と、速いテスト（通信なし、数十秒） | 開発用リポジトリの Stop hook（`.claude/settings.json` に書き、プラグインには入れない）。落ちたら、直すまで続けさせる（8回まで） | かからない |
| 1つの機能を作り終えたとき | その機能の振る舞いテストを1回ずつ | `claude plugin eval . --scaffold --trust-plugin --tag <機能> --runs 1 --ablation none --max-cost-usd <上限>`。通るまで直すときは `/goal` を使う。判定役は会話しか見ないので、終わりの条件は「eval の出力で、全ケースの合格を示した」にする | 少し |
| コミットの前 | 仕様に照らして、正しさに穴がないか | 開発用の subagent `spec-check`（Read・Grep・Glob、Opus 5.5。プラグインには入れない）。SPEC の該当箇所と変更を照らし、要件の抜け、違う振る舞い、テストの抜けだけを返す。文体は見ない | 少し |
| 毎日の終わり | 振る舞いテストを全部1回 | `--runs 1 --ablation none` | 中くらい |
| 11/6 と 11/8 の朝 | Δ と、3回とも合格するか | Δ のケースは `--ablation with-without`、全部は `--runs 3` | 中くらい |

**振る舞いテストの費用を抑える工夫**

- 保存しておいた状態から始めて、ケースを短くする。
- 機能ごとのタグを付け、直した機能のケースだけを回す。
- 採点はコードを優先する。AI の判定役は haiku を基本にし、読んで判断するものだけ Sonnet 5.5 にする（7章）。
- `--max-cost-usd` で上限を決める。
- Δ と3回の実行は、節目にだけ行う。
