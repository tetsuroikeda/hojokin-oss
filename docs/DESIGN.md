# 設計：補助金申請を自社で進めるための Claude Code プラグイン（仮称 hojokin-oss）

- 作成日：2026年11月3日。SPEC.md の要件を、どう作るかを決める文書です。SPEC の範囲は削らず、すべて作ります。
- ハッカソンの審査の配点（Impact 30、Demo 25、Claude の使い方 25、深さ 20）を踏まえ、部品を増やすより、選んだ理由がはっきりした少ない部品で、確実に動く設計にしています。

設計の初めに作者と決め、SPEC にも書いたこと。決まりの本文は SPEC の該当箇所にあり、ここでは要点だけを示す。

| 申請者自身が作成・申請する決まりへの対応 | ログイン、確認・誓約・同意のチェック欄（宣誓の欄を含む）、最後の提出は担当者が行う。それ以外の入力（加点の選択など）は、ツールが一時保存まで進める。チェック欄の見分け方は5章 | 2.3、4章 |

### 1.1 この文書で使う言葉

SPEC の用語の表にある言葉（制度データ、原本、写し、提出版、担当者、仮の印、ファイルの道具など）は、そのまま使う。ほかに次の言葉を使う。

| 言葉 | 意味 |
|---|---|
| 本体 | 社長と話している Claude（subagent ではないほう） |
| 審査役 | 申請書を、書いたときとは別の文脈で確かめる subagent。SPEC の F9 にある「書くAIとは別の文脈のAI」で、テストでいう「審査員役」の採点もこの役が行う |
| 読み取り役 | 書類や公募要領を読み取る subagent |
| 道具 | プラグインのコードが行う、答えが1つに決まる処理（計算、書き込み、照合など）。skill に入れた Python のスクリプトで行い、プラグインは MCP のサーバーを持たない。Claude Code に組み込みの道具（SPEC の「ファイルの道具」、Bash、ブラウザの道具）とは別 |
| ブラウザの道具 | デスクトップアプリの内蔵ブラウザと Claude in Chrome が持つ、ページを読む・クリックする・入力する道具。Claude Code とデスクトップアプリに組み込まれていて、プラグインが作るものではない |
| 要修正・要確認・助言 | 審査役の指摘の重さ。要修正は直すまで完成にしない。要確認と助言は社長に示し、直すかは社長が決める。書類の不備の重さ（SPEC F5）は、別に「重大・要確認・助言」を使う |
| 「要確認」（値の状態） | 制度データの値や書類の読み取りで、裏付けが取れていないもの。計画書で使う値に残っていたら完成にしない |
| 書いてよい範囲 | Word・Excel のうち、道具が書き込んでよい所。様式なら制度データの入力欄（行を足してよい表も、ここで決める）、ツールが作る書類ならスクリプトのひな形で決める（例：根拠対照表の行、財務モデルの「実績」シートの追加） |
| 画面入力の許可 | 担当者が `/hojokin:nyuryoku` を呼んだときに hook が残す記録。これがないと、会社のフォルダでは、ブラウザの道具のクリック・入力・添付を hook が拒む |
| 完成の記録 | 確かめの道具が、完成の条件（8章）をすべて満たしたときだけ残す記録 |

## 4. プラグインの構成

### 4.1 部品の使い分け

考え方は「必ず守る決まりは、道具の中のコード、hooks、公式の設定で止め、すり抜けたものは結果の確かめで見つけて戻す。それ以外は、手順も道具もモデルに任せる」。必ず守る決まり（5章）は、SPEC の要件のうち Claude の判断に任せられないもの（提出しない、原本を変えない、書式を壊さない など）に絞り、それ以上は足さない。公式の記事は、エージェントにコンピュータ（Bash とファイル）を持たせることを勧めている。承認を求めすぎると、人が確かめずに許すようになるとも書いている（15.4）。

| 部品 | 使う所 | 理由 |
|---|---|---|
| skill（6つ） | 段階ごとの手順と判断の物差し。答えが1つに決まる処理（計算、照合、様式への書き込み、Word・Excel の作成、書類の整理、公式資料の取得、今の状態の画面、版の閲覧など）は、skill に入れた Python のスクリプトで行う | 開いたときに文脈に入るのは名前と説明だけ。公式文書は、決まった処理をスクリプトにすることを勧めている（毎回コードを生成させるより確かで、出力だけが文脈に入る） |
| 公式の設定（会社のフォルダの `.claude/settings.json`） | ファイルの道具に、会社のフォルダの外を読み書きさせない。原本などと Word・Excel を Write・Edit で書き換えさせない（deny）。Web 検索と公的なサイトの取得を確認なしにする（allow）。中身は4.7 | どのモードでも効き、OS によらない。プラグインからは設定できないので、初回に社長の了承を得て作る（4.7） |
| hooks（6つの場面） | 設定では書けない決まり（画面入力の守りを含む）、結果の確かめと戻し、版の記録、開いたときの情報、審査役の結果の保存 | Claude の判断を通らず、必ず動く。文脈も使わない |
| ブラウザの道具（内蔵ブラウザ、Claude in Chrome。プラグインは作らない） | 電子申請の画面への入力 | Anthropic が保守し、ログインした状態を保てる。クリックや入力は、安全の分類器も確かめる。必ず守る決まりは hook で止める（5章） |
| subagent（2つ） | 審査役と読み取り役 | 別の目が要るものと、量の多い読み取りで本体の文脈を守るものに絞る。読み取り役は、読むものに合わせて呼ぶときにモデルを替える（7章） |
| 予定の作業（デスクトップアプリの予定の作業と、クラウドの routines。プラグインには入らない） | 開いていない間の見回り（SPEC F6） | 時刻で動く hook はない。予定の作業は、プラグインに入れて配る方法が公式文書にないので、案件ができた後に、Claude が社長の了承を得て作る（4.7） |

hooks を使う場面は、次の6つ。

| 場面 | すること |
|---|---|
| SessionStart（開いたとき） | 4.7 の「開いたときの流れ」 |
| UserPromptSubmit（社長が送ったとき） | 社長が手で変えたファイルを「社長」として履歴に残し、申請書の差分を Claude に渡す。指摘らしい言葉に一言添える（10章）。発言にある外の場所を、取り込みのために控える（4.7）。`/hojokin:nyuryoku` が呼ばれたら、「画面入力の許可」を記録する |
| PreToolUse（Claude が道具を使う前） | 設定では書けない決まりで止める（会社のフォルダの外の読み書きを含む）。ブラウザの道具のクリック・入力・添付も、ここで見分ける（5章）。auto モードでは、審査役が報告を渡す道具（SubagentHandback）から結果を保存する（8章） |
| PostToolUse（Claude が道具を使った後） | ブラウザの道具がページを読んだ結果から、部品の番号と種類・名前の対応を控える（5章） |
| Stop（Claude が応答を終えたとき） | ツールが変えたファイルを「ツール」として履歴に残す。結果を確かめる（原本と公式資料のハッシュ、Word・Excel の書式、版の名前のファイル、答えの引用）。外れていれば戻すか、直させる（5章、9.2）。質問の記録を残す。今の状態の画面を作り直す |
| SubagentStop（subagent が終わったとき） | 審査役の結果を、本体を通さずにそのまま保存する（default のモード。8章） |

- matcher は正規表現の形で書く。英字・数字・`_`・`-`・`|` だけの matcher は名前そのものの並びとして扱われ、`Claude_Browser|claude-in-chrome` は何にも合わない（実験 E1・E3）。subagent の名前には、プラグインの名前が前に付く（`^hojokin:shinsa$`）。
- 拒むときは JSON で返す。終了コード2で返すと、理由の前に起動のコマンドが付き、社長に見える文が読みにくくなる（実験 E4）。

**スクリプトの動かし方**

- 決まった処理は skill のスクリプトで行い、skill の `allowed-tools` で、その回だけ確認なしに動かす。社長には auto モードを勧める（4.7）。
  - allowed-tools には、その skill のスクリプトを動かす Bash の規則（`Bash(python3 -B "${CLAUDE_PLUGIN_ROOT}/skills/<skill>/scripts/*)` と、引用符のない形）と、その skill のフォルダを読む Read の規則（`Read(/${CLAUDE_PLUGIN_ROOT}/skills/<skill>/**)`）を書く。引用符のない形だけでは、本文の引用符つきのコマンドに当たらなかった。会社のフォルダの設定のもとで、この規則が要る理由は 4.7。形は tests/test_skill_permissions.py で確かめる。
  - 手順でほかの skill のスクリプトを使うときは、そのスクリプトを1つずつ名指しで足してよい（今は kaku が使う kiroku の record.py だけ）。
  - claude -p（2.1.317）では、`--resume` の後と、subagent から戻った後に、前に呼んだ skill の allowed-tools が効かず、その skill の道具が会社のフォルダの read block で拒まれた。skill を呼び直すと動いた（M12a）。そのため SKILL.md に、社長の答えを受けて続けるとき、読み取り役・審査役から戻った後、会話を開き直した後は、道具を動かす前にその skill を呼び直すと書く。デスクトップの auto モードで同じかは、まだ確かめていない。
- 道具に渡す JSON は、Write で `記録/一時/<道具ごとの決まった名前>.json` に置き、`--input`・`--values`・`--list`・`--apply` でその場所を渡す（書く文のように JSON でないものも、同じく `記録/一時/` に決まった名前で置く。例：`記録/一時/書く文.txt`）。標準入力（heredoc）で JSON を渡すと、会社のフォルダの read block で確かめになるため（claude -p では拒まれ、デスクトップでは毎回確かめの画面が出る見込み。M12a）。ファイルは消さず、決まった名前で上書きする。`記録/一時/` は版の履歴に入れない（4.5）。
- スクリプトと hook は、Mac に入っている `/usr/bin/python3`（3.9）で、`-B` を付けて動かす（実験 E4・E5）。使うライブラリは、Python だけで書かれたものをプラグインに同梱する（4.5）。C の拡張を持つもの（lxml など）は同梱できず、入れるには初回に通信が要るため、使わない。
  - JSON Schema の検査は、jsonschema を同梱せず、スキーマが使う決まりだけを扱う lib/schema_lite.py で行う（jsonschema の部品に、Python だけで書かれていないものがあるため）。jsonschema と同じ判定になることは開発のテストで確かめ、スキーマに知らない決まりが出てきたら、道具は止まって知らせる。
  - Word・Excel の XML は標準のライブラリで扱う。ただし ElementTree で読み直して書き出すと、名前空間の宣言が落ちる（M6 で試した。その1・2 の document.xml で、根の宣言36個が10個になり、接頭辞が ns0 などに変わり、mc:Ignorable が指す接頭辞の宣言もなくなった）。そこで、書く道具は expat で要素のバイトの場所を取り、書いてよい範囲のバイトだけを差し替え、ほかはバイトのまま残す（lib/xml_spans.py）。
- Claude が Bash で動かすコマンドには、プラグインの環境変数（`CLAUDE_PLUGIN_ROOT` など）が入らない。SKILL.md の本文では `${CLAUDE_PLUGIN_ROOT}` などが置き換わるので、そこに書いた形で、場所を引数として渡す。
- スクリプトで足りないときは、Claude がその場でコードを書いてよい（例：見慣れない形の決算書の Excel を読む）。そのコードも `記録/一時/` に置いて動かし、`python3 -c`・パイプ・sed は使わない（どれも確かめになりやすいため）。

### 4.2 skill

skill の名前には、プラグインの名前が前に付く（例：`/hojokin:sagasu`）。プラグインの正式な名前は14章の課題として残し、ここでは仮に hojokin とする。

| skill | 機能 | 説明（案） | 呼び方 |
|---|---|---|---|
| sagasu | F1, F2 | 使える補助金・助成金を探し、どれに申請するかを決めるときに使う。要件、義務、返還の条件、自己負担、二重受給を説明する | 普段の言葉 |
| junbi | F3, F4, F6, F7、F12 の手続きの切り替え | 申請する補助金を決めた後に使う。公募要領を取り込み、制度データ・概要と流れ・書類の一覧・日程を作る。制度の質問に答える。締切と今の状態、外部への依頼と待ち、事業期間中と事業後の義務、公募要領の改訂、採択後の次の手続きへの切り替えも扱う。見回りの設定と、見回りの手順も持つ | 普段の言葉 |
| shorui | F5 | 「書類を入れた」「確認して」「整理して」と言われたときに使う。原本の整理、名前の付け直し、写しの作成、不備のチェック | 普段の言葉 |
| kaku | F8, F9、F10 の入力シート、F11、F12 の差し戻しと実績の比較 | 財務モデル・計画書・入力シート・採択後の報告書を作り、審査役に確かめさせて直すときに使う。差し戻しへの対応と、説明の練習も扱う | 普段の言葉 |
| kiroku | F13 の一覧と手直し、版 | この会社について覚えていることを見る・直すとき、書類の前の版を見る・戻すとき、「提出した」と言われたときに使う | 普段の言葉 |
| nyuryoku | F10 の画面入力 | 電子申請の画面に入力し、一時保存まで進める | **担当者が呼んだときだけ**（`disable-model-invocation: true`） |

- 担当者が呼んだときだけ動かすのは、`nyuryoku` だけにする。
  - 理由：社長の GビズID でログインした国の申請画面を操作するため。
  - ほかの skill が変えるのは会社のフォルダの中だけで、版の履歴から戻せる。
  - 普段の言葉で「入力して」と言われたら、Claude は `/hojokin:nyuryoku` を選ぶよう案内する。
- 決めるとき（sagasu）は、選んだ制度の公募要領を読み、要件・義務・返還の条件を出典のページ付きで説明する。制度データは、決めた後に junbi が作る。
- skill どうしの説明が重ならないように、段階（探す・準備・書類・書く・記録・入力）で分け、社長が実際に言いそうな言葉を説明に入れる。正しく選ばれるかは実験 E10 で確かめる。
- どの段階にも共通の決まり（聞き方、推測しない、指摘を記録するかの判断、平易な説明、計算と日付は道具で行うこと、画面入力は `/hojokin:nyuryoku` を選ぶよう案内すること）は、開いたときに毎回渡す短い文（1,200字まで）に書く。プラグインは CLAUDE.md を配れないため。`nyuryoku` は `disable-model-invocation` で説明が文脈に入らないので（公式文書の skill。2026-11-03 に確かめた）、案内はこの文に書く。
- SKILL.md は500行未満にする。細かい手順は、skill の中の別ファイル（例：kaku の「説明の練習」「差し戻し」）に分ける。別ファイルはファイルの道具で読めないので（4.7）、スクリプトが中身を出して渡す。
- skill の指示の細かさは、公式の「自由度」の考え方で決める。壊れやすく、順番が決まっている処理（様式への書き込み、計算、書類の整理、画面入力）だけは手順を固定し、スクリプトに任せる。聞き取り、書く、調べる、説明するは、目的と物差しと確かめ方だけを書き、進め方はモデルに任せる。

### 4.3 subagent

| subagent | 使える Claude Code の道具 | モデル | 役目 |
|---|---|---|---|
| shinsa（審査役） | Read・Grep・Glob だけ | Opus 5.5 に固定（effort は high） | 申請書を、書いたときとは別の文脈で確かめる（8章） |
| yomitori（読み取り役） | Read・Grep・Glob と Bash（PDF や Word・Excel を文字にするスクリプトを動かす） | 読むものに合わせて、呼ぶときに替える（7章。書類の仕分けは Haiku 5.5、金額と明細は Sonnet 5.5、公募要領と様式は Opus 5.5） | 書類の種類・日付・相手先・金額を読み取る。公募要領から制度データの下書きを作る。様式の項目と書き込む位置を対応づける。結果は JSON で返し、保存は本体が道具で行う |

- プラグインの subagent では、hooks・mcpServers・permissionMode の設定が効かない。そのため、読み取りだけに絞るのは `tools` の一覧で行う。
- subagent はふだん裏で動くので、本体は、終わったという知らせを待ってから次に進む。
- プラグインの subagent はこれ以上増やさない。書く作業には社長との聞き取りの流れが要るので、本体で行う。段階ごとに subagent を分けると、流れを渡し直す手間が増えるだけになる。
- 一方で、Claude Code に組み込みの subagent（Explore など）は、広い調べもの（所在地の自治体の制度、予算の資料など）に本体の判断で使ってよい。本体の文脈を守れるため。

### 4.4 使わなかった案

| 案 | 使わなかった理由 |
|---|---|
| 機能ごとの skill（14個） | 説明が毎回文脈に入る。説明が重なると、違う skill を読んだり、使うべき skill を見落としたりする、と公式文書にある |
| 会社のフォルダに CLAUDE.md を置く | 毎回全文が文脈に入るうえ、決まりを守らせる力もない。毎回変わる情報は SessionStart で渡す |
| プラグインの settings.json の `agent` で、本体の道具を絞る | プラグインを入れた全部のフォルダで、Claude の動きが変わってしまう |
| Claude Code の自動の memory、subagent の memory | 会社のフォルダの外に置かれる。フォルダを別のパソコンに移すと失われ、会社をまたいで混ざるおそれもある。会社の記録はフォルダの中に持つ |
| スクリプトを最上位の `bin/` に置く | claude.ai と Cowork が、最上位に `bin/` のあるプラグインをインストールしない。スクリプトは skill の中に置く |
| auto モード（分類器）だけで守る | 承認は減るが、記事では、行き過ぎた動作の17%を見逃したとある。慎重な人の確認の代わりにはならないとも書かれている。社長には auto モードを勧めるが（4.7）、必ず守る決まりは、道具の中のコード、hooks、設定と結果の確かめで守る |
| prompt 型・agent 型の hook で決まりを守らせる | 結果がぶれ、費用もかかる。守らせる決まりは、設定、コードの hook と道具の中だけで判定する |
| 書く役や、段階ごとの subagent | 聞き取りの流れが切れる |
| プラグインの専用ブラウザ（MCP のサーバーで自作する） | 守りを道具の中に書けるが、ブラウザ本体の準備、画面を出して開くこと、Windows、本物のサイトで自動操作とみなされるおそれなど、確かめることが多い。同じ守りは、ブラウザの道具への hook で書ける（5章） |
| ブラウザの安全の分類器とサイトの許可だけで守る | 分類器は確率で判断する。提出・チェック欄・パスワードは必ず守る決まりなので、hook のコードで止める |
| monitors（書類の見張り） | SPEC が求めているのは、「開いたとき」と「頼まれたとき」だけ |
| 様式を python-docx・openpyxl で開いて保存する | Excel の様式では、拡張の条件付き書式・入力規則の一覧・図形などが落ち、結合したセルの書式も変わった（実験 E2）。様式は XML を直接書き換える（5章） |
| 補助プログラムを、初回に venv と pip で用意する | 通信が要る。eval の中では実行のたびに準備が走り、しかも通信できない（実験 E3・E5）。Python だけのライブラリを同梱する（4.5） |
| Output style | 毎回文脈に入る。文体は skill の物差しで足りる |
| Claude Managed Agents で見回る | API の契約（使った分だけ払う）が要り、SPEC 2.1 のサブスクリプションの前提と合わない。まだお試しの段階（beta）。クラウドの routines が、サブスクリプションの中で同じことをできる |
| `/loop`・セッションの中の予定（CronCreate）で見回る | 開いているセッションの間だけ動き、繰り返しは7日で消える。取りこぼした分も動かない |
| 携帯への通知（Remote Control） | つないでいる間は、会話の記録が Anthropic のサーバーにも残る。作者が届け方に選ばなかった（2026-11-03） |
| 今の状態を Artifact で出す | 画面が claude.ai に上がる。書類と履歴の置き場所の決まり（5章）の外になる |

- **段階のフォルダは、制度データの「手続きの段階」から作る。** 持続化なら「1_申請」「2_見積書等の提出」「3_実績報告」「4_効果報告」になる。
  - 番号は、書類を出す段階だけを順に 1 から数える。道具は、この形になっていない名前（いちばん前が「2_採択発表」など）のフォルダを作らず、手続きの段階を読み直させる（読み取り役が申請の段階を落とし、「2_採択発表」ができたことがあったため。M2c）。
  - 準備（F3）では申請の段階のフォルダだけを作り、採択後の段階のフォルダは、その段階へ切り替えるとき（F12）に作る。
- **案件のフォルダの名前の年は、案件を始めた年。** 年が変わってから資料を取り直しても（採択後の手引き、改訂の確認など）、同じ略称・枠・回のフォルダを使い、新しい案件を作らない。
- どの段階のフォルダも、中は「申請書」（作る書類）と「添付する書類」（写し）の2つにそろえる。採択後の報告書も、同じ所で同じように扱える。
- 役所から受け取った通知（採択の通知、交付決定の通知、差し戻しの文面や画面の写真）は、受け取った書類なので `原本/役所からの通知/` に置く。社長はどこに入れてもよく、ほかの書類と同じようにツールが整理する。貼り付けられた差し戻しの文面も、ここにテキストとして残す。案件とのつながりは台帳に持ち、今の状態の画面に示す。
- 不備を直すときも、ファイルは増やさない。写しは作り直し、申請書はその場で直す（前の版は履歴に残る）。
- `記録/` は、スクリプトと hook が決まった形で書く（`記録/一時/` と財務モデルの指定は、Claude が Write で書く）。会社の記録、制度データ、書類の台帳、作業の記録（審査役の結果と版のファイルを除く）は、社長が頼めば Claude が直し、社長が手で直してもよい（どれも履歴に残る）。
- `.hojokin/` の画面入力の許可と部品の控えは、版の履歴に入れない。`今の状態.html`・`今の状態.xlsx` も、見るだけで開くたびにコードが作り直すので、`見るだけ/`・`記録/一時/` と同じく会社のフォルダの `.gitignore` で版の履歴に入れない。
- `記録/制度データ/読み取り/<案件>/` に、読み取り役の章ごとの結果（裏取りの結果つき）を置く。1つの制度データにまとめたものは `記録/制度データ/<制度>_<公募回>.json`（9章）。
- 財務モデルは、kaku が前提・基準年度の実績・事業ごとの式を `記録/財務モデルの指定.json` に Write で書き、道具がそこから 財務モデル.xlsx を作る。指定は版の履歴に残るので、前提の出典をたどれる。
- `記録/書類の台帳.json` は、原本ごとに、場所・区分・種類・日付・相手先・補足・元の名前と元の場所・中身のハッシュ・版の印・大きさ・整理した日時を持つ。動かさずに確かめた書類（確かめ済み）は、場所・ハッシュ・理由・確かめた日時を持つ。書くのは、書類を整理する道具（shorui のスクリプト）だけ。原本の名前は「<日付>_<種類>[_<相手先>][_<補足>].<拡張子>」で、同じ名前の原本があれば移さずに補足を求める。
- `記録/期限の台帳.json` は、出来事（採択発表・交付決定・事業の完了・決算）の日付と、見込みか確定か、その出典（通知の原本）を持つ。出来事は1件ごとに、案件・名前（制度データの期限の決め方にある出来事の名前）・日付・状態（確定・見込み）・出典（通知の原本の場所か社長の答え）・記録した日を持ち、同じ案件・同じ名前の出来事は1件にする（M10 で作った形）。作業ごとに、種類（提出・取り直し・依頼・証拠・義務）、案件、段階、締切、始める日、状態（まだ・依頼した・待っている・届いた・済み）、だれがするか（社長・担当者・外部）、出典（制度データの項目、社長の答え、原本）を持つ。期限はコードが制度データの「期限の決め方」から計算し、この台帳に残す。

### 4.6 社長に渡す文書と、進み具合の画面

| 文書 | 中身 | 作り方 |

| 補助金の候補.docx | 3つの区分の候補、それぞれ合う理由、対象外になりそうな点、次の公募の見込み、予算の状況、出典の URL | Claude が調べた結果を、道具が Word にする |

| 今の状態.html | 下の「進み具合の画面」 | 開いたときと、Claude が応答を終えるたびに、コードが作り直す。書類の整理・不備チェック・書き込み・提出も、その応答の終わりに反映される |

**進み具合の画面（今の状態）に並べるもの**

- 期限切れ（いちばん上に分けて）、今日やること、近い締切、遅れている作業（全案件をまとめて、それぞれの中を締切順）。今日やることは、締切か始める日が今日のもの。1つの作業は、期限切れ・今日やること・遅れている作業・近い締切の順に見て、最初に当たる1つにだけ入れる。近い締切の日数は `.hojokin/` の設定から取る（はじめは30日。7日以内は強めて示す）。遅れている作業は、逆算した始める日を過ぎて済んでいないもの
- 工程表：案件ごとに手続きの段階を横の帯で並べ、今日の線と期限の印を付ける。複数の案件を1つの表に並べ、重なる時期が分かるようにする。HTML は道具が表と図形で作り、外の部品（ライブラリや外のサイト）を読まない
- 期限ごとに、見込みか確定か、だれがするか（社長・担当者・外部）、依頼の状態（まだ・依頼した・待っている・届いた）
- 事業期間中は、経費ごとの証拠（見積・発注・納品・請求・支払・写真など）の揃い具合。事業の後は、効果報告の数字の用意、事業場内最低賃金の確かめ、処分の制限と書類を残す期間
- 案件ごとの手続きの流れ（申請 → 交付申請 → 実績報告 → 効果報告1〜5年目）と、今いる段階、次の締切まであと何日
- 書類：必須・任意ごとの揃い具合と、書類ごとの状態（揃った・足りない・不備あり・期限が近い）。原本か写しか、場所、有効期限、元の原本が新しくなっていないか、提出版に入っているか、最後に変えた日
- 不備：重さごとの件数と一覧（直し方、直したか）
- 申請書：様式の項目ごとの進み具合（まだ・下書き・仮の印あり・確かめ中・完成）、文字数と上限、審査役の指摘の数
- 長い期限：効果報告などの5年先までの期限を、年ごとに
- 最近の変更（いつ・何を・だれが）と、会社について覚えていることの件数

開いたときは、この中から「期限切れ」「今日やること」「近い締切」「遅れている作業」を締切順に、最初の返事で示す（4.7）。

- 画面と Excel は見るだけにする（作り直すたびに上書きされるため）。済んだことは、社長が会話で伝えるか（「様式4を頼んだ」「見積書が届いた」）、届いた書類を会社のフォルダに入れると、道具が期限の台帳に残す。
- 期限切れには、制度データと公式資料にある手（遅れの届け出など）を出典つきで示す。資料になければ、事務局への問い合わせ文の案を作る。

### 4.7 初めて使うときと、開いたときの流れ

**初めて使うとき**

- 社長は、デスクトップアプリの設定 → プラグイン →「＋ 追加」→「リポジトリから追加」に、このプラグインの公開の GitHub のリポジトリを入れて足す。画面からは手元のフォルダを足せない（実験 E4）。リポジトリの根の `marketplace.json` が、根のプラグインを指す。
- 目印（`.hojokin/`）のないフォルダでは、hooks は何もしない。スクリプトも、補助金を探すこと（F1）と、会社のフォルダを作ること以外は動かない。
- どの skill も最初に目印を確かめ、なければ「このフォルダを〇〇社の会社のフォルダにしますか」と社長に聞く。
- 次のフォルダは会社のフォルダにしない。道具は何も書かずに断り、新しいフォルダを作ってそこで始め、元の書類は場所を伝えて取り込むよう案内する。
  - ホームのフォルダと、それを含むフォルダ（/Users など）、ディスクの根（「/」と、外付けのディスクなどのつなぎ目）（中のものがすべて版の履歴と照らしの対象になってしまうため。目印があっても断る）
  - 前から `.git`・`.gitignore`・`.claude/settings.json` があるフォルダ（以前そこで Git や Claude Code を使っていたとき）。hook を止める設定や、原本を履歴に入れない行で、守りが弱まることがあるため。「次から聞かない」で Claude Code が作る `.claude/settings.local.json` は、守りを弱める項目があるときだけ断る
- 書類と版の履歴の置き場所を、経営者に3段から選んでもらう（SPEC 共通の要件）。①パソコンの中だけ（既定。Git で残し、送り先を持たない）、②期限の一覧だけをクラウドに置く、③会社のフォルダごとクラウドに置く。②③の置き先は、GitHub の非公開のリポジトリ、Google ドライブ、OneDrive、Dropbox。
  - ②③では、何がどこに上がるか、だれが読めるか、クラウドの予定の作業が置き先を読むことを知らせ、同意を得てから、選んだ段・置き先・同意の日を `.hojokin/` の設定に残す。
  - クラウドの予定の作業が置き先を読む道は、GitHub は動くたびの取り寄せ、Google ドライブ・OneDrive・Dropbox は claude.ai のコネクタ。OneDrive を読む Microsoft 365 のコネクタは、法人の Microsoft 365 の契約が要る（個人の Outlook・Hotmail では使えない）。Dropbox のコネクタは、チームの契約では管理者が有効にする。
  - ③で同期されるフォルダ（Google ドライブ、OneDrive、Dropbox。iCloud Drive も同期されるフォルダとして見分ける）に置くときは、2台のパソコンで同時に使うと壊れやすいこと、中身がパソコンにない設定では遅くなることも知らせ、版はファイルで残す（10章）。Google ドライブなどは場所で見分ける（~/Library/CloudStorage/<サービス>-…、~/Library/Mobile Documents/、ホームの直下の前からの形、根の .dropbox）。iCloud の「デスクトップと書類」は、Finder の設定（com.apple.finder の FXICloudDriveDesktop・FXICloudDriveDocuments）を /usr/bin/defaults で読み、1 のときだけ同期されるとみなす（切った Mac で 0 と読めることは確かめた。開発の Mac は切ってあり、入れた Mac で 1 になるかは確かめていない。期間中は確かめない）。~/Library/Mobile Documents/com~apple~CloudDocs/ の中の Desktop・Documents のフォルダは、切った後も残るので見分けに使わない。~/Desktop が iCloud Drive の中への別名なら、別名をたどった場所で見分ける。
  - 同期されるフォルダでは、Git の形では何も書かずに断り、版の持ち方（①パソコンの中だけ／③同期の形）を経営者に選んでもらう。③の道具の中身はできていて（M0c）、選ばれたら道具が .git を作らずに `記録/版/` を用意する（lib/company_init.init の form=FILES）。ただし、会社のフォルダを作る道具からこの形を選ぶ入口は期間中に作らない（K4 を飛ばすため）。期間中は③を「今は選べない」と示して①を勧め、README にも、同期されないフォルダに作るよう書く。
  - Git の形の会社のフォルダ（目印と .git がある）が、後から同期されるフォルダに移されていたときは、何も書き足さずに断り、同期されない場所へフォルダごと移すよう経営者に案内する（同期されるフォルダの形を選ぶ入口は、期間中はない）。同期されるかどうかは、大文字と小文字をそろえた場所で見分ける。Dropbox の目印（根の .dropbox）は、ホームより下だけで探す（~/.dropbox/ はアプリの設定のフォルダのため）。
  - 置き場所は後から変えられる。クラウドをやめたとき、置き先に上がったものを消すのは社長が置き先で行う（ツールは消さない）。
  - ②の期限の一覧の置き方と、③の GitHub の送り先の作り方（非公開であることの確かめ方、送るときの認証）は14章の課題。期間中は置き場所の②③（K4）を飛ばすので、選べるのは①だけにし、README に書く。
- 社長が了承したら、道具が一度に用意する：目印、フォルダの形（4.5）、版の履歴、`.claude/settings.json`。この後は、5章の決まりが効く。補助プログラムの準備（通信）は要らない（使うライブラリは同梱する。4.1）。
- 会社のフォルダの `.claude/settings.json` に書くもの（このリポジトリの開発用の設定とは別。12章）：

| 区分 | 中身 |
|---|---|
| 会社のフォルダの外 | `permissions.blockReadsOutsideWorkingDirectories: true`：ファイルの道具は、会社のフォルダの外（別の会社のフォルダ、認証情報など）を読まない。`permissions.blockWritesOutsideWorkingDirectories: true`：Write・Edit・NotebookEdit は外に書かない |
| 規則の deny | 組み込みの Edit（Write も含めて止まる）で、原本、公式資料、審査役の結果、`.hojokin/`、`.claude/`、`.git/`、版のファイル（`記録/版/`）、Word・Excel のファイルを書き換えない |
| 規則の allow | Web 検索、公的なサイト（`*.go.jp`、`*.lg.jp`）と持続化の公式サイト（`*.jizokukahojokin.info`。A15。効くのは default のモードだけの見込み）の取得。そのほかのサイトの取得は確かめる |

- 設定の名前にある「作業フォルダ」は、Claude Code を開いたフォルダのこと。社長は会社のフォルダで Claude を開くので、会社のフォルダの外が止まる。
- block の2つは、どの設定ファイルにも書け、どのモードでも効く（読む側は 2.1.257 以降、書く側は 2.1.314 以降）。deny はフォルダを信頼する前から効き、allow は信頼した後に効く（公式文書）。11/3 のデスクトップアプリの中の版（2.1.309）では書く側が効かなかったので、PreToolUse で補う（実験 E6、5章）。
- 読む側の block は、Bash のコマンドが名指す場所にも効く（2.1.317）。プラグインを入れた場所（~/.claude/plugins/ の下）は、block で「外」として断られない。ただし、Read の許可の規則がその場所を含まないと確かめになるので、各 skill の allowed-tools に、その skill のフォルダを読む Read の規則を書く（4.1）。会社のフォルダの設定には、プラグインの場所を書かない。
  - `--plugin-dir` で読み込んだ開発中のフォルダは、許可の規則があっても断られる。開発で会社のフォルダの設定ごと試すときは、`--settings` の `permissions.blockReadsExemptPaths` にそのフォルダを入れる（この項目は `--settings` からしか読まれない。11章）。
  - プロジェクトの allow は、フォルダを信頼するまで読まれない（claude -p では「Ignoring … not been trusted」と出る）。
  - 標準入力で渡す JSON（heredoc）も、この block のもとでは確かめになる。そのため、道具に渡す JSON・文はファイルで渡す（4.1）。
- 社長が外のファイルを取り込みたいときは、場所を伝えてもらい、取り込みのスクリプトが会社のフォルダに写す。スクリプトは、社長の直前の発言にあった場所だけを受け付ける（UserPromptSubmit hook が控えた場所と照らす）。Claude は、写したものをファイルの道具で読む。ファイルの道具は伝えた場所も含めて外を読まないので、SPEC F5 の「社長が伝えた場所を除く」は、写すことで満たす（T5-9）。写すと原本になり、出典と版が会社のフォルダの中に残る。
- ユーザーの設定にある追加の作業フォルダは、会社のフォルダで開いても作業フォルダに数えられた（実験 E6 で、拒否の文の作業フォルダの一覧に並んだ。読ませて確かめてはいない）。block の設定は作業フォルダの外にしか効かないので、そこは止まらないと見ている。会社のフォルダの設定からは外せないので、PreToolUse でも、ファイルの道具が会社のフォルダの外を読むことを拒む（5章）。
- ファイルの道具は、プラグインの中のファイル（knowledge/ など）も外として読まない（実験 E6）。skill と subagent が同梱の知見や定義を使うときは、スクリプトが中身を出力して渡す。
- 申請サイトは、初めて操作するときに、Claude in Chrome か内蔵ブラウザがサイトごとに許可を求めるので、担当者が許す。画面入力には Claude in Chrome を勧め、拡張機能を入れてつなぐよう案内する（ターミナルでは `/chrome` で有効にする。プロジェクトの設定からは有効にできない）。内蔵ブラウザで進めるときは、添付は担当者が行う（5章）。
- auto はプロジェクトの設定では既定にできないので、社長には、デスクトップアプリのモードの選択で auto を選ぶよう案内する。auto では、会社のフォルダの中の読み取りと編集が確認なしになり、そのほかは分類器が判断する。
- 初めて使うセッションでは SessionStart がもう動いた後なので、開いたときに渡す共通の決まり（4.2 の短い文）は、会社のフォルダを作った道具が結果として返す。
- `.claude/settings.json` は、作ったその場で効く（実験 E6。開き直さなくてよい）。
- デモは、この用意を済ませた会社のフォルダから始める。

**見回りを作るとき**（SPEC F6。11/7 に、時間があれば作る）

- 最初の案件ができた後に、Claude が見回りを勧め、社長の了承を得て作る。頻度（はじめは平日の朝に1回）、届け方（デスクトップの通知、自分宛てのメール）、宛先、メールを送るか下書きに置くかを、選択肢の画面で1問ずつ聞く。
- ①の会社は、デスクトップアプリの予定の作業で作る（Claude がセッションの中で作れる。定義はホームの `~/.claude/scheduled-tasks/` に置かれる）。アプリが開いていてパソコンが起きている間に動き、眠っていて逃した分は、起きたときに最後の1回だけ動く。「パソコンを眠らせない」の設定を案内する（ふたを閉じると眠る）。
- ②③の会社は、クラウドの予定の作業（routines）でも作れる（`/schedule` か claude.ai の画面。間隔は最短1時間。research preview）。両方を使ってもよい。
- 見回りの指示には、読む・今の状態を作り直す・知らせる、のほかはしないことを書く（5章）。指示は毎回まっさらな会話で読まれるので、それだけで足りる形にする。
- 作れないときや、社長が自分で作りたいときは、手順を案内する。

**開いたときの流れ**（SessionStart hook。すべてコードで行い、モデルは使わない）

1. 原本と公式資料が書き換わっていたら、版の記録より先に、履歴から戻して知らせる（5章）。そのうえで、社長が閉じている間に手で変えたファイルを、「社長」として履歴に残す。申請書の手直しがあれば、前の版との差分を作る（10章）。版の記録が止まっているとき、大きすぎて残せないファイルがあるとき、時間内に残しきれずに次に回したファイルがあるときは、そのことを渡す情報に入れる。
2. 中身のハッシュで、増えた書類・変わった書類を見つける（移しただけ・名前を変えただけは除く）。版の履歴の送り先が、選んだ置き場所のとおりか（①②と同期されるフォルダの形では0件、③の GitHub では選んだリポジトリ1つだけ）も確かめる。`見るだけ/` を片付ける（ツールが出して中身が変わっていないものだけを消す。compact のときは片付けない）。
3. 今日の日付（差し替えを含む）から、期限の台帳の期限を計算し直し、期限切れ・今日やること・近い締切・遅れている作業を締切順に組み立てる。近い締切の日数は設定から取る。出来事の日付が分からない期限は「見込み」とする。期限の台帳ができるまで（K1）は、制度データの手続きの段階と決まった期日から組み立てる。申請の段階は、決まった期日のうち名前に案件の回と締切を含むものを先に使い、名前に別の回のある期日は使わない（制度データを直近回の資料で作ったとき、段階の期限が前の回の締切になるため）。日が決まっていない期日（「12月下旬」）は見込みとし、旬のはじめの日で近い締切に入れ、終わりの日を過ぎてから期限切れにする。
4. 進行中の案件と次に申請する制度の公式サイトを、短い時間（数秒）で区切って確かめる。間に合わなければ「確かめられなかった」とする。
5. 会社の記録の要約、申請書の手直しの差分、どの段階にも共通の決まりを添え、10,000字以内に切って Claude に渡す。今の状態の画面も作り直す。

- Python が動かない Mac（開発ツールがない など）では、上の流れは動かない。そのときは起動用のスクリプトが、Python なしで決まった文（開発ツールを入れる案内）を渡す。README にも同じ案内を書く（実験 E5）。
- 書類の整理と不備チェック、改訂の中身の読み取りは、Claude が社長の最初の発言のときに行う。hook は情報を渡せるだけで、Claude は社長の最初の発言まで動かないため。社長が別のことを頼んだら、そちらを先にする。整理と確かめの対象は、開いたときにハッシュで見つけた増えた・変わった書類だけにする。前に確かめて書類の台帳に「確かめ済み」と残した書類は、原本の外に元の名前のまま残っていても（社長が動かさないよう答えたものなど）、ハッシュが変わらない限り整理し直さない。
- 整理で通知の原本（採択の通知、交付決定の通知など）が見つかったら、Claude が日付を読み取り、社長に確かめてから、道具が期限の台帳の出来事を「確定」にして期限を計算し直す。依頼していた書類が届いたら、依頼の状態を「届いた」にする。

## 5. 必ず守る決まりと、強制しないこと

すべての hook は、最初に会社のフォルダの目印（`.hojokin/`）があるかを確かめ、なければ何もしない。プラグインの hook は、プラグインを入れた全部のフォルダで動くためである。

守りが想定する相手は、協力的な Claude と、Git を知らない社長のうっかりである。悪意のある人による書き換えや偽装（控えのファイルの書き換え、大文字・小文字だけ違う場所を使った偽装など）は想定しない。守りの種類は SPEC が求める分にとどめ、作りは単純にする（守りが1つ増えるごとに、誤って拒む道も1つ増えるため。作者の決定、2026-11-04）。

| 決まり | 止める所 | すり抜けへの備え |

| 提出ボタンを押さない | 画面入力の守り（PostToolUse と PreToolUse の hook）。名前に `Claude_Browser`・`claude-in-chrome`・`computer-use` を含む道具が対象。PostToolUse が、ページを読んだ結果（read_page など）から、部品の番号と種類・名前・囲むラベルの対応を控える。PreToolUse は、通してよいものだけを通し、それ以外（知らない道具の名前を含む）は拒む。クリックは、番号で指し、控えた対応で「押してよいボタン」（次へ・一時保存・戻るなど。制度データの画面の定義から作る）に当たると分かるものと、下の2行で通す欄だけ。表示名に「提出」「送信」「申請する」「確定」「完了」などを含むボタンは、制度データにかかわらず押させない（この禁止の語はコードに固定する）。座標でのクリック、ダブルクリック・右クリック・ドラッグ、打ち込み、Enter などのキー、JavaScript とショートカットの実行は拒む | 制度データは AI が下書きするので、禁止の語を優先する。通してよいものだけを並べるので、道具の出力の書き方が変わっても、押す側には倒れない。部品の番号は画面ごとに振り直されるので（実験 E1）、クリックやページの移動の後は控えを捨て、次の操作の前にページを読み直させる。まとめて動かす道具（browser_batch）は中の1つずつを見て、クリックは1回までで最後の動作に限る（前の画面の控えで、次の画面の部品を押させないため）。会社のフォルダでは、画面を操作する機能（computer use）は拒む |
| 確認・誓約・同意のチェック欄に入れない | 画面入力の守り。チェック欄・ラジオボタン・選択欄と、そのラベルへのクリックと入力は、ページの構造から欄の名前（囲むラベルの名前か、ラベルの中の文字。欄そのものの名前は、チェック欄なら「on」、ラジオボタンなら値、選択欄なら選んでいる項目になるため使わない。実験 E1）が読み取れ、入力シートでツールが入れる欄（加点の選択など）とされ、名前に「確認」「誓約」「同意」「宣誓」を含まないものだけ通す。名前が読み取れない欄には入れない | 項目名の文字に頼る分、確実さは少し下がる（作者の了承済み）。試した画面では、チェック欄そのものの名前は「on」としか出なかったが、囲むラベルの名前（「賃上げ加点」など）はページの構造から読めた。選択欄は、ラベルの名前が空になる形があり、そのときは担当者が入れる（実験 E1）。本物の画面には、4つの語を含まない宣誓の行や、「確認」を含む加点の行もある（D11a）。前者は入力シートでツールが入れる欄に当たらないので拒み、後者は担当者が入れる。担当者が入れる欄がある画面（最初の誓約や宣誓の画面など）では、Claude は入れるべき欄を示して止まる。入力シートのチェック欄の値は「はい」（入れる）・「いいえ」（外す）で書き、空の欄には触れない。チェック欄とラジオボタンは、入れた後の状態をページの構造から読み取れない（実験 E1）。そのため、入れた後は nyuryoku の道具が、文字の欄と選択欄を画面の値で照らし、チェック欄とラジオボタンは、ツールが入れた欄と担当者が入れる欄の一覧にして出す。Claude はそれを示し、担当者に画面で確かめてもらってから続ける |

| パスワードを扱わない | 画面入力の守り。種類がパスワードの欄への入力は拒む | ログインは、担当者がブラウザで自分で行う。Claude in Chrome は、ログイン画面で止まって本人に任せる |
| 画面入力は、担当者が呼んだときだけ | `nyuryoku` に `disable-model-invocation: true` を付け、Claude が自分で始められないようにする。加えて、会社のフォルダでは、ブラウザの道具のクリック・入力・添付は、担当者が `/hojokin:nyuryoku` を呼んだときに UserPromptSubmit hook が記録する「画面入力の許可」がないと、PreToolUse で拒む。ページを読むだけの道具は拒まない。許可はそのセッションの間だけ有効 | `disable-model-invocation` は skill が自動で選ばれることを止めるだけで、道具そのものは止めないため、許可の記録で道具を止める |
| Word・Excel の様式と申請書類の書式を壊さない | 決まった書き込みは skill のスクリプトで行う。スクリプトは「書いてよい範囲」（1.1）だけに書き、書いた後に直前の版（社長が手で直した後なら、その版）と比べる。範囲の外が1か所でも変わっていたら保存しない。様式は、ファイルの中の XML を直接書き換え、ほかの部品はバイトのまま残す（Excel の様式を openpyxl で開いて保存すると、拡張の条件付き書式・入力規則の一覧・図形などが落ちた。実験 E2）。Word も同じ形にそろえる。比べるのは、書式・余白・表の行と列・結合したセル・数式・入力規則・シートの構成・ヘッダーとフッターで、ファイルの中の部品の XML どうしで比べる（ライブラリで読み直したものでは、読むときに落ちる部品が前後どちらにも見えないため）。様式が消すよう求める説明の文（Word その1・2 の説明の青字）は、書いてよい範囲に含めて消す。組み込みの Write・Edit で .docx・.xlsx などに書くことは、規則の deny で止める | Claude がその場で書いたコードで書き換えた場合は、Stop hook が、変わった Word・Excel を同じ物差しで比べ、範囲の外が変わっていたら直前の版に戻して Claude に伝える。PDF にするときは写しを作り、元は変えない |
| 原本・公式資料を1バイトも変えない。審査役の結果、`.hojokin/`・`.claude/`・`.git/`・`記録/版/` を Claude が書き換えない | 組み込みの Write・Edit は、規則の deny と PreToolUse で止める。原本の置き場への移動と名前の付け直しは、書類を整理するスクリプトだけが行う。原本と公式資料は読み取り専用にする | どの経路で変わっても結果で守る。原本と公式資料は、開いたときと、Claude が応答を終えるたびに、版の記録より先に、道具が置いたときの控え（`.hojokin/一時/原本の印.json`）のハッシュと照らす。変わっていたら版の履歴から戻し、社長に知らせる（書き換わった中身は版に残さない）。戻す元は、控えの版の印か、その場所の版のうち同じハッシュのもの（いちばん新しい版とは限らない）。台帳と資料の一覧は Claude も社長も直せるので、その値だけでは書き戻さない。控えにない項目は、今の中身と版の履歴の入れたときの版で確かめられたときだけ照らし、そうでなければ知らせる。照らして戻すのは `原本/<区分>/` と `案件/<案件>/公式資料/` の下だけで、台帳や資料の一覧がその外を指していても、書かずに知らせる。整理の道具と公式資料を取る道具は、置く前に中身を版の履歴の置き場に入れるので、同じ応答の中の書き換えも戻せる。版の履歴に入れたときの中身がなければ、消さずに知らせる。審査役の結果は、完成の判定のときに保存したハッシュと照らし、合わなければ使わない（8章） |
| 版のファイルを増やさない | Write・Edit は PreToolUse で、名前に「_v2」「最終」「修正版」「コピー」などを含む新しいファイルと、その名前の新しいフォルダの中への書き込みを拒む（会社のフォルダからの場所の、まだない部分を見る）。「その1最終」「計画書第2版」「計画書v2」のように区切りなしで付けた形も含み、言葉の一部として出てくる「最終確認」「富士コピー」は通す（言葉の一覧は lib/version_names.py）。スクリプトは決まった名前でしか書かない | その場のコードで作られた場合は、Stop hook が、その応答で足されたファイルと、前の版になかったフォルダの名前で見つけ、元のファイルにまとめるよう Claude に伝える（フォルダは1件にまとめ、元のフォルダを示す）。Stop の hook で続けているときも、新しく足された分は伝える（1つの応答で3回まで。超えた分は次の応答の終わりに伝える）。前の版は版の履歴に残る |
| 会社のフォルダの外に書かない・外を読まない | ファイルの道具は、公式の設定（`blockWritesOutsideWorkingDirectories`、`blockReadsOutsideWorkingDirectories`）で止める。デスクトップアプリの版では `blockWrites` が効かなかったので（実験 E6）、PreToolUse でも、外への Write・Edit・NotebookEdit を拒む。ユーザーの設定の追加の作業フォルダは設定では止まらないと見られるので（4.7）、PreToolUse で、外を読む Read・Grep・Glob なども拒む。設定と同じく、Claude Code 自身が要るファイル（計画のファイル `~/.claude/plans` と、このセッションの置き場。大きな道具の結果が置かれる）は通し、`~/.claude` のほかの所は通さない。外かどうかを決めるときは、次のようにする。(a) 相対の場所、Glob の型の起点、path を省いた Grep・Glob が探す場所は、hook の入力の cwd（Claude がいま居るフォルダ）から解く。cwd がなければ会社のフォルダから解く。読む場所が取れないときは、cwd そのものを照らす。(b) 別名と「..」をたどった後に、名前の文字の形を NFC にそろえてから比べる（実験 E5。Finder で作った名前は NFD のことがある）。スクリプトは、取り込みで社長が伝えた場所を読むほかは、会社のフォルダの中しか扱わない。取り込みでは、元のファイルを動かさない（4.7） | その場で書いたコードが外に触れる場合は、Claude Code の権限の仕組みに任せる |
| 書類と履歴を、経営者が選んだ範囲のほかに送らない | ①②と同期されるフォルダの形では、会社のフォルダの Git に送り先を持たせない。③で GitHub を選んだときだけ、`.hojokin/` に記録したリポジトリ1つを送り先に持ち、送るのはその1つに限る（送る道具は、記録と照らしてから送る）。②の期限の一覧は道具が決まった形で作り、書類の中身・金額・決算の数字・会社の記録・版の履歴を入れない。②③は、作るときに知らせて同意を得る（4.7） | 開いたときに、送り先の設定が選んだ置き場所のとおりかを確かめる。違えば知らせ、送る道具を止める |
| 見回りでは、会社の書類を変えない | 見回りの指示に、読む・今の状態を作り直す・知らせる、のほかはしないことを書く。デスクトップの予定の作業では、見回りのセッションを見分けて、PreToolUse で、今の状態のほかへの書き込み、ブラウザの道具、送る道具を拒む（見分け方は実験 E13 で確かめる）。知らせの文はスクリプトが作り、案件名・期限の名前・日付・あと何日・することだけを入れる。メールの道具の宛先は、設定のアドレスと照らす | クラウドの予定の作業でプラグインの hook が効くかは確かめていない。そこでは指示と、置き先の権限（GitHub のブランチの保護など）に頼る。見回りの後に開いたとき、版の履歴で、見回りの間に変わったファイルがないかを確かめる |
| 版を自動で残す | 社長が手で変えた分は、UserPromptSubmit と SessionStart で「社長」として残し、理由は「社長が手で変更」とする。なぜ直したかは、Claude が差分から判断して会社の記録に残す（10章）。ツールが変えた分は、Stop で「ツール」として残し、理由には、その応答のもとになった社長の依頼の文を使う（1行にそろえて100字で切る）。応答が Stop まで届かないまま次の発言が来たときは、それまでの分を前の依頼の「ツール」の分として残す。応答の途中の自動の compact で動く SessionStart では残さない。版の日時は、差し替えた今日の日付に従う | 1つのファイルやフォルダを読めないとき（権限がないなど）と、比べた後に消えたときは、そのファイルだけを飛ばし、ほかは残す。読めないものは消したことにせず、開いたときに知らせ、読めるようになったら、最初に見つけた場面のだれ・理由で残す。Stop の hook で続けさせている間は応答が終わっていないものとし、社長が続きを止めて次を送っても、続きの中の変更は「ツール」で残す。ほかのセッションの hook が版を残している間（版の錠が取れない）や、版を残す処理が落ちたときは、その場面で最後の版から変わっていたファイルとその状態（大きさ・時刻など）を、その場面のだれ・理由とともに `.hojokin/一時/版の記録/錠待ち/` に控える。次に版を残せた場面は、控えたときと状態が同じファイルを、そのだれ・理由で残し、控えた後にまた変わったものは、その場面のだれ・理由で残す。応答の終わりで錠が取れなくても、その応答で足された版の名前のファイルは、控えから見つけて Claude に伝える |
| 開いたときに渡す情報を10,000字以内にする | SessionStart で情報を組み立てるコードが、上限で切る。超えると先頭の2,000字しか渡らない（すべての hook に共通の決まり） | — |
| 補助プログラムが動かないときは止める | hook は、起動用の小さなスクリプト（run.sh）から動かす。目印があるのに Python が動かないとき、または Python が hook の時間切れより前に終わらないとき（PreToolUse なら10秒の時間切れに対して8秒ほどで、起動用のスクリプトが止める）は、Write・Edit・NotebookEdit、Bash、ブラウザの道具（ページを読むだけのものも）を拒む。拒むときは、開発ツールを入れるなどの準備の案内を返す | 決まりが、気づかないうちに外れることを防ぐ。hook が時間切れになると、Claude Code は道具をそのまま通す（実験 E5）。Python が動かないと応答の終わりの確かめも働かず、Bash で変えたものを戻せないので、Bash も止める。見張りが止めるのは Python そのものだけである。開いたときや応答の終わりの処理が別のプログラム（LibreOffice など）を呼ぶときは、その呼び出しにも、見張りより短い時間の区切りを付ける。Python の中の長い処理（版を残すことなど）にも、見張りより短い上限を置き（版は開いたとき・送ったとき15秒、応答の終わり35秒）、残りは次の場面に回す。版を残す処理が落ちたときは、hook を落とさずに控え、開いたときに伝える（Python が動かないときの案内とは分ける）。見張りに止められて .git に残った錠は、次の場面で片付ける（版の錠に処理の番号を書き、持ち主が動いていなければ外す）。Mac では sh と `/usr/bin/python3` で動かす。Windows でも動く形にするが、期間中は確かめない（SPEC 4章） |

**強制しないこと**（Claude に任せる）

- 文体の「注意」「弱い注意」の項目、構成、質問の言い回し、勧める任意書類、記録に残すかどうか、審査の観点の重み。
- 1回の質問を3つまでにすることは強制せず、テストで確かめる。
- 文体の「要修正」（100字を超える文、記号の残り、です・ます調とである調の混在）は、完成かどうかの判定にだけ使い、作業は止めない。

## 6. コードで処理することと、Claude に任せること

- 入力シートの、会社に当てはまらない欄（選ばない加点・特例の欄、支援者がいないときの支援者の欄、出さない書類の添付の欄など）には、値として「該当なし」と書く（チェック欄は「いいえ」）。確かめの道具は、この欄を空欄に数えず、画面入力の道具は、この欄を画面に入れない。当てはまるか分からない欄は「該当なし」にせず、社長に聞く（省力化の申請画面は、ツールが入れる欄が207あり、条件付きの欄が多い。M12b）。

  - 画面のない実行（eval・`claude -p`）では、AskUserQuestion は使えない（実験 E3）。会話を続けるテストの仕組みには、選択肢に答える役を作る（11章）。
  - 選択肢の画面が使えないときは、普段の文章で「【質問】」と書いた後に、番号と「（理由：…）」を付けて並べる。Stop hook がそれを読み取って、同じく質問の記録に残す。
  - 説明の練習（F11）の問いは聞き取りではないので、選択肢の画面を使わず、【質問】の形にもしない（選択肢は答えを教えることになるため）。問いは番号を付けて普段の文で3つまで並べ、質問の記録には入れない。
- PDF への変換と、様式の数式の計算し直しは LibreOffice で行う（実験 E2・E5）。
  - PATH に頼らず、決まった場所（`/Applications/LibreOffice.app` など）と Spotlight で探す。利用者の設定は一時の場所に作る（社長が開いている LibreOffice とぶつからないため）。
  - 計算し直しは「常に」にする。既定では計算し直さず、古い値や一部だけ計算し直した誤った値が残った。
  - フォントの置き換え表を固定する。様式のフォント（BIZ UD ゴシックなど）がない Mac では、変換のたびに置き換えが変わり、ページ数が揺れた。様式のフォントがなければ社長に知らせ、無料で入れられることを案内する（入れるのは社長）。
  - LibreOffice がなく Word があれば Word を使う（Word を外から動かすことは確かめていない）。どちらもなければ、PDF にする操作を社長に案内する。

## 8. 審査役と、「書く → 確かめる → 直す」の繰り返し

**審査役に渡すもの**（確かめの道具が、1つのフォルダにまとめて作る）

- 計画書の本文（様式の項目ごと）
- 制度データから抜き出したもの（審査項目、加点、様式の項目と分量）
- 根拠対照表と聞き取りの記録
- 会社の記録のうち、書き方の決まりと、過去に受けた指摘（審査のコメントや、不採択の後の相談で受けた指摘）
- 文体の基準の C
- コードによる確かめの結果

書いたときの考えの経過は渡さない。

**審査役が返すもの**（JSON）

- 聞き取りと食い違う記述（T9-2）
- 文体の C の12の観点ごとに、可か不可かと、その理由。あわせて、数字・単位・固有名詞・期日が1つもない段落（文体の基準 A の「具体性」）（T9-3b）
- 「現状と目標 → 課題 → 解決策 → 効果」の4つの段がそろっているかと、つながりが切れている所（T8-8）
- AI が読んでも、主張・根拠・数字を拾える書き方か（作者の見立て「審査で AI も使われる」。A1）。審査役に作者の知見（knowledge/）は渡さない。知見は書く段階で使う
- 目安のない項目の長さ（T8-9）。持続化の4,000字のように上限しかない項目も含め、長すぎないか、足りないか
- 審査項目と加点項目ごとの点数と理由、弱い所（T9-5）
- 過去に受けた指摘に応えているか（T13-9）、会社の書き方の方針と構成の決まりに沿っているか（T13-6）
- 指摘ごとの重さ（要修正・要確認・助言。1.1）

点数は参考として見せるだけで、合否には使わない。

**結果の保存**：本体が指摘を落としたり書き換えたりできないよう、hook が、本体を通さずに結果を保存する。
- 取り出す所はモードで違うので、両方に hook を付ける（実験 E3）。default のモードと eval（`dontAsk`）では、SubagentStop の最後の報告から取り出す。auto モードでは、審査役は報告を SubagentHandback という道具で渡し、SubagentStop には報告が来ないので、その道具の PreToolUse（matcher は `^SubagentHandback$`）から取り出す。審査役かどうかは、入力の agent_type（`hojokin:shinsa` が入る。M7 で確かめた）で照らす。
- 確かめの道具は、審査役に渡すフォルダ（`記録/審査に渡すもの/`）に「確かめの番号」と計画書のハッシュを書いた控えを置く。hook は、審査役のとき（SubagentStop では matcher の `^hojokin:shinsa$`、auto モードでは上の agent_type で見分ける）だけ、その控えと結果を結び付けて `記録/審査役の結果/` に保存する。
- 報告は、前後に json の囲み（3つのバッククォート）が付いたまま届くので、外してから JSON として読む。
- auto モードでは審査役が裏で動き、本体は報告を待たずに一度応答を終えることがある。kaku は、保存された結果がそろってから次に進む。

**確かめの流れ**

1. コードで確かめる（費用はかからない）。
2. 通らなければ直して、1に戻る。このときは審査役を呼ばない。
3. 通ったら審査役を呼ぶ。
4. 要修正の指摘を直して、1に戻る。要修正がなければ完成とする。要確認と助言の指摘は、社長に示す。

**完成とする条件**（SPEC F9。すべて満たすこと）

- コードの確かめで、次がすべて0件。
  - 根拠のない記述、食い違い、本文への出典の書き込み
  - 文体 A の要修正と、B と会社の「避けたい言い方」に当たる言い回し。社長が残すと決めたものは除く。A と B が重なる項目は A に従い、「注意」「弱い注意」の項目は判定に使わない
  - 仮の印、空欄、文字数の超過
  - 計画書で使った制度データの値と書類の読み取りに残った「要確認」
  - 計画書・様式・入力シートと財務モデルとの数字の食い違い、財務モデルに残った仮の前提
- コードの確かめで、数値の要件を満たし、見積書が要る経費に見積書がある（8.4）。
- 審査役：今の版の計画書を確かめた結果で、要修正0。
- 完成の記録は、確かめの道具だけが残す。道具は、保存された審査役の結果が今の版のハッシュと合うかをコードで確かめてから残す。

**途中でやめて社長に返す条件**（SPEC F9）

- 社長に返すまでの間に審査役を3回（仮）呼んでも、要修正が残る。社長の答えをもらって直した後は、数え直す。
- 同じ指摘が2回続く（直しても良くならない）。
- 社長の答えや判断が要る（仮の印、空欄、足りない事実、B の言い回しを残すか）。このときは、3回を待たずにすぐ聞く。
- 文章を直しても通らないコードの確かめがある（例：数値の要件を満たさない。前提や計画そのものを変える必要がある）。このときも、すぐに社長に返す。
- コードの確かめで見つかった問題を直して確かめ直す繰り返しが、5回（仮）を超えた。

返すときは、直したこと、残った指摘と直し方の案、質問（3つまで）を示す。

### 8.1 誤りを見つける仕組み

| 誤りが起きる所 | 確かめ方 |

| 制度データ（読み違い） | JSON Schema で形を確かめ、出典の裏取り、重要な項目の2回の読み取り、資料どうしの食い違いの一覧、正解との突き合わせ（期間中は Claude が作った仮の正解）を行う（9.2） |
| 質問への答え | 答えに付けた引用が、そのページに本当にあるかを道具が確かめる（9.2） |
| 会社の書類の読み取り | 読み取り役は、読めない値を「要確認」として返す。金額は計算で照合し、日付・金額・名義の食い違いは書類どうしで照らす（8.4） |
| 計画書の数字・固有名詞・日付 | 根拠対照表と照らす（根拠なし0、食い違い0）。計算はすべて道具で行い、Claude は計算しない。数字は財務モデルから取り、計画書・様式・入力シートと財務モデルが一致するかを、コードで照らす |

| 計画書の中身と聞き取りの食い違い | 審査役 |
| 様式の崩れ、文字数 | コード（書き込み前後の構造の比較、文字数と換算） |
| 期限・日付 | すべて道具で計算する。今日の日付は差し替えに従う |
| 画面への入力 | 入れた後に画面の値を読み取り、入力シートと比べる（文字と選択欄。チェック欄とラジオボタンは読み取れないので、担当者が画面で確かめる。5章） |
| 製品全体の振る舞い | テスト（11章）と Δ |

### 8.2 読みやすい申請書にする仕組み

- **構成**：「現状と目標 → 課題 → 解決策 → 効果」を、制度データの様式の項目に割り当てる。各項目の最初に結論を書く。作者の観点と構成の型（例文は入れない）を物差しにする。公開されている採択事例は、作者が観点と構成の要点だけを knowledge/ に書き起こして参考にし、文章は流用しない（どこまで参考にするかは14章）。
- **中身**：会社の資料と聞き取りから、その会社の事実・数字・現場の出来事・社長の判断の理由を使う（文体の基準 C3〜C6）。社名を他社に替えても通じる文にしない。
- **文体**：文体の基準の A・B と、会社の「避けたい言い方」をコードで数える。C は審査役が読んで確かめる。
- **分量**：制度データの上限と目安に合わせる。上限はシステムの上限であって、書くべき長さではない。持続化の4,000字のように上限しかない項目や、指示がない項目は、審査項目を満たすのに必要十分な長さにし、上限まで埋めない（審査役が確かめる）。
- **図表**：作業の前後比較、工程表、数値計画のグラフは、道具が数字から作る（数字は根拠対照表と同じもの）。社長が用意した写真も入れる。
- **最後の確かめ**：作者が、審査役と同じ採点表と文体の基準の C で読む（T9-6）。

### 8.3 財務モデル（計画の数字の土台）

計画書の数字は、表面的なものになりやすい。そこで、前提から数字を組み立てた財務モデルを先に作り、計画書・様式・入力シートの数字はすべてここから取る。後から実績と比べて確かめることもできる。

**大きさの決まり**：財務に詳しくない社長や担当者でも、自分で説明できる大きさにする。ただし、売上を「単価 × 数量」に、人件費を「人数 × 時間 × 単価」に分けることはやめない。ここを省くと、数字の裏付けがなくなるためである。

- **置き場所**：会社のフォルダの直下に「財務モデル.xlsx」を1つだけ置く。2件目の計画は1件目の計画を含めて作るので、案件どうしの数字が食い違わず、同じ経費を二重に数えることもない。2件目を足すと合算は変わるが、提出した案件の数字は、提出版に入れた財務モデルで固定する。計画書と財務モデルの照合（T8-11）は、提出済みの案件ならその提出版の財務モデルと、作成中の案件なら今の財務モデルと行う。
- **シートは3つ**（採択後に「実績」を1つ足す）

| シート | 中身 |
|---|---|
| 前提 | 数字の元になる前提だけを並べる。1社で15個ほどまで（多くても20個）。前提ごとに、値・単位・「この数字は何か」の一言・根拠（決算書・見積書・聞き取り・統計）と出典。決まっていないものには仮の印を付ける。社長が書き換えてよいのは、このシートの色を付けたセルだけ |
| 計画（5年） | 上に「まとめ」として、大事な数字を5つほど言葉で示す（例：5年後の売上、付加価値額の伸び、給与の伸び、要件を満たすか）。その下に、既存事業・新事業（案件ごと）・合算を同じ行の並びで5年度分示す。売上は商品や販路で2〜3区分まで、経費は原材料費・人件費・減価償却費・その他の経費の4区分まで。人件費は「給与支給総額」と「法定福利費など」に分けて持つ（給与の要件に使うのは給与支給総額で、付加価値額に使う人件費とは範囲が違うため）。最後に、補助金の指標（付加価値額、労働生産性、1人当たり給与支給総額、年平均の伸び、補助額など）と、要件を満たすかの判定を置く |
| 月次（1年目） | 1年目の12か月分。売上と経費を月ごとに示し、季節の波や立ち上がりを見えるようにする。合計は計画の1年目とつながる |
| 実績（採択後に足す） | 実績報告と効果報告のときに実績を入れ、年度ごとに計画と比べる |

- **分かりやすくする工夫**
  - 数式には名前を付けたセルを使い、「＝単価_冷凍惣菜 × 数量_冷凍惣菜」のように言葉で読めるようにする。
  - 専門用語には一言の説明を付ける（例：付加価値額は「営業利益＋人件費＋減価償却費。会社が新しく生み出した価値」）。
  - Claude は、財務モデルを見せるときに「売上は〇〇を月〇個、〇円で売る前提です」のように、前提を普段の言葉で説明する。
- **簡単にしすぎないための工夫**
  - 「まとめ」に、数量が計画より2割少なかった場合でも要件を満たすかを1行で示す。要件を満たせないと返還につながるため。
  - 新事業をしない場合（既存事業だけ）と合算を並べて、補助事業の効果を数字で示す。
  - 要件の判定は、様式（省力化なら別紙4）の数式と同じ計算で行う。ちょうど要件の値の計画が、計算の小数の誤差と切り捨てで、基準を下回ることがある（例：給与の伸びがちょうど3.5%の計画が、別紙4 では3.49%になる。実験 E2）。判定（満たす・満たさない）は様式の数式の値（小数第3位以下を切り捨てた値）で行う。そのうえで、切り捨てる前の伸びと基準との差が0.01ポイント未満のときは、満たす・満たさないのどちらでも社長に知らせ、計画の数字を少し上げることを勧める（差は小数第9位で丸めてから比べ、Excel の式でも同じにする）。
- **新事業の列の置き方**：持続化のように新しく売るものは、その売上と経費を置く。省力化のように今の事業のやり方を変えるものは、導入による増減を置く（作業時間が減って下がる人件費、空いた人手で増やす生産の売上と原価、設備の減価償却費）。どちらも、合算の列で既存事業と足し合わせる。
- **作り方**：前提は、Claude が聞き取りと書類から集め、根拠を付ける。数字の組み立ては、すべて道具が Python で行う。Excel には数式のまま書き、どの数字がどの前提から来たかを、社長が Excel で追えるようにする。Excel の数式は、開いたときに Excel が計算する。
- **つながり**：計画書の数字は、根拠対照表に「財務モデルの前提 P-07」のように示す。そこから決算書や聞き取りまでたどれる。
- **審査役**：前提が実績・見積・統計に基づいているか（文体の基準 C4）、売上や経費の伸びに無理がないかを確かめる。
- **採択後**：実績報告と効果報告では、実績のシートに数字を入れ、計画との差と、要件（給与支給総額など）を満たせそうかを示す。満たせない見込みなら、返還の条件とあわせて早めに知らせる。

### 8.4 書類と経費を正しく読み取る仕組み

**スキャンした PDF と写真**

- 道具が、PDF に文字が入っているかを確かめる。文字がない PDF（スキャンしたもの）や写真は、ページを画像にし、向きを直してから読み取り役に渡す。Claude は画像をそのまま読める。
- 別の文字認識のソフトは入れない。初回の用意が増えるうえ、読み取りの正しさは次の照合で確かめるため。
- 読み取る項目は、書類の種類ごとに決めておく。見積書なら、発行日、有効期限、宛名、発行者、品名・型番、数量、単価、金額、小計、消費税、合計、税込か税抜か。請求書と納品書は、これに登録番号や納品日などを足す。
- 金額と明細は、Sonnet 5.5 で読む（7章）。

**計算で照合する（コード）**

- 明細ごとに「数量 × 単価 ＝ 金額」、明細の合計 ＝ 小計、小計 ＋ 消費税 ＝ 合計、税率（10%・8%）が合うかを確かめる。
- 合わなければ、読み違いの疑いがある。その部分を拡大した画像で、Opus 5.5 に読み直させる。
- それでも合わなければ「要確認」とし、その部分の画像と読み取った数字を並べて、社長に確かめてもらう。推測で埋めない。しみなどで数字が読めないときも、ほかの欄から計算で埋めて済ませない（計算で出る値は、確かめてもらう候補として示してよい）。
- 書類どうしも照らす。見積書・納品書・請求書の品名と金額、宛名と会社の記録の社名、日付の順（見積 → 発注 → 納品 → 請求。交付決定より前の発注は事前着手）を確かめる。

**経費の読み取り**

- 経費の一覧は、入力シートの経費明細の欄にまとめ、別のファイルは作らない。行ごとに、経費の区分、品名、数量、単価、金額（税抜）、根拠の種類（見積書・カタログ・メモ・聞き取り）と出典を持つ。
- 見積書から読んだ金額は、上の照合を通ったものだけを使う。
- メモや社長の話からの金額（例：「チラシ代は30万円くらい」）は、仮の印を付けて入れ、見積書がそろったら差し替える。制度データで見積書が要る経費（例：50万円以上の設備）は、見積書がないと完成にしない。
- 経費の区分は、制度データにある「補助の対象になる経費」の定義（出典付き）に照らして、Claude が判断する。迷うものや、対象外になりそうなものは「要確認」とし、資料の該当ページを示す。資料に書かれていなければ、問い合わせ文の案を作る。
- コードで確かめるもの：税込と税抜の混在、経費の合計と補助額（上限と補助率）、財務モデル（投資額と減価償却費）や計画書との一致、2つの案件で同じ経費を数えていないか（二重受給）。

確かめ方は T5-1（不備を仕込んだ書類セットに、スキャンした PDF と写真を含める）、T5-8（スキャンした書類の金額と明細が正解と一致するか）、T8-13（スキャンした見積書とメモから作った経費明細が正解と一致するか）。

- ページは資料の下に印刷された番号で示す。持続化の公募要領・操作手引き・補助事業の手引きは、印刷された番号が PDF のページより1つ小さく、Q&A は5つ小さい。
- 省力化の交付申請の手引きは第6回版までしか公開されていない。持続化の操作手引きと補助事業の手引きは、第19回版が最新である。回の違う資料は、制度データの「資料」に回を明記して区別する。
- 書類の取得の決まり・依頼先・依頼の締切・依頼の目安の日数（表の「書類」の行に書いた欄）と、「義務（事業期間中・事業後）」の欄は、11/5 にスキーマへ任意の欄として足した（K1 の先行）。この表に義務の行を足すのは K1 で行う（表の行はスキーマの必須の欄と1対1で対応させ、tests/test_schema.py で確かめているため）。
  - 義務の行の持ち方：名前、種類（証拠をそろえる・事前に申請する・報告する・守り続ける・残す）、始まりと終わりの決め方（期限の決め方と同じ式）、繰り返し、確かめ方、守れないとき（返還など）、出典。事業期間中の証拠は、経費ごとにそろえる書類の種類で持つ。
  - SPEC 5章で確かめた値：省力化は、計画変更（必要なとき）、状況報告（条件付き）、効果報告（毎年1回を5年）、給与支給総額の伸び（未達は返還）、事業場内最低賃金（地域別+30円）。持続化は、実績報告、事業効果報告（1回）、賃上げ特例の給与支給総額（2027年4月〜2028年3月）。
  - そのほかの値（経費ごとにそろえる証拠の種類、財産の処分の制限の期間、書類を残す期間など）は、A2・A3 で正解を作るときに資料とページを確かめて入れる。
- 財務モデルで判定する数値の要件は、今は道具が基準の文から読み取っている（「◯%以上」「毎年／終了時点」と指標の名前。M5）。持続化の賃上げ特例（12か月どうしの比較、給与支給総額の合計）のように、文の書き方に頼るとプログラムを変えずに判定できない要件が出てきたら（T0-1）、数値の要件に機械で読める「判定」の欄を足す。持つのは、指標（付加価値額・労働生産性・1人当たり給与支給総額 など）、基準の数、比べる時期（毎年・計画期間の終わり）、比べ方（以上）、様式の丸め、特例を選んだときだけか。読み取り役が下書きし、道具が基準の文と食い違わないかを照らす。足すかは B13 で決め、スキーマも直すので日のブランチで行う。表の行は増やさない。

**1つの形で両方を表せる理由**

- 申請も採択後も、同じ「手続きの段階」の形で表す。だから、F3〜F10 の仕組みを F12 でもそのまま使える。
- 様式は「入力先」の違いだけで、ファイルと画面の両方を表せる。
- 期限は決め方の式で持つので、「採択発表から2か月」のような期限も、決まった日付も表せる。

### 9.1 どの補助金でも動く流れ

1. **探す**：jGrants の検索、同梱の「例年公募がある制度の一覧」、所在地の都道府県・市区町村のサイト、厚生労働省の助成金から候補を集める。
2. **制度データを作る**：公募要領・様式・手引きをダウンロードし、読み取り役が制度データの下書きを作る。道具が形を確かめ、出典を裏取りする。読み取れない項目は空けたまま、問い合わせ文の案を付けて社長に示す。
3. **様式を対応づける**：
   - 様式がある制度は、道具が Word・Excel の見出し・表・セルの一覧を作り、読み取り役が様式の項目と書き込む位置を対応づけて、制度データに書く。Excel の様式では、保護したシートのロックしないセル（様式が入力欄として開けてあるセル）を道具が取り出し、書いてよい範囲の下書きにする（実験 E2）。
   - 様式がない制度は、入力シート（画面の項目）に書く。
   - 申請画面（入力シート）の欄と押してよいボタンは、電子申請マニュアルの画面ごとのページから、読み取り役が作る。欄の名前とボタンは画面の絵にしかないことが多いので、PDF のページを画像として読ませる。申請の手続きの章と同じ章の名前で別の呼び出しにし、裏取りの道具で申請画面だけを差し替える（流れのページだけを読むと、欄もボタンも空になり、入力シートが作れず、守りが一時保存も次へも拒んだ。M8・M6）。
   - どちらも決まっていない制度は、様式の項目の一覧から計画書の Word を作る。
4. **あとは制度データで動く**：書類の一覧、日程、段階のフォルダ、書く、確かめる、入力、採択後の手続きのすべてが、制度データで動く。プログラムは変えない（T0-1）。省力化と持続化のほかに、補助金と助成金を1つずつ選んで確かめる（T3-6）。

### 9.2 公募要領を正しく読み、質問に正しく答える仕組み

**資料をページ付きの文字で持つ**

- 公式資料をダウンロードしたら、道具がページごとの文字にして `記録/資料の本文/` に置く。印刷されたページ番号と PDF のページの対応も取る（ずれ方は9章の注のとおり）。出典は、いつも印刷された番号で示す。
- 文字を取り出せないページ（画像だけのページ）や、表が崩れるページは、ページの画像も読み取り役に渡す。

**制度データを作るとき**

- 読み取り役は、一度に全部を読まず、章ごとに読む。値ごとに「根拠の文」（資料から抜き出した短い文）とページを付けて返す。
  - 根拠の文は、ページの文字のとおりに写す（空白と改行の違いは、道具が除いて比べる）。値に関わる所だけを400字まで（仮）写し、離れた2か所を合わせるときは「…」でつなぐ（切れ端は4字以上）。箇条書きの印（文字として写せない記号）や、ページの境目（次のページの上に印刷された番号の行）をまたぐときも、そこを「…」で区切る（またいで写した根拠の文は、裏取りで外れた。M2c）。
  - 値は、金額は円の整数、補助率は "1/2"、日時は {"日時": "2026-10-16T17:00+09:00"} の形で返す。
  - 章ごとの結果は、裏取りの結果と一緒に `記録/制度データ/読み取り/<案件>/<章>_<回目>回目.json` に置く。置き場所は道具が決め、`記録/制度データ/` の決まった名前のほかには書かない。
- 道具が裏取りする。根拠の文がそのページに本当にあるか、値がその文の中にあるかを確かめ、どちらかが外れたら「要確認」にする。道具は状態を下げるだけで、上げない。
  - 数（万・億・令和を読み替える）・割合・日付と時刻は、1つ残らず根拠の文にあることを求める。言葉は言い換えてよいので、2字ずつの組の半分以上（仮）が根拠の文にあればよい。
  - 金額は「万円」「億円」「円」の付いた数を円にしたものと、期限の期間は数と単位の組（「14か月」）と照らす。出来事は、根拠の文のその期間の前にある出来事の言葉と照らす。経費の上限の補助金額は、補助金の額に当たる言葉のある文でだけ通す（数だけを照らすと、単位や出来事を取り違えた期限が確認済みになるため）。
  - 外れた値は、読み取り役にその項目を全部読み直させて、同じ章として道具に通す。道具は、その章の前の結果のうち、渡された項目だけを差し替える。
- 重要な項目（締切、補助上限、補助率、数値の要件、必須書類、補助の対象にならない経費）は、読み取り役にもう一度、別の呼び出しで初めから読ませる。2つが食い違えば「要確認」にする。
- 重要な項目の確かめでは、スキーマで任意の欄（数値の要件の満たせないとき、必須書類の有効期限 など）の「読み取れない」は、埋まっていないに数えず、空けたまま社長に伝えて問い合わせ文の案に回す。必須の欄（締切の日時、補助上限、数値の要件の基準 など）の「読み取れない」は、埋まっていないに数える（11/5 の作者の決定）。
- Q&A と公募要領で書き方が違うときや、回の違う資料が混ざるときは、両方の値と出典を「資料どうしの食い違い」として持ち、社長に示す。
- 新しい版や Q&A が出たら、変わったページだけを読み直す（F7）。
- 作者が作った正解と突き合わせる（T3-7）。期間中は、Claude が作った仮の正解で照らす（作者の確かめは後。14章の「制度データの確かめ方」）。

**質問に答えるとき（F4）**

探し方は固定せず、Claude に任せる。ページごとの文字を言葉で探しても、該当する章を直接読んでも、制度データから出典をたどってもよい。決めるのは、答えの形と、結果の確かめだけにする。

- 答えの形：「結論 → 根拠（資料名・ページ・どの回の資料かと、短い引用）→ 注意」。引用は「」で囲み、資料名とページを添える（コードで照らせるようにするため）。
- 結果の確かめ：Stop hook が、応答の中の引用がそのページに本当にあるかを照らす。なければ応答を終わらせず、Claude に答え直させる。
- 資料に見つからなければ「資料には書かれていません」と答え、事務局への問い合わせ文の案を作る。推測で補わない。

確かめ方は T3-7・T3-8（制度データ）、T4-1（答えが資料にある15問と、ない5問）、T4-2（引用がそのページにない答えを道具が見つけるか）。

## 10. 会社の記録と、書類の版

**会社の記録**（`記録/会社の記録.json`。項目ごとに id を持つ）

| 種類 | 持つもの |
|---|---|
| 事実 | 値、変わりうる情報か、出典（原本とページ／質問と答えた日／社長の手直し）、覚えた日、最後に確かめた日、状態（有効・食い違いあり） |
| 書き方の決まり | 区分（直した表現・好む言い方・避けたい言い方・書き方の方針・構成）、内容、きっかけ（案件・社長の発言や手直し・日付） |
| 不備と差し戻し | 案件、手続きの段階、内容、原因、次に注意する書類と照合の決まり、出典（差し戻しの文面や写真の原本）、受け取った日 |
| 申請と採否 | 案件、結果、受けた指摘（審査のコメントや、不採択の後の相談で受けた指摘）、指摘に当たる審査項目、出典（採否の通知や指摘のメモの原本）、日付 |

どの種類も、覚えた日と、出典（原本・質問・社長の手直し・社長の発言）を必ず持つ。だれが書き、だれが直してよいかは4.5。変わりうる事実は、最後に確かめた日が今日より前なら、使い回す前に「前回は◯でしたが、変わりましたか」と確かめる（仮）。

**学ぶきっかけと、残し方**

| きっかけ | 見つけ方 | 残し方 |
|---|---|---|
| 会話での指摘・訂正 | Claude が判断する。UserPromptSubmit hook が、「直して」「違う」「〜ではなく」などの言葉を見つけたら、「記録に残すか判断する」という一言を添える | 道具で会社の記録に加える。「今回だけ」は残さない。どちらとも取れるときは「次からもそうしますか」と確かめる |
| 社長が Word・Excel の申請書を手で直した | 社長が送ったとき（UserPromptSubmit）と開いたとき（SessionStart、4.7）に、前の版との差分をコードで出す。タブ・改行・空白の違いはそろえてから比べる（LibreOffice で保存し直すと、中身が同じでもずれるため。実験 E2）。差分は3,000字（仮）までにし、超えたら直した項目の一覧だけを渡して、中身は道具で読ませる | 差分を Claude に渡す。Claude は、事実の訂正か、言い回しか、方針かを判断して残す。迷えば聞く |
| 差し戻し | 社長が貼った文面や、画面の写真 | 不備の型として残し、次からの不備チェックの照合に加える |
| 採否と、受けた指摘 | 社長が入れた採否の通知と、指摘のメモ（審査のコメントや、不採択の後の相談で受けた指摘）。理由を開示しない制度もあるので（ものづくり補助金 20次締切の公募要領）、メモも同じように受け取る | 指摘に当たる審査項目を残し、次の申請で審査役が応えているかを確かめる |
| 会社の資料・過去の申請書 | 最初に、読み取り役が読む | 事実として、出典と日付を付けて残す |

**学んだことを次に生かす仕組み**

- 開いたとき：記録の要約（変わりうる情報、最近増えた決まり）を渡す。
- 書くとき：`kaku` は書き始める前に、道具（skills/kaku/scripts/relevant_records.py）に書く項目の名前を渡し、関係する事実と書き方の決まりを取り出す。事実は、項目の名前と重なるものを先に並べ、ほかの事実も後ろに並べる（会社の事実は制度をまたいで使うので、制度では絞らない）。書き方の決まりと前の申請で受けた指摘は、すべて添える。記録から書いた箇所は、根拠対照表に記録の項目（例：会社の記録 事実-0001（従業員の数））として残る。
- 確かめるとき：「避けたい言い方」は、コードの文体の確かめに加わり、出てきたら要修正になる。同じ文字の言い回しは、コードが必ず見つける。活用や語順を変えた言い回し、書き方の方針、構成の決まりは、審査役が確かめる。
- 書類を集めるとき：過去の差し戻しの型が不備チェックに加わり、同じ不備を前もって注意する。
- 記録は会社のフォルダの中にあるので、セッションが変わっても、フォルダを別のパソコンに移しても残る。
- 変更の履歴（いつ・何から何に・だれが）は、版の履歴を項目ごとにたどって作る。同じ情報を2か所に持たない。
- 記録と違う値が出てきたら、道具は上書きせず、食い違いとして知らせる。Claude は両方を出典付きで示し、社長に決めてもらう。

**書類の版**

- 版の持ち方は2つで、会社のフォルダを作るときに経営者が選ぶ置き場所（4.7。①パソコンの中だけ、②期限の一覧だけクラウド、③フォルダごとクラウド）から決まる。①②と、③の GitHub は Git の形、③の Google ドライブ・OneDrive・Dropbox は同期されるフォルダの形。どちらでも、版の操作は同じ道具の入口（`lib/history.py`）から行い、skill と hook は持ち方を気にしない。
  - **Git の形**（①を勧める）：会社のフォルダの Git で管理する（送り先は持たない。③で GitHub を選んだときだけ、記録したリポジトリ1つを持つ。5章）。git のコマンドがない Mac でも動くよう、Python だけで動く Git（dulwich）をプラグインに同梱する（実験 E5）。利用者の全体の除外の指定（core.excludesFile、`~/.config/git/ignore`、`$XDG_CONFIG_HOME/git/ignore`）と `.git/info/exclude` は読まず、履歴に入れないものは会社のフォルダの `.gitignore` だけで決める（書類が黙って履歴から抜けないため）。利用者とパソコン全体の Git の設定（~/.gitconfig、GIT_CONFIG_GLOBAL、/etc/gitconfig。core.autocrlf や init.defaultBranch など）も読まない。同梱の dulwich は書き換えず、lib/history.py が読み込むときに設定の読み方と除外の読み方を差し替える。1回の場面で残しきれないファイルは次の場面に回し、回した場面のだれ・理由で残す。1つ2GB を超えるファイルと、時間内に読みきれないことが続いたファイルは版に残さず、開いたときに知らせる（仮）。1MB 以上のファイルは圧縮せずに置く（写真・PDF・Word はもともと圧縮されているため）。
  - **同期されるフォルダの形**（③で Google ドライブ・OneDrive・Dropbox を選んだとき）：Git は使わず、版を1つずつ丸ごとのファイルとして `記録/版/<書類>/` に「日時 だれ 印.拡張子」の名前で残す（読み取り専用。足すだけで書き換えない）。1件ごとの記録（版の印（Git と同じ40桁）、日時、だれ、理由、書類ごとの変更・案件・段階・版のファイル・sha256）は `記録/版/_版の一覧/` に1件1ファイルで置く。何が変わったかの控え・錠・書きかけは `.hojokin/一時/版の記録/` に置き、控えが消えても `記録/版/` から作り直す。原本と公式資料は、道具が置く前に中身を `記録/版/_預け/`（名前は中身の sha256）に読み取り専用で預ける（Git の形で .git に中身を入れるのと同じ役目）。戻すときは、預けた中身と版のファイルから sha256 で探し、版のファイルを取り出すときは sha256 を照らして、合わなければ断る。見分けは、.git があれば Git の形、なくて `記録/版/` があればこの形（lib/history_form.py）。版のファイルは規則の deny（`Edit(/記録/版/**)`）で書き換えさせない。足すだけなので同期で食い違いにくく、社長も前の版を Finder で見られる。履歴は同期先にも上がる（経営者が同意したときの例外）。2台のパソコンから同時に使わないよう案内する。道具の中身は M0c で作ったが、この形を選ぶ入口は期間中に作らない（4.7）。
- 書類ごとに1つのファイルを直して使う。版は hook の1回ごとに1件残し、「理由」「だれ（ツール・社長）」は版ごとに、「書類」「変更（足した・変えた・消した）」「案件」「段階」は書類ごとに、版のメッセージに決まった形（「理由: 」「書類: 」などの行）で書く。履歴を見るときは、lib/history.py が書類ごとの1件に分けて返す（同期されるフォルダの形でも同じ形で返す）。
- 版の履歴の中のファイルの名前は、濁点が分かれた形（Finder などで作られる）を1文字の形にそろえて残す（実験 E5）。作業のファイルの名前そのものは変えず、原本の置き場に移すときに、書類を整理するスクリプトがそろえる。
- 前の版や提出版を見るときは、`見るだけ/` に読み取り専用で取り出し、次に開いたときに片付ける。作業のファイルは増えない。
- 戻すときは、戻したこと自体を新しい記録として残す。履歴は書き換えない。
- 「提出した」と言われたら、kiroku の道具が、まだ版になっていない変更を先に残してから、提出版を記録する。
  - 提出版に入るのは、その段階のフォルダのすべて（申請書/ と 添付する書類/）と財務モデル.xlsx（8.3）。
  - 記録するのは、版の一覧（`記録/提出版.json`。案件・段階・番号・日時・版の印・社長の発言・ファイルごとの場所と大きさと sha256）と Git の印（`refs/tags/提出版/<案件>/<段階>/<番号>`。同期されるフォルダの形では、Git の印の代わりに、ファイルごとの版のファイルを版の一覧に書く）。出し直すと番号を1つ増やして足す。
  - 取り出すときは、版の中身の sha256 を記録と照らしてから `見るだけ/` に出す。だから、提出したときと同じ中身になる。
  - 段階のフォルダに、版の履歴に残せないもの（読めないファイル・フォルダ、.gitignore に当たるファイルなど）があれば、提出版を記録せずに、場所とわけを知らせる（Word・Excel が開いている間だけ作るファイルと、パソコンが自動で作るファイルは除く）。
  - 提出版の記録は前の版に戻さない（壊れたか消えたときだけ、直すために戻せる）。
- 原本と公式資料は、入れたときの1版だけが残る（版のファイルの形では、ほかに `記録/版/_預け/` に同じ中身が1つ残る。版の履歴には数えない）。そのため、整理の道具と公式資料を取る道具は、置く前に中身を版の履歴の置き場に入れ、版の印を台帳と資料の一覧の「置き場所」、原本の控え（5章）に残す。同じ応答の中で書き換えられても、応答の終わりに入れたときの中身へ戻せるようにするため。

## 11. テストの組み方

`claude plugin eval` には、次の制約がある。

- 自作のコードで採点できない。
- 社長役のような、模擬の利用者を置けない。
- 複数回のやりとりは、過去の会話のファイル（`history_file`）を渡す形だけ。
- `file_exists` が数えるのは、実行中に新しくできたファイルだけ。
- 準備のスクリプト（scaffold）は、`--scaffold` を付けたときだけ動く。

製品と同じようにスクリプトを動かせるよう、`--allow-tools` に Bash も入れる（SPEC 6章）。

**eval で確かめられないこと**（実験 E3）

- 会社のフォルダの `.claude/settings.json` は、eval では読み込まれない（外を読ませない設定、deny、allow は効かない）。これらは、pytest（設定の中身）とデスクトップアプリで確かめる。hook による守りは eval でも効く。
- eval の中の権限のモードは `dontAsk` で、デスクトップの default・auto とは違う。auto モードだけの経路（審査役の SubagentHandback。8章）は、記録した hook の入力を pytest で渡して確かめる。
- Bash の sandbox は通信を許さず、eval の道具の一覧に WebSearch・WebFetch がなかった。通信が要るケースの作り方は14章。
- T10-3 を模擬画面の記録で確かめる回では、担当者は確認・誓約・同意の欄に入れない。記録だけでは、入れたのが担当者かツールかを見分けられないため（D11a）。欄が担当者の欄かツールの欄かは、模擬画面の入力値.json の who で分かる（持続化では、4つの語を含まない担当者の欄もあるため、名前の語ではなく who で見る。D11c）。
- 会社のフォルダの設定ごと通しで試すとき（M12b など）は、claude -p に `--setting-sources project` と `--settings '{"permissions":{"blockReadsExemptPaths":["<読み込むプラグインのフォルダ>"]}}'` を付ける。プラグインを入れた場所と同じ扱いになり、allowed-tools の効き方も確かめられる（4.7）。eval は今のとおり、会社のフォルダの設定を読まない。

**採点の優先順**

1. `regex`：最後の応答、質問の記録、確かめの結果のファイルの文字を見る。
2. `tool_used`：読み取り役や審査役を呼んだか、道具に何を渡したか。
3. `file_exists`。
4. AI による判定（`llm`）は、T11-1 と T2-3 だけにする。SPEC で審査員役が判定するテストは、審査役が保存した結果で見る。合格ラインが「すべてに判定と理由」のもの（T9-3b、T9-5）は、そろっているかを `regex` で見る。判定の中身を求めるもの（T8-8、T8-9、T13-6 の方針と構成、T13-9）は、残した出力を pytest で調べる（下）。

**残した出力を、あとから pytest で調べる**（`--keep-temp`）

- 残ったフォルダは読み取り専用（`sealed/` は mode 000）なので、調べる前に chmod で読めるようにする。中の版の履歴は dulwich で読むか、外に写してから読む（中で git を動かさない。実験 E3）。
- T5-1：仕込んだ不備の一覧（testdata/書類セット/仕込んだ不備の一覧.json）と、不備の id ごとに突き合わせる。見逃し0件を求めるのは、SPEC T5-1 の重大の5つに当たる不備（一覧の「SPEC の重大」）で、ほかは SPEC の割合で見る。一覧の「関連して出てよい指摘」は、誤りの指摘に数えない。
- T5-4：ファイルの移動先と名前。
- T3-7：制度データの正解との一致（照らす範囲は14章の「制度データの確かめ方」）。
- T5-8・T8-13：読み取った金額と明細、作った経費明細が、正解と一致するか。
- T8-8・T8-9・T13-6・T13-9：審査役が保存した結果の判定が、SPEC の合格ラインを満たすか（例：T8-8 は、4つの段がそろい、つながりが切れている所が0件）。判定と理由があるだけでは合格にしない。

**Δ（プラグインなしとの差）**

- `--ablation with-without` で測る。
- プラグインなしでも同じ物差しで採点できるケースに絞る。候補は T0-10（推測しない）、T1-1、T4-1、T5-1、T8-5、T9-2、T12-3。
- 採点は最後の応答の文字で行い、プラグインの道具が作るファイルには頼らない（例：T5-1 は、仕込んだ重大な不備がすべて最後の応答に出てくるかで採点する）。制度データのファイルを調べる T3-7 は、Δ の候補にしない。
- 結果は README と動画に載せる。

**公式の資料を含む材料**

- 公募要領・様式・手引きは、リポジトリに入れず、downloads/ に置く（このリポジトリの決まり）。
- それを含むテストの材料もリポジトリに入れず、テストのときにスクリプトが downloads/ から作る。段階ごとに保存した会社のフォルダの公式資料、手で直した計画書の Word（T13-14）、公募要領の新旧2版（T7-1）がこれに当たる。
- 新しく clone した所では、先に資料を downloads/ に取るスクリプトを動かす（README に書く）。
- 段階ごとに保存した会社のフォルダ（`evals/状態/<段階>/`）には、作り直せないもの（原本・会社の記録・書類の台帳など）だけを置く。公式資料、資料の本文、制度データ（リポにある正解から置く）、概要と流れ.docx は、戻し方（`evals/状態/<段階>.json`）に従って、scaffold が製品の道具で作る（M12 の制度データと概要と流れ.docx には、資料の文をそのまま写した値が多く、保存できなかったため）。戻す道具は `evals/_lib/fukugen.sh <段階>` で、ケースの scaffold.sh から呼ぶ。公式資料は、取る道具に、通信の代わりに downloads/ から写す downloader を渡して置く。戻した版の履歴は、ツールの版1件にする（保存したときの履歴には公式資料が入るため、戻さない）。
- 人が撮った写真をテストの材料に入れるときは、そのまま入れない。EXIF・XMP（撮った位置・機種・日時）と色の情報を落とし、画素だけを保存し直したものを入れ、元の写真は Git の外に置く。材料を確かめるスクリプトは、JPEG に EXIF・XMP がなく、区切りが APP0 だけであることを確かめる（一度 Git の履歴に入った位置の情報は消しにくいため）。

## 12. 開発中の検証体制

| いつ | 何を | 仕組み | 費用 |
|---|---|---|---|
| ファイルを直したときの、各回の終わり | 構成の検査と、速いテスト（通信なし、数十秒） | 開発用リポジトリの Stop hook（`.claude/settings.json` に書き、プラグインには入れない）。変わったものがなければ流さない（下の指紋で見る）。落ちたら、直すまで続けさせる（2回まで） | かからない |
| 1つの機能を作り終えたとき | その機能の振る舞いテストを1回ずつ | eval に `--tag <機能> --runs 1 --ablation none --max-cost-usd <上限>` を付けて流す。通るまで直すときは `/goal` を使う。`/goal` の判定役は会話しか見ないので、終わりの条件は「eval の出力で、全ケースの合格を示した」にする | 少し |
| コミットの前 | 仕様に照らして、正しさに穴がないか | 開発用の subagent `spec-check`（Read・Grep・Glob、Opus 5.5。プラグインには入れない）。SPEC の該当箇所と変更を照らし、要件の抜け、違う振る舞い、テストの抜けだけを返す。文体は見ない | 少し |
| 毎日の終わり | 振る舞いテストを全部1回 | `--runs 1 --ablation none` | 中くらい |
| 11/6 と 11/8 の朝 | Δ と、3回とも合格するか | Δ のケースは `--ablation with-without`、全部は既定の3回 | 中くらい |

表の eval は、どれも SPEC 6章のコマンド（`claude plugin eval . --scaffold --trust-plugin --allow-tools Bash Write Edit --threshold 1.0 --json`）に、表のオプションを足して流す。ケースのファイルに runs を書かず、`--runs` も付けなければ、1ケースを3回流す。

hook とスクリプトは Mac の `/usr/bin/python3`（3.9）で動くが、テストは uv が入れた新しい Python で流れる。3.10 以降の書き方を見落とさないよう、速いテストで、lib/・hooks/・skills/*/scripts/ を `/usr/bin/python3` で読み込めるかも確かめる。

開発用の Stop hook は、変わったものがなければ流さない。lib/・hooks/・skills/・agents/・schema/・tests/・evals/・mock/・.claude-plugin/・testdata/・knowledge/・pyproject.toml・uv.lock について、`git ls-files -s`、diff、未追跡のファイルから指紋を作り、最後に通ったときの指紋と比べる。通った指紋は、セッションと worktree をまたいで1つのファイル（Git の共通のフォルダ）に持つ。コミットしただけの回、文書だけを直した回、別の worktree で同じ中身を確かめた後の回は流さず、待ちを増やさない。

**振る舞いテストの費用を抑える工夫**

- 保存しておいた状態から始めて、ケースを短くする。
- 機能ごとのタグを付け、直した機能のケースだけを回す。
- 採点はコードを優先し、AI の判定は2つのテストだけにする（モデルは7章）。
- `--max-cost-usd` で上限を決める。
- Δ と3回の実行は、節目にだけ行う。

**部品が効いているかを測る**

記事は、ハーネスの部品はどれも「モデルが自分ではできないこと」についての仮定で、モデルが変われば要らなくなるものもある、と書いている（15.4）。そこで、部品を1つずつ外した版と比べ、効いていない部品は外す。対象は、毎回の審査役（最後に1回だけにした場合と比べる）、UserPromptSubmit の一言、重要な項目の2回の読み取り。11/6 の Δ と同じ仕組みで測る（実験 E12）。

**開発中の承認を減らす**（このリポジトリの設定。プラグインには入れない）

- 開発のセッションは auto モードで行う（デスクトップアプリのモードの選択。ターミナルでは 2.1.283 以降、使えるときは auto が既定）。
- ファイルの編集は Edit・Write、読み取りは Read で行い、python3 での書き込みや、長くつないだ Bash は使わない。auto モードでは、このリポジトリの中の編集は確認なしで通るが、Bash で python3 を動かすと分類器にかかり、確認が出やすいため。
- このリポジトリの `.claude/settings.json` の許可の規則には、よく使う読み取りの操作とサイト（`/fewer-permission-prompts` で選んだもの）と、`git add`・`git commit`・`uv run pytest`・`claude plugin validate` を入れてある。狭い規則は auto モードでも効き続ける。利用枠を使う `claude plugin eval` と、push・マージは、今までどおり確かめる。
- 会社のフォルダの外を止める block の2つ（4.7）は、製品が会社のフォルダに作る設定に書くもので、このリポジトリの設定には入れない。このリポジトリには、会社の書類を置かないため。
