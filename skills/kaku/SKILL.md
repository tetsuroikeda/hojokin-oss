# 申請書を書く・確かめる・直す（F8、F9、F10 の入力シート、F11、F12 の差し戻しと実績の比較）

## 最初に目印を確かめる

- 最初に、今のフォルダに `.hojokin/`（会社のフォルダの目印）があるかを確かめる。
- 目印がなければ、ほかのことをせずに「このフォルダを〇〇社の会社のフォルダにしますか」と社長に聞く。
- 社長が了承したら、会社のフォルダを作る道具で用意してから進める。了承がなければ、何も書かずに終える。
- 今のフォルダは、Claude を開いたフォルダ（会話の環境の作業フォルダ）のこと。`cd` で会社のフォルダに入っても、道具に `--folder` で会社のフォルダを渡しても、hooks は開いたフォルダしか見ないので動かない（質問の記録・審査役の結果・版の記録が残らない）。開いたときや発言のときに「【hojokin】開いたフォルダ（…）は会社のフォルダではありません」と出たとき、道具の出力に「【注意】hojokin の hooks が…動いていません」と出たときは、先へ進まず、社長に Claude を会社のフォルダで開き直してもらう。

## 道具の動かし方（どの手順にも共通）

- 社長の答えを受けて続けるとき（新しい発言のたび）、読み取り役・審査役から戻った後、会話を開き直した後は、道具を動かす前にこの skill を呼び直す（呼び直さないと、道具が確かめの画面で止まることがある）。
- 道具に渡す JSON と文は、Write で `記録/一時/<決まった名前>` に置き、その場所を `--input`・`--values` で渡す。標準入力（`<<'EOF'`）では渡さない（会社のフォルダの設定で、確かめの画面が出るため）。ファイルは消さず、同じ名前で上書きする。
- その場の計算や読み取りのコードは書かない（`記録/一時/` の .py も `python3 -c` も使わない。パイプ・sed も使わない）。数字は財務モデルの道具で出す。JSON と文字のファイルは Read で読む。原本の PDF・Word・Excel（労働者名簿.xlsx など）の文字は、次の道具で出す。

```bash
python3 -B "${CLAUDE_PLUGIN_ROOT}/skills/kaku/scripts/moji.py" --folder "${CLAUDE_PROJECT_DIR}" --file "<原本の場所>" [--page <PDF のページ>]
```

## 書く前に会社の記録から取り出す

目的は、会社の記録にあることを社長に聞き直さず、記録にある強みや事実を初稿に入れること（SPEC F13）。

- 項目を書き始める前（書く前の質問を組み立てる前）に、書く項目の名前を渡して、関係する事実と書き方の決まりを取り出す。

```bash
python3 -B "${CLAUDE_PLUGIN_ROOT}/skills/kaku/scripts/relevant_records.py" --folder "${CLAUDE_PROJECT_DIR}" --item "<様式の項目の名前>" [--item "<別の項目>"] [--json]
```

- 出力の「当たりそうな事実」を先に使う。「そのほかの事実」も、項目に関係するものは使う。記録にあることは聞かない（1件目で答えてもらったことを、2件目でもう一度聞かない）。
- 出力の先頭の「使い回す前に確かめる変わりうる情報」のうち、書く文に使うもの（従業員の数は、会社の紹介や従業員数の欄で必ず使う）は、書く前の最初の質問の1問目で「前回は◯でしたが、変わりましたか」とまとめて確かめる。確かめずに初稿に使わない（SPEC F13「変わりうる情報は確認する」。この確かめは聞き直しに数えない）。変わらなければ確かめた事実ごとに kiroku の `record.py confirm`、変わったら `record.py update-fact` で記録を直してから書く。
- 「食い違いあり」の事実は、両方を出典付きで示して社長に決めてもらうまで使わない。
- 記録にないことだけを社長に聞く。答えで分かった事実は、kiroku の `record.py add-fact` で出典（質問と答えた日）と一緒に残す（次の申請で聞き直さないため）。
  kiroku の記録の道具は、この skill からも動かせる（書き方は kiroku の SKILL.md と同じ）。

```bash
python3 -B "${CLAUDE_PLUGIN_ROOT}/skills/kiroku/scripts/record.py" add-fact --folder "${CLAUDE_PROJECT_DIR}" --name "<名前>" --value "<値>" --changeable --source 質問 --question "<聞いた質問>"
python3 -B "${CLAUDE_PLUGIN_ROOT}/skills/kiroku/scripts/record.py" confirm --folder "${CLAUDE_PROJECT_DIR}" --id <事実の id>
python3 -B "${CLAUDE_PLUGIN_ROOT}/skills/kiroku/scripts/record.py" update-fact --folder "${CLAUDE_PROJECT_DIR}" --id <事実の id> --value "<新しい値>" --source 社長の発言 --utterance "<社長の発言>"
```

- 書き方の決まりは、どの申請書にも当てる。避けたい言い方は使わない。前の申請で受けた指摘には、応える記述を入れる。
- 記録から書いた箇所は、根拠対照表に、出力の「根拠対照表の出典」（例：`会社の記録 事実-0001（従業員の数）`）を出典として残す。
- 終了コード2は、記録が読めないときなど。理由を社長に伝え、記録にあるはずのことも推測で書かずに確かめる。

## 書く前に、足りない情報を洗い出して聞く（仮の印と空欄、会社の資料を使う）

目的は、推測で埋めずに、その会社ならではの事実と言葉で書くこと（SPEC F8、共通の要件「聞き方」、DESIGN 6章）。

0. 作者の知見を道具で出して読む：構成の型（審査員が追う筋、つなぎが切れやすい所、伝えるための事実の候補、図表が効く所）と、この制度の審査の観点、制度ごとの注（その制度だけの指標や様式の書き方。あるときだけ出る）。これは書き方の型ではなく、審査員に何が伝われば納得するかの観点。審査役も同じ観点で、伝わるかを確かめる。どの補助金でも、制度データの目的・審査項目・加点と、この知見から自分で考える。プラグインの中のファイルは Read では読めない（会社のフォルダの外として守りが止める）ので、Read で開かない。

   ```bash
   python3 -B "${CLAUDE_PLUGIN_ROOT}/skills/kaku/scripts/kakunin.py" chiken --folder "${CLAUDE_PROJECT_DIR}"
   ```
1. 書く項目ごとに、この会社で審査員を納得させるのに要る事実（数字・固有名詞・日付・社長の判断の理由）を考えて並べ（構成の型の事実の候補は、考える手がかり。全部を埋める必要はなく、その会社に効くものを選ぶ）、会社の記録（上の道具）、原本の置き場と入れ口の書類（決算書・見積書・名簿・会社案内・議事録・商品の資料・事業別の収支・写真など）、これまでの答えのどこにあるかを確かめる。書類の文字は moji.py で読む。
   - 議事録・会社案内・事業別の収支などの会社の資料にしかない事実（現場で測った時間、設備の止まった回数、ミスが起きた時間帯など）は、その会社ならではの事実として本文に使う。根拠対照表の出典には、その資料の場所とページを書く（例：`原本/会社の資料/<資料の名前>.docx p.2`）。
   - 様式や審査項目が求める事実の裏付けになる書類が手元にないときは、必須の書類でなくても社長に頼む（例：直近実績の表が3年分なのに決算書が2期しかない、作業時間の実測の記録、見積の比べ、現場の写真）。必須書類は申請を通すための最低限で、計画書を説得力のあるものにするのは、こうした書類の事実だから。届くまでは【空欄：…】にし、「記載なし」とは書かない。
2. どこにもない事実を、全体の一覧にして社長に見せてから聞く。
   - 選択肢の画面（AskUserQuestion）で1問ずつ聞く。選択肢には勧める案と「分からない」を入れ、問いの文の終わりに「（理由：…）」を付ける。
   - 選択肢の画面が使えないとき（拒まれたとき）は、普段の文章で、行の頭に `【質問】` と書いた後に、`1. 問い（理由：…）` の形で並べる。
   - 一度に聞くのは3つまで。多いときは、先に全体の一覧を見せてから3つずつ聞く。質問と答えは、hook が案件と段階を付けて `記録/質問の記録.json` に残す（Claude はこのファイルを書かない）。
3. 答えを待つ間に下書きを書くときは、手元の資料と答えから考えられる案を【仮：…】で書く。
   - 過去と今の事実（決算の数字、人数、作業時間、取引先の名前、起きたこと）は、仮でも作らず【空欄：何が要るか】にする（例：`【空欄：今の作業の1日の延べ時間】`）。資料にも答えにもない事実を、それらしく作らない。
   - 将来の計画（増産の量、伸び率、単価や商品構成、ロス・残業の減り方、新しい販路、ほかに考えた手と選んだ理由、リスクと手当て）は、計画を作るのが仕事なので、Claude が根拠を添えて提案してよい。【仮：提案。理由】で書き、社長に選んでもらう（下の「構想を立てる」）。
   - 情報が少ないことを、浅い計画のいいわけにしない。空欄を並べて止まらず、筋書きの案を先に示し、社長には「この案でよいか」を聞く（社長は、白紙の質問より、案を直すほうが答えやすい）。
4. 答えで分かった事実は、kiroku の `record.py add-fact` で出典（質問と答えた日）と一緒に残し、【仮】【空欄】を書き直す。社長が選んだ提案も、社長の答えとして残す（出典は社長の答えと日付）。

## 構想を立てる（少ない情報から、投資の効果が数字で伝わる筋書きを作る）

目的は、審査員が「この投資（設備・販路開拓・人への投資など、制度が支えるもの）で会社がこう良くなる」と数字で納得できる、創造的で実現できる計画にすること（SPEC F8「設備投資の効果を財務計画の損益に表す」）。効果の筋は、制度データの目的・審査項目と、会社の困りごとから組み立てる。財務モデルを作る前に行う。財務モデルの道具が「投資の効果の見え方」の知らせを出したときも、ここに戻る。

1. 構想役（subagent の `hojokin:kousou`。Opus 5.5）を呼ぶ。依頼の文には、読むファイル（会社の記録、財務モデルの指定と数字の控え、制度データ、見積書やカタログの文字を `記録/一時/` に置いたもの）と、社長の目指すこと・困りごとを書く。構想役は、効果の連鎖、堅実・標準・積極の3つの筋書き、勧める筋書きと財務モデルの式の案、社長に聞くことを JSON で返す。
2. 勧める筋書きを、社長に普段の言葉で、数字の根拠を添えて示す。選択肢の画面で、勧める案・ほかの2つ・「直したい」を示して選んでもらう。
3. 選んだ筋書きを財務モデルの指定にする。確かさが「社長に確かめる」「一般的な目安」の前提は、社長が認めるまで `"仮": true` にする。認めたら、根拠を「社長の答え（日付）」にして仮を外す。
4. 筋書きは、計画書の芯にする。効果の組み立て、ほかに考えた手と選んだ理由、リスクと手当てのうち、審査員の納得に効くものを、効く所で数字と一緒に書く（どの項目に何を書くかは決めない）。

- 構想役の提案は、社長が選ぶまで決まったものとして書かない。社長が「もっと控えめに」「もっと攻めたい」と言えば、構想役の別の筋書きか、前提を変えて財務モデルを作り直す。
- 数量を2割減らしても数値の要件を満たすか（財務モデルの道具が判定）は、どの筋書きでも確かめる。積極的な案ほど、守れることを数字で示す。
- 社長が答えて会社の記録が増えたら（増産の量、取引先、単価、人の配置など）、その答えを前提にして財務モデルを作り直し、計画書と様式の数字をそろえる。コードの確かめは、財務モデルを作った後に増えた・変わった事実を「注意」に挙げる。

## 財務モデルを作る（計画書の数字は、すべてここから取る）

目的は、前提から数字を組み立てた財務モデル.xlsx を先に作り、数値の要件を満たすかを様式と同じ計算で確かめること（SPEC F8、DESIGN 8.3）。数字の計算は道具が行う。Claude は電卓の代わりに計算しない。

- 前提（単価・数量・賃上げ率など）と基準年度の実績（決算書の売上・原材料費・給与支給総額・その他の人件費・減価償却費・その他の経費・役員数・常勤従業員数・全月分の給与を受けた従業員数）を、聞き取りと書類から集める。数字は書類か社長の答えにあるものだけを使う。決まっていない前提は `"仮": true` にする。
- 集めたものを、指定の JSON として `記録/財務モデルの指定.json` に書く。前提は15個ほど、多くても20個まで。率は小数で書き、単位を `"%"` にする。前提ごとに「根拠」と「出典」を書く（基準年度の値にも）。
- 売上は「単価 × 数量」に分け、数量の前提の名前は `数量_` で始める（例：`数量_<商品>`）。道具は、`数量_` の前提を2割減らした場合も数値の要件を満たすかを判定する。
- 足し算・割り算・時間の換算は、その場で Python を書かず、道具で出す。基準年度の値と、制度に固有の指標（省力化の省力化指数など。制度ごとの注に書き方がある）は、道具が出す（`記録/一時/` にその場の計算のコードを置かない）。
- 市場や商圏の大きさ、地域の需要などの推定に、出典つきの公的な統計を使ってよい（出典を根拠対照表に残す）。推定の計算は、統計の値を前提に置いて財務モデルで行う。

### 基準年度の値を決算書から足し上げる

決算書（売上原価の明細と販売費及び一般管理費の明細）の科目ごとの金額を、区分（売上・原材料費・給与支給総額・その他の人件費・減価償却費・その他の経費）に割り当てて、`記録/一時/決算の内訳.json` に Write で置く。人件費と給与の区分は、制度の様式や公募要領の定義に合わせる（定義が制度ごとの注にあれば、それに従う）。人数は、名簿などの出典と一緒に `"人数"` に書く。

```json
{"決算書": "決算書 第18期", "行": [{"科目": "材料費", "区分": "原材料費", "金額": 82600000, "出典": "p.3"}, {"科目": "労務費の給与", "区分": "給与支給総額", "金額": 33400000, "出典": "p.3"}],
 "営業利益": {"金額": 4800000, "出典": "p.2"},
 "人数": {"役員数": {"値": 2, "根拠": "役員名簿", "出典": "役員名簿"}, "常勤従業員数": {"値": 15, "根拠": "労働者名簿", "出典": "労働者名簿"}, "給与を受けた従業員数": {"値": 15, "根拠": "労働者名簿", "出典": "労働者名簿"}}}
```

```bash
python3 -B "${CLAUDE_PLUGIN_ROOT}/skills/kaku/scripts/zaimu_model.py" kijun --folder "${CLAUDE_PROJECT_DIR}" --input 記録/一時/決算の内訳.json --into 記録/財務モデルの指定.json
```

- 道具が区分ごとに足し上げ、足し上げた営業利益が決算書の営業利益と合うかを確かめてから、指定の「基準年度」を置き換える（出典には科目と金額が並ぶ）。合わなければ何も書かずに断るので、抜けた科目や区分の割り当てを直す。

### 制度に固有の指標

省力化の省力化指数・投資回収期間のように、制度に固有の指標と様式の書き方は、上の chiken が出す「制度ごとの注」に従う（その制度のときだけ出る）。

- 1年目の月次に季節の波を付けるときは、`"月次の波": [12か月分の重み]` を足す（売上と原材料費をその重みで分ける）。なければ12か月で同じにする。

```json
{
  "計画の年数": 5,
  "前提": [
    {"名前": "単価_<商品>", "値": 680, "単位": "円/個", "説明": "<商品>1個の値段", "根拠": "聞き取り", "出典": "社長の答え（日付）"},
    {"名前": "数量_<商品>", "値": 18000, "単位": "個/年", "説明": "1年に売る数", "根拠": "聞き取り", "出典": "社長の答え（日付）", "仮": true},
    {"名前": "賃上げ率", "値": 0.04, "単位": "%", "説明": "1人当たりの給与を毎年上げる割合", "根拠": "聞き取り", "出典": "社長の答え（日付）"}
  ],
  "基準年度": {
    "売上": {"値": 201600000, "根拠": "決算書", "出典": "決算書 第N期 p.2"},
    "原材料費": …, "給与支給総額": …, "その他の人件費": …, "減価償却費": …, "その他の経費": …,
    "役員数": 2, "常勤従業員数": 7, "給与を受けた従業員数": 7
  },
  "既存事業": {"給与支給総額": "基準_給与支給総額*(1+賃上げ率)^年"},
  "新事業": [{"名前": "<商品>", "始まる年": 1, "売上": "単価_<商品>*数量_<商品>", "原材料費": "…"}],
  "人数": {"常勤従業員数": "基準_常勤従業員数+1"}
}
```

- 行の名前は、売上・原材料費・給与支給総額（全月分の給与を受けた従業員の分）・その他の人件費（法定福利費・役員の報酬など）・減価償却費・その他の経費。人件費と営業利益は道具が計算する。既存事業で書かない行は基準年度のまま、新事業で書かない行は0、人数で書かない人数は基準年度のまま。
- 投資の効果を、式のどこかに必ず入れる（どの行に効くかは、構想の筋書きによる）。人件費を賃上げだけで伸ばし、売上を少し伸ばすだけの式では、投資の効果が損益に出ず、審査員に伝わらない（リハーサルで、営業利益率が1%に届かなかった）。量を増やす計画は、実現できる上限（設備の能力・人手・商圏など）を前提に置き、`MIN(…)` で式に入れる。
- 今の取引の数量（実績）には「数量_」を付けず、計画で増やす分だけを「数量_」にする。道具の「数量が2割少ない場合」は「数量_」の前提を0.8倍にするので、今の数量まで「数量_」にすると、今の売上まで2割減らした厳しすぎる判定になる（リハーサルで、労働生産性が −20% と出た）。
- 量に比例する経費は売上ではなく数量に比例させ、比例しない経費（地代家賃・リース料・保険料など）は決算書の内訳から固定費の前提に分ける（全部を比例させると、利益の増え方を少なく見積もる）。
- 売上と経費の分け方（新事業の行の式、既存事業の伸び）は、社長の話と構想の筋書きから決める。式に使えるのは、前提の名前・`基準_売上` などの基準年度の名前・`年`（基準年度が0、1年目が1）・同じ事業の行の名前・数・`+ - * / ^`・かっこ・ROUND/ROUNDDOWN/ROUNDUP/MIN/MAX。数は前提に置き、式の中に数を書き込まない（1 や 12 のような決まった数は除く）。

```bash
python3 -B "${CLAUDE_PLUGIN_ROOT}/skills/kaku/scripts/zaimu_model.py" build --folder "${CLAUDE_PROJECT_DIR}" --spec 記録/財務モデルの指定.json [--seido 記録/制度データ/<制度>_<回>.json] [--replace] [--json]
```

- 道具は、会社のフォルダの直下に `財務モデル.xlsx`（シートは前提・計画・月次の3つ）を作り、LibreOffice で計算し直して Python の計算と照らす。数値の要件の基準は制度データから読み、様式（別紙4）と同じ計算で判定する。置いたら、数字の控え `記録/財務モデルの数字.json` を書く（計画書との照合に使う。書き換えない）。
- 出力の「数値の要件」と前提を、社長に普段の言葉で伝える（どの指標が何年目にどれだけ伸び、要件のいくつを満たすか）。
- 出力の「数量が2割少ない場合」も伝える。満たさないと出たら、要件を満たせないと返還につながることを伝え、計画を見直すかを社長に決めてもらう。
- 出力の「投資の効果の見え方」（営業利益と営業利益率、営業利益の増加、浮く時間の人件費相当額）を読む。知らせが出たら、そのまま完成に進まず、上の「構想を立てる」に戻って効果を式に入れ直す（構想役に、知らせと今の指定を渡して呼び直してよい）。直した後の営業利益の増加と営業利益率を、社長に伝える。
- 計画書・様式・入力シートに書く数字（売上・付加価値額・伸び率・省力化指数・投資回収期間など）は、この出力か数字の控えから取る。根拠対照表の出典は「財務モデル P-07」（前提の番号）か「財務モデル 合算 売上 5年目」「財務モデル 省力化指数」の形で書く。
- 「境目の知らせ」が出たら、必ず社長に伝える。様式の計算は端数を切り捨てることがあるので、ちょうど基準の計画は、基準をわずかに下回ると判定されることがある。計画の数字を少し上げることを勧める。
- 「特例を選ぶときだけ」の要件は、社長がその特例を選ぶときだけ伝える。「判定しなかった要件」（最低賃金など）は、財務モデルの数字では判定しないので、別に確かめる。
- 財務モデル.xlsx がもうあるときは断られる。作り直すときは、社長が前提のセルを書き換えていないかを確かめ、その値を指定に入れてから `--replace` を付ける（前の版は版の履歴に残る）。
- 「LibreOffice が見つからない」と出たら、確かめずに置いたと伝える（Excel で開くと計算される）。
- 終了コード：0 作った、1 補助プログラムが読めない（プラグインを入れ直すよう案内）、2 しなかった（理由を読み、指定を直す）、3 計算し直すと食い違った（財務モデル.xlsx は置いていない。道具の不具合なので、数字を使わず、作者に知らせる）。

## 様式と入力シートに書く（書式を壊さない）

目的は、公式の様式（Word のその1・2、Excel のその3）と入力シート.xlsx に、書いてよい範囲だけを書き、ほかを1バイトも変えないこと（SPEC F8、DESIGN 5章）。Word・Excel は、Write・Edit やその場のコードで書き換えない。必ずこの道具で書く。その場のコードで書き換えると、応答の終わりの hook が範囲の外の変化を見つけて直前の版に戻す。手順は固定する。

- 様式の入力先が画面の制度（制度データの様式の「入力先」の種類が「画面」。経営計画を申請の画面に入れる制度など）は、計画書の本文も、下の 5 の入力シートの欄（例：画面「経営計画入力（様式２）」の欄「1-1.自社の概要」）に `yoshiki.py sheet` で書く。初稿でも、Markdown や Word の別の文書を作らない（確かめの道具と画面入力の道具が、入力シートを読むため）。書いた文は、応答でも社長に見せる。

1. 様式の項目の「書き込む位置」に「範囲」がなければ、先に対応づける。道具で様式の一覧を出す。

```bash
python3 -B "${CLAUDE_PLUGIN_ROOT}/skills/kaku/scripts/yoshiki.py" outline --folder "${CLAUDE_PROJECT_DIR}" [--case <案件>]
```

2. 読み取り役（yomitori。model は opus）を呼び、一覧の全文と、制度データの様式の項目（名前と「書き込む位置」の「見出し」）を渡して、項目ごとの書き込む位置を JSON で返させる。依頼の文には次を書く。
   - 返す形：`{"様式": "<様式の名前>", "対応": [{"項目": "<項目の名前>", "書き込む位置": {"見出し": "<一覧の段落の文字のまま>", "場所": "<一覧の場所の名前>", "範囲": "見出しの後" か "セル"}}]}`
   - 「見出しの後」：見出しの段落が表のセルの中にあり、その後ろ（セルの終わりまで）に書く項目。「場所」は見出しの段落（例：t4.r2.c0.p0）。
   - 「セル」：見出しが表の前か同じ行の左のセルにあり、そのセルに書く項目（例：（２）事業計画名 → t1.r0.c0）。「場所」は書くセル。
   - 表の欄を持つ項目（「（1）事業者情報」の商号又は名称・代表者役職・氏名など、「1. 事業者の概要」の経営理念・直近実績の各セルなど）は、欄ごとに `{"項目": "<項目の名前>", "欄": "<欄の名前>", "書き込む位置": {"見出し": "<同じ行の左のセルの文字>", "場所": "<書くセル>", "範囲": "セル"}}` を返す。同じ見出しのセルが並ぶ表（直近実績の年ごとの列など）は、欄の名前に列の見出しを添える（例：`売上金額（2025年度）`）。
   - 見出しの後に書く項目の中に、書き込む表がある（「5. 事業の実施体制」の役割分担の表など）ときも、表のセルを欄として返す。欄の名前は「<行>（<列の見出し>）」（例：`1行目（役職）`）、見出しは同じ列の1行目の文字。
   - 月の欄に印を付けるスケジュールの表は、セルごとではなく、表を1つの欄として返す：`{"項目": "<その表を持つ項目>", "欄": "スケジュールの表", "書き込む位置": {"見出し": "<表のすぐ前の段落の文字>", "場所": "<表の場所。例：t5.r0.c0.t0>", "範囲": "表"}}`。
   - 一覧にない場所や文字を作らない。決められない項目は返さず、理由を書く。
   - 様式の Word にある入力の欄は、申請画面にも入れる欄（事業者情報・事業計画名・概要など）でも、すべて対応づけて書く（出す PDF に空の枠を残さない）。制度データの項目にない欄は、`"足す": true` を付けて返す（map が様式の項目として足す）。
3. 返った JSON（`{"様式": "…", "対応": [ … ]}`）を、そのまま Write で `記録/一時/様式の対応.json` に置き、map に渡す。道具が様式と照らして確かめ、合うものだけを制度データに書く。1件でも合わなければ何も書かないので、直す所を読み取り役に伝えて返し直させる。

```bash
python3 -B "${CLAUDE_PLUGIN_ROOT}/skills/kaku/scripts/yoshiki.py" map --folder "${CLAUDE_PROJECT_DIR}" --input 記録/一時/様式の対応.json
```

4. 項目に書く。書く文を Write で `記録/一時/書く文.txt` に置いて渡す（改行で段落を分ける。行の頭の「・」は Word の箇条書きになる。`|` で区切った行が続く所は表になり、直前に `【表：題】` の行を置くと題が付く）。初めてなら、公式資料の様式を写して `案件/<案件>/<段階>/申請書/その1・2.docx` を作る。同じ項目に書き直すと、前の文は置き換わる（前の版は版の履歴に残る）。様式が消すよう求める説明の青字は、その項目の範囲の分だけ消える。

```bash
python3 -B "${CLAUDE_PLUGIN_ROOT}/skills/kaku/scripts/yoshiki.py" write --folder "${CLAUDE_PROJECT_DIR}" --item "<項目の名前>" [--field "<欄の名前>"] --input 記録/一時/書く文.txt
```

   表の欄を持つ項目は、欄ごとに `--field` を付けて書く。様式のすべての項目と欄を書く（書いていない項目と欄は、確かめで空欄に数える）。
   様式に表がある項目は、その表に書く。役割分担の表は人ごとに1行。表の代わりに文章や自作の図にしない（コードの確かめが「様式の表に書いていない項目」を注意に挙げ、審査役が要修正にする）。

   スケジュールの表は、道具が表ごと作る（月の欄に印を付け、A4 横1枚に収める）。審査員が1枚を見て、いつ何をし、いつ効果が出始めるかを読み取れることが目的。行にするのは大きな工程（投資の中身によって、発注・導入・試しの運用・本番・効果の確かめ など）で、細かい作業や申請前の準備は本文に書く。工程と作業の名前に日付を書かず、時期は印で示す（●○◎などの意味は凡例に書く）。

```bash
python3 -B "${CLAUDE_PLUGIN_ROOT}/skills/kaku/scripts/yoshiki.py" schedule --folder "${CLAUDE_PROJECT_DIR}" --item "<スケジュールの表を持つ項目>" --input 記録/一時/スケジュール.json
```

   指定は `{"1年目の始め": "2028-04", "補助事業実施期間": {"始め": "2027-07", "終わり": "2028-03"}, "凡例": "●：実施　◎：本番の開始　○：準備・継続", "行": [{"工程": "1. 要件定義・設計", "作業": "業務の分析と設計", "始め": "2027-07", "終わり": "2027-10", "印": "●"}]}`。期間が2つ以上の行は `"期間": [{"始め", "終わり", "印"}, …]`。1年目は財務モデルの1年目、実施期間は制度データの期間と本文の日付に合わせる。1枚に収まらないと道具が断るので、行をまとめるか名前を短くする。作った後に PDF の写しで1枚かを見る。

   - 書き方は任せる（作者の方針）。渡すのは目的だけ：業界の外の審査員が読んで、この会社の課題、なぜこの投資なのか（ほかの手ではなく）、効果がどう組み立てられているか、本当に実行できるか、が納得できること。そのために、見出しの立て方、項目の中の順番、文の長さと形、表と文章の使い分けは、項目ごとに最もよく伝わる形を自分で選ぶ。社長が自分の会社のことを話しているように、その会社の出来事と言葉で書く。
     - 守ること（ここはゆるめない）：事実と数字は会社の記録・書類・社長の答え・財務モデルと、出典つきの公的な統計・公募要領にあるものだけ。資料にない事実を足さない。様式の欄と上限、様式の表を守る。どの会社にも当てはまる段落を書かない。
     - 長さは字数で決めず、読み手と目的から自分で決める。読み手は、書面だけで採点する業界の外の審査員で、分量では採点しない（公募要領）。項目ごとに、審査項目と観点の問い（この会社の課題は何か、なぜこの投資か、効果の数字はどう組み立てたか、本当に実行できるか、失敗したらどうするか）に、会社の事実と根拠（実測・書類・計算・統計）で答え切った所が終わり。答え切れていなければ、言葉ではなく事実と根拠を足して厚くする（足りない事実は社長に聞くか、書類を頼む）。どこを厚くするかは、制度の審査項目の重みで決める。図や表のほうが伝わる所は図表にし、本文はその読み方を書く。様式に字数がある欄（事業計画名の30字程度など）だけは、その字数に合わせる。
     - 文体の注意（60字・100字を超える文、文体の基準 B の避ける言い回しなど）は読みやすさの目安で、完成を止めない（作者の決定）。合わせるための書き直しは要らず、自然に言い換えられる所だけ直す。審査役やコードの指摘で直すときも、指摘の文言をなぞって1文を差し込まず、伝わるように段落ごと書き直す。

   - 図表と写真（SPEC F8・T8-3）：審査員が文章より早く分かる所（比べ・内訳・推移・流れ・役割・現場の様子）は、図か表にする。どれをどこに幾つ置くかは Claude が決め、書く文の中に1行で置く。
     - 図：`【図：推移｜売上・営業利益】`（財務モデルの行を1〜3つ選んで、基準年度と計画の年ごとの棒。選べる行は道具が示す）、`【図：数値計画】`（付加価値額・労働生産性・1人当たり給与支給総額）、`【図：前後比較】`（制度ごとの注にあるとき）、`【図：工程表】`（様式にスケジュールの表がないときだけ）。
     - 写真：`【写真：原本/写真・カタログ/<ファイル>.jpg｜題】`（会社のフォルダの中の PNG か JPEG）。
     - 表：`【表：題】` の行の後に `|` で区切った行を並べる（1行目が見出し）。比べた手、経費の内訳、効果の内訳、役割の分担、リスクと手当てなど。
     図表の要点（何がどれだけ変わるか など）は本文にも書く。
   - 図の数字は、道具が財務モデルの数字の控えから取る（Claude は図の数字を書かない。先に財務モデルを作る）。表の数字は本文と同じく根拠対照表に残す。
     工程表は、`{"工程表": {"題": "…", "行": [{"作業": "発注", "始め": "2027-07", "終わり": "2027-07"}]}}` を Write で
     `記録/一時/図表.json` に置き、`--figures 記録/一時/図表.json` で渡す。月は、本文と根拠対照表にある日付と同じにする。
   - 道具は図をセルの幅に収めて入れる。図を作るのに LibreOffice が要る。終了コード2で「図を作れなかった」と出たら、
     理由（財務モデルがない、工程表の月の形 など）を直すか、図を置く行を外して書き直す。書き直すと、前の図は片付く。

4b. 様式を書き終えたら（完成の記録の後、提出の前）、PDF の写しを作る。提出の形式が PDF の様式（その1・2）は、この写しを添付する。

4c. Excel の様式（省力化のその3 など。様式ごとの値の取り方は、制度ごとの注に従う）に書く。書いてよいのは、様式が入力の欄として開けているセル（保護したシートのロックを外したセル）だけ。まず一覧を出す。

```bash
python3 -B "${CLAUDE_PLUGIN_ROOT}/skills/kaku/scripts/yoshiki.py" outline --folder "${CLAUDE_PROJECT_DIR}" --excel
```

   一覧の見出しと「書いてよいセル」から、項目ごとのセルを決め、`{"値": [{"シート": "<シートの名前>", "セル": "C6", "値": 22500000}]}` を Write で `記録/一時/その3の値.json` に置いて渡す。初めてなら、公式資料の様式を写して `申請書/その3.xlsx` を作る（開いたときに計算し直す設定を付ける）。

```bash
python3 -B "${CLAUDE_PLUGIN_ROOT}/skills/kaku/scripts/yoshiki.py" cells --folder "${CLAUDE_PROJECT_DIR}" --input 記録/一時/その3の値.json
```

   - 数字は財務モデルの道具の出力（数字の控え）から取る。数式のセルには書かない（道具が計算し直して値を保存する）。
   - 様式に初めから入っている例の値（事業計画年数・成長率・算定根拠の例の文など）は、すべて会社の値で書き直す。
   - 1件でも書けない値（数式のセル、入力の欄でないセル、結合の左上でないセル）があれば何も書かないので、出た理由を直して渡し直す。

   - 一覧の見出しに「（凡例：…）」と付いたセルは、色で入力の欄を示す凡例で、書けない。説明は、同じ色の「書いてよいセル」に書く。
   - 道具は、書いた後に数式のセルの値を LibreOffice で計算し直して、ファイルに保存する（数式と書式は変えない）。「計算し直せませんでした」と出たら、社長に伝える。出力の「計算の結果がエラーのセル」に入力のシートのセル（別紙4 など）があれば、空いている入力の欄を確かめる。書いた後に、前に作った Excel の様式の値だけを計算し直すときは次の道具を使う。

```bash
python3 -B "${CLAUDE_PLUGIN_ROOT}/skills/kaku/scripts/yoshiki.py" recalc --folder "${CLAUDE_PROJECT_DIR}" [--file <申請書の Excel のファイル名>]
```

5. 入力シートの欄に書く。初めてなら、制度データの申請画面から `申請書/入力シート.xlsx` を作る。担当者が入れる欄（確認・誓約のチェックなど）には書かない。上限（目安でないもの）を超える値は断られるので、短くする。数字の欄は数で渡す。

```bash
python3 -B "${CLAUDE_PLUGIN_ROOT}/skills/kaku/scripts/yoshiki.py" sheet --folder "${CLAUDE_PROJECT_DIR}" --field "<欄の名前>" --value "<値>"
```

   欄が多いので、画面ごとなどにまとめて書く（1件でも書けなければ何も書かないので、出た直す所を直して渡し直す）。
   `{"値": [{"画面": "<画面の名前>", "欄": "<欄の名前>", "値": "<値>"}]}` を Write で `記録/一時/入力シートの値.json` に置いて渡す。

```bash
python3 -B "${CLAUDE_PLUGIN_ROOT}/skills/kaku/scripts/yoshiki.py" sheet --folder "${CLAUDE_PROJECT_DIR}" --values 記録/一時/入力シートの値.json
```

- 会社に当てはまらない欄（選ばない加点や特例の欄、支援者がいないときの支援者の欄、出さない書類の添付の欄など）には `該当なし` と書く（チェック欄は「いいえ」）。数字の欄にも書ける。画面入力の道具は、この欄を画面に入れない。当てはまるか分からない欄は、推測で `該当なし` にせず、社長に聞く。
- 添付の欄の値は、添付する書類の、会社のフォルダからの場所を書く（原本の置き場の書類か、申請書のファイル。画面に添付するのは、段階のフォルダの `添付する書類/` の写し）。
- 支援者の欄（省力化の「事業計画書作成支援者情報」、持続化の「第三者からのアドバイスの有無」など）には、道具が入力シートの「案内」の列に、このツールは支援者に当たらないことの案内を入れる（SPEC 2.3）。道具が出した案内を、そのまま社長に伝える。人の支援者（コンサルタントなど）が計画書づくりに関わったかを社長に聞き、関わっていれば正直に書く。関わっていなければ、支援者が関与していないことを示す欄を「はい」、ほかの支援者の欄を `該当なし` にする。

- 計画書と入力シートの数字は、財務モデルの道具の出力から取る（Claude が計算しない）。
- 終了コード：0 書いた、1 補助プログラムが読めない（プラグインを入れ直すよう案内）、2 しなかった（理由を読んで直す。書き込む位置が見つからないときは、社長が見出しを書き換えていないかを確かめ、対応づけし直す）、3 書くと範囲の外が変わるので保存しなかった（ファイルは前のまま。道具の不具合か様式の想定違いなので、作者に知らせる）。

## 確かめる（コードの確かめ → 審査役 → 完成の記録）

目的は、書いた本人の思い込みを持ち込まずに申請書を確かめ、条件をすべて満たしたときだけ完成にすること（SPEC F9、DESIGN 8章）。完成かどうかは Claude が決めず、道具が決める。

1. 書きながら、本文に書いた数字・固有名詞・日付と出典を、根拠対照表に残す。本文には出典を書かない。出典は、書類とページ、社長の答えと日付、会社の記録の項目、財務モデルの前提の番号など。
   `{"行": [{"記述": "<本文に書いた数字など>", "種類": "数字", "書いた場所": "<様式の項目>", "出典": "<出典>"}]}` を Write で `記録/一時/根拠.json` に置いて渡す。

```bash
python3 -B "${CLAUDE_PLUGIN_ROOT}/skills/kaku/scripts/kakunin.py" konkyo --folder "${CLAUDE_PROJECT_DIR}" --input 記録/一時/根拠.json
```

   - 本文の数字（単位つき）・日付・固有名詞（会社の名前など）は、1つ残らず根拠対照表に行を作る。記述は本文の文字のまま書く（「月に約120件」など）。「1日に」「1パックあたり」のような書き方は要らない。
   - 財務モデルから取った数字の出典は、頭を「財務モデル」にして、前提の番号（`財務モデル P-07`）か、`財務モデル 合算 売上 5年目`・`財務モデル 労働生産性の伸び 5年目`・`財務モデル 省力化指数` の形で書く。道具がこの出典の数字を、数字の控えと照らす。
2. コードで確かめる（費用はかからない）。仮の印（【仮：…】、財務モデルなどの「状態」が仮の行）、空欄（【空欄：…】、まだ何も書いていない様式の項目と欄、入力シートの空の値）、根拠対照表の出典のない行、根拠対照表にない本文の数字・日付・固有名詞、表の記述が本文にない行（食い違い）、本文に書いた出典、財務モデルとの食い違いを数える。

```bash
python3 -B "${CLAUDE_PLUGIN_ROOT}/skills/kaku/scripts/kakunin.py" count --folder "${CLAUDE_PROJECT_DIR}"
```

   - 残っていれば、直して数え直す。このときは審査役を呼ばない。仮の印・空欄・出典が分からないものは、社長に聞く（3つまで、理由を添えて）。推測で埋めない。
3. 通ったら、審査役に渡すものをまとめる。通らないときは何もまとめないので、審査役を呼ばない。

```bash
python3 -B "${CLAUDE_PLUGIN_ROOT}/skills/kaku/scripts/kakunin.py" prepare --folder "${CLAUDE_PROJECT_DIR}"
```

   - その3 の数式のセル（省力化指数・投資回収期間など）は、道具が LibreOffice で計算し直した写しから値を渡す（様式のファイルは変えない）。「数式の値は計算し直せなかった」と出たら、そのまま審査役を呼び、社長にも伝える（Excel で開いて保存すると直る）。

4. 審査役（subagent の `hojokin:shinsa`）を呼び、出力にある依頼の文（確かめの番号と `記録/審査に渡すもの/`）をそのまま渡す。書いたときの考えや、自分の見立ては渡さない。審査役の報告は、hook が本体を通さずに `記録/審査役の結果/<確かめの番号>.json` に保存する。Claude はこのフォルダを書き換えない。
5. 審査役が終わったという知らせを待ってから、保存された結果を読む。auto モードでは、審査役が裏で動き、知らせの前に一度応答を終えることがある。「まだ届いていません」と出たら、知らせを待って読み直す。道具が審査役の結果の「そろい具合」を数えて出すので、そろっていなければ、足りない所を伝えて審査役を呼び直す（呼んだ回数に数える）。点数は参考として社長に見せるだけで、完成かどうかには使わない。

```bash
python3 -B "${CLAUDE_PLUGIN_ROOT}/skills/kaku/scripts/kakunin.py" result --folder "${CLAUDE_PROJECT_DIR}"
```

6. 要修正の指摘を直し、2 に戻る（直したら、前の結果は使えない）。要修正がなければ、完成の記録を残す。道具が、コードの確かめ、今の版を確かめた審査役の結果、要修正0件をコードで確かめてから残す。要確認と助言の指摘は、社長に示し、直すかを決めてもらう。

```bash
python3 -B "${CLAUDE_PLUGIN_ROOT}/skills/kaku/scripts/kakunin.py" finish --folder "${CLAUDE_PROJECT_DIR}"
```

- 途中でやめて社長に返すとき：社長の答えや判断が要る指摘が出た（すぐ返す。審査役を呼び直さない）、文章を直しても通らない（数値の要件を満たさない など）、審査役を3回呼んでも要修正が残る、同じ指摘が2回続く、コードの確かめを直す繰り返しが5回を超えた。返すときは、直したこと、残った指摘と直し方の案、質問（3つまで、理由を添えて。【質問】の形か選択肢の画面）を示す。
- 回数と、社長の答えが要るかは、道具が `.hojokin/一時/確かめの回数.json` で数える。count・prepare・result の出力に「社長に返します」と出たら、そこで止めて社長に返す。prepare は、社長に返す理由があるあいだ審査役に渡すものをまとめない（終了コード3）。
- 社長の答えをもらって直した後は、回数を数え直す（質問の記録に新しい答えが入ると、道具が数え直す。また3回まで呼べる）。
- 完成の記録は、要修正0件に加えて、審査役の筋立てに切れ目がなく（4つの段がそろう）、目安のない項目に「足りない」「長すぎる」がないときだけ残る。分量の目安（「30字程度」など）は、目安の半分から2割増しまでの範囲（仮）を道具が数える。
- 終了コード：0 した、1 補助プログラムが読めない（プラグインを入れ直すよう案内）、2 しなかった（理由を読んで直す）、3 通らない（count・prepare はコードの確かめが通らない、result はまだ届いていない、finish は完成の条件を満たさない。出た理由を直す）。

## 経費明細

目的は、経費明細の金額が、照合を通った見積書の金額と1円も違わず、メモや聞き取りからの金額には仮の印が付き、補助の対象にならない経費が「要確認」として資料のページ付きで示されること（SPEC F8、DESIGN 8.4）。財務モデルの投資額と減価償却費も、ここから取る。

1. 見積書が照合を通っているかを確かめる。shorui の skill を呼び、その「金額の照合」の `show` で見る（shorui の道具は、shorui の skill から動かす）。照合していない見積書・経費のメモが入れ口などにあれば、先に shorui の手順（整理、金額の照合）で原本にし、照合する。終わったら、この skill を呼び直して続ける。
2. 使う見積書を決める。頼むつもりの会社の、いちばん新しい正式な見積書を使う。相見積（比べるためのもの）、置き換わった概算、有効期限が切れた見積書の金額は入れない。メモ・会社の記録・社長の答えで、どれを使うかを確かめる（分からなければ聞く）。
3. 行を作る。見積書の行は、見積書の明細（税抜の金額）をそのまま使い、明細の番号を書く（まとめるときは番号の一覧にし、金額はその和）。メモ・聞き取りからの金額は、根拠を「メモ」「聞き取り」にする（道具が「仮」にする）。数字の欄には文字を入れない。
4. 経費の区分を、制度データの「補助の対象になる経費」に照らして決める。「補助の対象にならない経費」に当たりそうなもの・迷うものは、明細から外さずに「要確認」の行として残し、わけと資料のページを書く（外すかは社長が決める）。資料に書かれていなければ、問い合わせ文の案を作る。
5. 行を Write で `記録/一時/経費明細.json` に置き、道具で残す。外れがあれば、出た理由を読んで直し、もう一度流す。
   ```bash
   python3 -B "${CLAUDE_PLUGIN_ROOT}/skills/kaku/scripts/keihi.py" save --folder "${CLAUDE_PROJECT_DIR}" --case "<案件>" --input 記録/一時/経費明細.json
   ```
   形：`{"行": [{"経費の区分": "機械装置・システム構築費", "品名": "…", "型番": "…", "数量": 2, "単位": "台", "単価": 3900000, "金額": 7800000, "根拠": "見積書", "原本": "<見積書の原本の場所>", "明細の番号": 1, "出典": "<見積書の番号と日付>"}, {"品名": "…", "数量": 1, "単価": 100000, "金額": 100000, "根拠": "メモ", "原本": "<メモの原本の場所>", "出典": "<メモのどこか>", "要確認": {"わけ": "…", "資料のページ": "要領8 p.23"}}]}`
6. 社長には、行ごとの金額・根拠・仮の印・要確認と、合計（見積書から・仮・要確認）を一覧で示す。仮の行は、見積書がそろったら差し替えることを伝える。使わなかった見積書と、そのわけも伝える。

- 道具の出力「合計」の「見積書から」と「仮」を、財務モデルの投資額に使う（要確認の行は入れない）。
- 終了コード：0 残した、1 補助プログラムが読めない、2 残さなかった（照合していない見積書、金額の食い違い、期限切れの見積書、要確認に資料のページがない など。理由を読んで直す）。

## 差し戻しへの対応（F12）

「差し戻された」「事務局から直すように連絡が来た」と言われたら（差し戻しの文面を貼り付けられたとき、画面の写真を入れたときも）、提出版と照らして箇所を特定し、直して確かめ直す。進め方はこの skill の別ファイル（差し戻し.md）にあり、道具の出力で読む。

```

1. 差し戻しを原本にする（貼り付けた文面は Write で `入れ口/<受け取った日>_差し戻し.txt` に置き、shorui の整理で原本にする。写真も同じ）。終わったら、この skill を呼び直す。

```

- 終了コード（sashimodoshi.py）：0 出した、1 補助プログラムが読めない、2 しなかった（提出版がない など。担当者が出したときに kiroku で提出版を残していなければ、照らせないことを伝える）。

## 採択後：交付決定の前の発注と、実績の比較（F12）

**交付決定の前の発注・契約（事前着手）**：交付決定の通知が届く前に「もう発注してよいか」「契約だけ先にしてよいか」と聞かれたら、交付決定より前の発注・契約・支払いは補助の対象外になると、言い切って強く伝える（「〜かもしれません」と弱めない）。業者に急かされていても同じ。交付決定の通知が届き、その日付を junbi で残してから発注するよう勧める。見積の依頼や相談は発注・契約に当たらないので、進めてよいことも添える。

1. 交付決定の日は、原本の置き場の交付決定の通知と、開いたときの期限の一覧（junbi の期限の道具。junbi の skill から動かす）で確かめる。通知がなく、台帳にも交付決定の日がなければ、交付決定の前とみなす。推測で「もう決まっているはず」としない。
2. 根拠は、制度データの「してはいけないこと」（事前着手）と、手続きの段階の「始まる条件」の出典（資料名とページ）で示す。

**実績の比較（実績報告・効果報告）**：実績を財務モデルに入れて計画と比べ、満たせない要件は返還の条件と一緒に伝える。比べる計算は道具が行う（Claude は計算しない）。

1. その年の実績（決算書の数字。基準年度と同じ9つ：売上・原材料費・給与支給総額・その他の人件費・減価償却費・その他の経費・役員数・常勤従業員数・給与を受けた従業員数）を、決算書と名簿から集める。決算書の科目の足し上げは、上の「基準年度の値を決算書から足し上げる」の kijun と同じ形で道具に任せてよい。
2. 実績を Write で `記録/一時/実績.json` に置く。形：`{"年": 1, "実績": {"売上": {"値": 205200000, "根拠": "決算書", "出典": "第19期の決算書 p.2"}, …}}`（年は事業計画の何年目か）。
3. 道具で比べる。目標値（応募のときに自分で定めた1人当たり給与支給総額の伸び）は提出版の計画書から、交付額は交付決定通知書（か確定の通知）から取って渡す（分からなければ渡さない。推測で入れない）。
   ```bash
   python3 -B "${CLAUDE_PLUGIN_ROOT}/skills/kaku/scripts/zaimu_model.py" compare --folder "${CLAUDE_PROJECT_DIR}" --spec 記録/財務モデルの指定.json --actual 記録/一時/実績.json --target <要件の率> --grant <交付決定額>
   ```
4. 結果の表（行ごとの計画・実績・差）と、要件ごとの判定を、そのまま伝える。「満たさない」「届かない見込み」の要件は、返還の条件（出典つき）と、届くのに要る残りの年の伸び、返還額の目安（出たとき）を添える。返還の条件が資料から読み取れないと出たら、そのまま伝え、事務局への問い合わせ文の案を作る。
5. 残りの年の計画（賃上げなど）をどうするかは、社長と相談する。財務モデルの指定は、社長の了承を得てから直す。

- 終了コード：0 比べた（満たさない要件があっても 0）、1 補助プログラムが読めない、2 しなかった（実績の形が違う、9つの値が足りない、会社のフォルダの外の場所 など）。
