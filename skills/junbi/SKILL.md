# 案件の準備と、制度の質問・期限・改訂（F3、F4、F6、F7、F12 の手続きの切り替え）

## 最初に目印を確かめる

- 最初に、今のフォルダに `.hojokin/`（会社のフォルダの目印）があるかを確かめる。
- 目印がなければ、ほかのことをせずに「このフォルダを〇〇社の会社のフォルダにしますか」と社長に聞く。
- 社長が了承したら、会社のフォルダを作る道具で用意してから進める。了承がなければ、何も書かずに終える。
- この skill の道具が「別名（シンボリックリンク）になっている」「会社のフォルダの外を指しています」と出して断ったら（終了コード 2。何も書いていない）、
  別名の先は会社のフォルダの外のこともあるので、ほかの道具やその場のコードで読んだり書いたりしない。出力の場所を社長に伝え、
  本物のフォルダやファイルに置き換えてもらってから、もう一度流す。

## 道具の動かし方（どの手順にも共通）

- 社長の答えを受けて続けるとき（新しい発言のたび）、読み取り役から戻った後、会話を開き直した後は、道具を動かす前にこの skill を呼び直す（呼び直さないと、道具が確かめの画面で止まることがある）。
- 道具に渡す JSON は、Write で `記録/一時/<決まった名前>.json` に置き、その場所を `--input`・`--list`・`--apply` で渡す。標準入力（`<<'EOF'`）では渡さない（会社のフォルダの設定で、確かめの画面が出るため）。ファイルは消さず、同じ名前で上書きする。
- その場の計算のコードが要るときも `記録/一時/` に置く。`python3 -c`・パイプ・sed は使わない。

## 公式資料を取り、書類フォルダを作る（F3）

申請する制度と回が決まったら、最初に公式資料を取る。取るのも、置くのも、文字にするのも道具が行う。

1. 公式サイトのダウンロードのページで、公募要領・様式・手引き・電子申請マニュアル・スケジュールのページの場所を確かめる。
   申請する回の資料がまだ公表されていなければ、直近回の資料を使う（推測で次の回の場所を作らない）。
2. 取る資料の一覧を用意する。
   - 省力化（一般型）第8回・第9回と持続化（一般型・通常枠）第20回は、同梱の一覧がある：
     `${CLAUDE_PLUGIN_ROOT}/skills/junbi/取る資料/省力化_一般型_第9回.json`（第9回の資料がまだない様式・手引きは第8回のもの）、
     `${CLAUDE_PLUGIN_ROOT}/skills/junbi/取る資料/省力化_一般型_第8回.json`、`${CLAUDE_PLUGIN_ROOT}/skills/junbi/取る資料/持続化_通常枠_第20回.json`
   - ほかの制度は、同じ形で作る。「制度」に名前・略称・枠・種類（補助金か助成金）・公募回（申請する回）を、「資料」に資料ごとの id（短い呼び名。出典に使う）・名前・公募回（その資料そのものの回）・URL を書く。
3. 道具を動かす。申請する回が一覧の回と違うとき（第9回の申請を第8回の資料で始めるときなど）は、`--case-round` に申請する回を渡す。
   一覧を作ったときは、`記録/一時/取る資料.json` に置き、`--list 記録/一時/取る資料.json` で渡す。
   すでに始めた案件の資料を取り直すとき（公表された回の資料を取る、採択後の手引きを取る、改訂を確かめる など）は、
   前の `記録/資料の本文/<案件>/資料の一覧.json` の「案件」を `--case` に渡す。年が変わっていても、同じ案件のフォルダに置くため。
   `--case` を渡さなくても、同じ略称・枠・回の案件のフォルダが1つあれば、道具はそれを使う。

```
python3 -B "${CLAUDE_PLUGIN_ROOT}/skills/junbi/scripts/fetch_documents.py" --folder "${CLAUDE_PROJECT_DIR}" --list "${CLAUDE_PLUGIN_ROOT}/skills/junbi/取る資料/省力化_一般型_第8回.json" --case-round 第9回
```

4. 道具の結果を、社長に平易に伝える。
   - 「直近回である第◯回の資料に基づいています」と出たら、必ずそのまま伝える。回の違う資料（第6回版の手引きなど）も伝える。
   - 終了コード 1 は、そろっていない資料がある。取れなかった資料は、ダウンロードのページで場所を確かめ直して取り直す。「前と中身が違う」資料は、改訂かもしれないと社長に知らせる（道具は上書きしない）。
   - 終了コード 2 は、何もしていない（会社のフォルダでない、一覧の形が違う、案件のフォルダを決められない、書く先が別名になっている）。
     同じ制度・枠・回の案件のフォルダが2つ以上あると出たら、どの案件かを確かめて `--case` に渡して動かし直す。
5. 道具が作るもの
   - 書類フォルダ：`案件/<年>_<略称>（<枠>）<申請する回>/`（年は案件を始めた年）と、その中の `公式資料/`（読み取り専用。書き換えない）。段階のフォルダは、制度データを作った後に、その手続きの段階から作る。
   - ページごとの文字：`記録/資料の本文/<案件>/<資料の id>/`。`ページ_001.txt`（PDF のページごと。1行目に印刷されたページ番号）と `ページの対応.json`。出典は、いつも印刷されたページ番号で示す。文字のないページ（画像だけのページ）は、ページの対応の「文字を取り出せないページ」にある。
   - 資料の一覧：`記録/資料の本文/<案件>/資料の一覧.json`。制度データの「資料」と同じ形（id・名前・公募回・URL・取得日・ハッシュ・ページのずれ）で、制度データを作るときにそのまま使う。

## 制度データの下書きを、読み取り役に章ごとに読ませ、道具で裏取りする（F3）

公募要領は、本体では読み込まない（文脈を守るため）。読み取り役（subagent `hojokin:yomitori`）に章ごとに読ませ、返った JSON を道具で裏取りする。

1. 章を決める。公募要領の目次のページ（`記録/資料の本文/<案件>/<資料の id>/` のはじめの数ページ）を見て、章とページの範囲（印刷されたページ番号）を決める。一度に全部を読ませない。
2. その章で読む項目の形を、道具で出す（項目は制度データの項目の名前。いくつ並べてもよい）。

```
python3 -B "${CLAUDE_PLUGIN_ROOT}/skills/junbi/scripts/urakadori.py" --form 補助額 補助の対象になる経費
```

3. 読み取り役を呼ぶ。公募要領と様式を読ませるときは、モデルに **opus** を指定する（DESIGN 7章）。渡すのは、案件の名前、資料の id、章とページの範囲、読む項目、2. の形。
   章の名前は、公募要領の見出しのとおりにする（「_v2」「最終」などを付けない。付けると道具は何も書かない）。
4. 返った JSON を、そのまま Write で `記録/一時/読み取り.json` に置き、道具に渡す（道具は会社のフォルダの外のファイルを読まない）。

```
python3 -B "${CLAUDE_PLUGIN_ROOT}/skills/junbi/scripts/urakadori.py" --folder "${CLAUDE_PROJECT_DIR}" --case "<案件>" --input 記録/一時/読み取り.json
```

   置き場所は道具が決める。章ごとの結果は `記録/制度データ/読み取り/<案件>/<章>_<回目>回目.json`、
   制度データの全体（「スキーマの版」があるもの）は `記録/制度データ/<制度の略称>_<公募回>.json`。ほかの場所には書けない。
5. 道具の結果で次を決める。
   - 終了コード 0：形が合い、どの値も裏取りで外れなかった。
     「照らせる値がありませんでした」と出たら、どの値も読み取れなかった。合っていたのではないので、読み取れない項目として社長に伝える。
   - 終了コード 1：裏取りで外れた値を「要確認」にした（理由は注記と結果の表にある）。次のように読み直す。
     1. 外れた値のある項目（「補助額」など）を、読み取り役にもう一度読ませる。その項目は区分も件も**全部**返させる（一部だけ返すと、残りが消える）。根拠の文はページの文字のとおりに写させる。
        読み直させるときも、はじめの依頼と同じ決まり（読むページの範囲、段階のフォルダの名前、読み取れなかった項目の書き方など）を渡す。渡さないと、はじめの依頼で守れていたことが崩れる。
     2. 返った JSON を、同じ章の名前・同じ回目のまま道具に通す。道具は、この章の前の結果のうち、渡された項目だけを差し替え、ほかの項目は残して、章の全体を照らし直す（結果に、差し替えた項目と残した項目が出る）。
        差し替えで件数が減ったら（「手続きの段階（12件 → 8件）」など）、抜けた件がないかを確かめ、抜けていれば、前の件数を伝えて全部を読ませ直す。
        件数が同じでも、前の件が別の件に入れ替わることがある。前の結果の件の名前と照らし、抜けた件があれば、件数だけでなく前の件の名前を並べて渡す。
     3. 前の結果のファイルを Claude が書き換えて通し直さない。直した値も、読み取り役に読ませて渡す。
     4. 直らなければ、要確認のまま社長に示す。
   - 終了コード 2：何も書いていない。形が合わないときは、結果に出た誤りの一覧を読み取り役に渡し、返し直してもらう。
     形にない欄（中身が null の見慣れない欄など）が混ざっただけなら、前に返した JSON と誤りの一覧を渡し、資料を読み直さずに直させてよい。
     章の名前に版の名前の語があると出たら、章の名前を見出しのとおりにして通し直す。
   - 終了コード 3：補助プログラムが動かないか、裏取りの途中で止まった。外れた値があるという意味ではない。結果に出た案内のとおり、プラグインを入れ直すか公式資料を取り直してから、もう一度通す。
   - 推測で埋めない。読み取れない項目は空けたまま社長に伝え、問い合わせ文の案を作る（F3）。

## 章ごとの読み取りを1つの制度データにまとめ、段階のフォルダを作る（F3）

公募要領の全部の章（申請・審査・採択後の手続きの章を含む）と、手続きの段階・期日・様式・申請画面に関わる資料
（スケジュールのページ、応募申請の手引き、電子申請マニュアル、様式、交付申請・実績報告の手引き）を読ませ、
どの章も裏取りの道具で終了コード 0（か、直せない値を要確認のまま）にしてから、まとめる。

- 手続きの段階は、申請から採択後までを全部読ませる。書類を出す段階にだけ、段階のフォルダの名前を「フォルダ」に書かせる（「1_申請」「2_交付申請」の形。DESIGN 4.5）。
  番号は、書類を出す段階だけを順に 1 から数える。道具は、1 から順になっていない名前（いちばん前が「2_採択発表」など）のフォルダを作らない。
- 読み取れない項目は「読み取れなかった項目」に、理由と問い合わせ文の案を付けて入れさせる（項目の名前は、まとめの結果の書き方に合わせる）。
- 書類の「手続き」には、使う手続きの段階の id（「応募申請」など）を書かせる。「1_申請」のようなフォルダの名前にしない
  （概要と流れ.docx で、どの手続きの書類か分からない書類になる）。書類を読む章と手続きの段階を読む章が別なら、段階の id を渡して読ませる。
- 申請画面（入力シートと、画面入力の守りの「押してよいボタン」のもと。F10、DESIGN 5章・9章）は、電子申請マニュアルの
  画面ごとのページを**全部**読ませる（流れのページだけでは、欄もボタンも空になり、入力シートが作れず、守りが一時保存も次へも拒む）。
  - 申請の手続きの章とは別の呼び出しで、「申請画面」だけを読ませる（量が多いため）。章の名前は申請の手続きの章と同じ、回目も同じにして
    裏取りの道具に通す（道具は、その章の前の結果の申請画面だけを差し替え、ほかの項目は残す）。ほかの章には申請画面を読ませない。
  - 渡すのは、マニュアルの資料の id と、流れのページから画面の確認のページまでの範囲（省力化の第8回なら 電子申請マニュアル8 の p.6〜28）。
    欄とボタンは画面の絵にあるので、PDF のページを画像として読ませる（読み方と、欄・ボタンの決まりは、読み取り役の指示にある）。
  - まとめた後、`--check` の結果の「欄も押してよいボタンもない申請画面」が1以上なら、その画面のページを渡して、申請画面を全部読ませ直す。
- **重要な項目の2回目の読み取り**（SPEC F3「2回独立に読み取り、食い違えば要確認」）：締切・補助上限・補助率・数値の要件・必須書類・
  補助の対象にならない経費を含む章は、1回目の裏取りを終えた後に、読み取り役（opus）をもう一度、**別の呼び出しで初めから**読ませる。
  - 渡すのは、1回目と同じ章の名前・ページの範囲と、重要な項目だけ（`urakadori.py --form` で出した形）。「2回目」と伝え、「回目」を 2 にさせる。
    1回目の結果は見せない（独立に読ませるため）。重要な項目のない章（審査項目・様式・申請画面など）は、2回目を読ませない（費用を抑える）。
  - 返った JSON を `記録/一時/読み取り.json` に置き、1回目と同じく `urakadori.py --input` に通す（道具が `記録/制度データ/読み取り/<案件>/<章>_2回目.json` に置く）。
  - まとめる道具が、1回目と2回目を突き合わせ、食い違った値を要確認にする（値の中の数を比べる。言い回しの違いは見ない）。
    結果の「2回の読み取りで食い違った値」は、その項目を読み取り役に読み直させるか、要確認のまま社長に示す。

```
python3 -B "${CLAUDE_PLUGIN_ROOT}/skills/junbi/scripts/seido_data.py" --folder "${CLAUDE_PROJECT_DIR}" --case "<案件>" --merge
```

1. 道具が、章ごとの結果（1回目）を章の順にまとめ、「制度」「資料」を資料の一覧から入れ、2回目の読み取りと突き合わせ、全体を裏取りし直して
   `記録/制度データ/<制度の略称>_<公募回>.json` に置く。公募回は、制度データを作った資料の回（第9回の申請を第8回の資料で始めたときは第8回）。
   どの章も読んでいない項目は空けたまま「読み取れなかった項目」に入る。2回目の読み取りは値には使わず、突き合わせだけに使う。
   2回目がまだなければ、結果に「重要な項目の2回目の読み取り：まだありません」と出るので、上の手順で読ませてから、まとめ直す。
2. 続けて確かめた結果を出す：形（スキーマ）、重要な項目（締切・補助上限・補助率・数値の要件・必須書類・補助の対象にならない経費）が
   値か「要確認」で埋まっているか、出典のない値の数。形が合えば、いちばん前の段階（1_申請）のフォルダを作る。
   重要な項目のうち任意の欄（数値の要件の計算式・元の数字の決め方・満たせないとき、必須書類の有効期限・期数、
   補助の対象にならない経費の上限・例外）が「読み取れない」のものは、埋まっていないに数えず、「任意の欄で読み取れない値」として出る。
   必須の欄（締切の日時、補助額の上限・補助率、数値の要件の基準、必須書類と経費の内容など）の「読み取れない」は、埋まっていないに数える。
3. 道具の結果で次を決める。
   - 終了コード 0：形が合い、重要な項目はすべて埋まり、出典のない値は0件。読み取れない値と要確認の値は、社長に一覧で示し、
     問い合わせ文の案を添える。
     - 「任意の欄で読み取れない値」は、資料に書かれていないこととして空けたまま社長に伝え（「満たせないときの扱いは、資料には書かれていません」など）、
       事務局への問い合わせ文の案を作る。推測で扱いを決めない。
     - 「同じ項目の問い合わせ文の案がまだないもの」は、その値の理由（制度データの「理由」）をもとに、Claude が問い合わせ文の案を作って社長に示す。
       同じことを別の名前で書いた「読み取れなかった項目」に問い合わせ文の案があれば、それを使う。制度データの JSON は Claude が書き換えない
       （その章を読み直させるときは、読み取り役に問い合わせ文の案も付けさせる）。
   - 終了コード 1：制度データは置いたが、足りないところがある（結果の一覧）。1件もない重要な項目や、埋まっていない値は、
     その章を読み取り役に読ませ直し、裏取りの道具に通してから、もう一度まとめる。直せなければ、空けたまま社長に示す。
     「（値が空）」は、読み取り役が「読み取れない」にせず、空の値を確認済みで返したもの。その項目を読ませ直し、資料にないなら「読み取れない」にして理由を書かせる。
     「手続きの段階・様式に当たらない名前」が出たら、その書類（または手続きの段階）を読んだ章を、結果に出た「当たる名前」の一覧を渡して読ませ直す。
     書類の「手続き」は段階の id に、段階の「様式」は様式の名前に合わせさせる（一覧にない様式は、書類の「形式」か段階の「注意」に残させる）。
     同じ書類を2つの章が読んでいたら、どちらの章で読むかを決め、もう一方の章にはその書類を入れないよう伝えて読ませ直す。
   - 終了コード 2：何も書いていない（読み取りの結果がない、形が合わない、案件を決められない など）。結果のとおりに章を読ませてから、まとめ直す。
   - 終了コード 3：補助プログラムが動かないか、途中で止まった。プラグインを入れ直してから、もう一度試す。
   - 「同じ名前の件が2つ以上」「2つ以上の章が違う値で読んでいます」と出たら、章をまたいで重ねて読んでいないかを確かめる。
   - 「段階のフォルダを作れませんでした」と出たら、手続きの段階を、上の決まりを渡して読み取り役に読ませ直し、裏取りの道具に通してから、もう一度まとめる。
4. 確かめるだけ（書き換えない）のときは `--merge` の代わりに `--check` を使う。
5. 採択後に次の段階へ進むとき（F12）は、下の「採択後に、次の手続きの段階へ切り替える」の道具を使う（段階のフォルダも作る）。

## 申請までの日程・加点・書類の一覧（F3）

制度データをまとめたら、締切から逆算した日程、加点が締切までに間に合うか、申請の書類の一覧を、道具で出して社長に示す。
日付・あと何日・間に合うかは、道具の値をそのまま使う（頭で計算しない。今日の日付は差し替えられていることがある）。

```
python3 -B "${CLAUDE_PLUGIN_ROOT}/skills/junbi/scripts/nittei.py" --folder "${CLAUDE_PROJECT_DIR}" --case "<案件>"
python3 -B "${CLAUDE_PLUGIN_ROOT}/skills/junbi/scripts/nittei.py" --folder "${CLAUDE_PROJECT_DIR}" --case "<案件>" --docs
```

- 日程：作業（外部に頼む書類、取る期間のある書類、計画書（案）を固める日、電子申請、締切、間に合う加点の準備）を、始める日の早い順に出す。
  - 「（目安）」の付いた期日は出典のないツールの目安なので、そう伝える。【遅れ】【期日を過ぎた】は強めて伝える。
  - 「頼んでから届くまでの日数は、まだ分かりません」の書類は、期限の道具（下の「期限と、外部への依頼と待ち」）の手順で社長に日数を聞き、
    `kigen.py --days` で残してから、もう一度日程を出す（日数は会社の記録にも残り、日程の道具も使う）。
  - 「当てはまるときだけ」の書類は、会社の記録で当てはまるかを確かめ、分からなければ社長に聞く。当てはまらないものは示さない。
- 加点：「これから取り始めるとき」に締切までに間に合うかを、「取れる見込み」「今回は取れない」「確かめが要る」で出す。
  - すでに満たしている加点（認定を受けているなど）か、会社が条件に当たるかは、会社の記録で確かめてから伝える（道具は日付だけで見ている）。
  - 「確かめが要る」（かかる日数が資料に書かれていない）は、推測で日数を入れない。社長に、すでに満たしているか、取るのに何日かかるかを聞く。
    答えの日数は、会社の記録に「加点の日数：<加点の名前>」として残す（kiroku の道具）と、次から道具が逆算に使う。
  - 「今回は取れない」は、わけ（基準日・依頼の締切・締切のどれを過ぎたか）と出典を添えて、はっきり伝える。
- 書類の一覧（`--docs`）：必須・条件付き・任意を出す。社長に示すときは、表で「区分｜書類｜条件・有効期限｜効く審査項目・加点｜出典」とする。
  - 必須の書類は、道具の一覧のとおり全部を示す（省かない。様式で作る書類も、ツールが作るものとして入れる）。
  - 任意の書類には、どれにも効く審査項目か加点を添える。制度データの一覧にない任意の書類（会社概要、事業別の収支、商品・サービスの説明、
    作業工程の写真など）を勧めるときも、道具が出す審査項目・加点の名前のどれに効くかを1つずつ添える。

## 公募要領の改訂や、新しい公募回の資料が出たとき（F7）

変わったページだけを読み直す（DESIGN 9.2）。全部の章を初めから読み直さない。

1. 取り直す：上の「公式資料を取り、書類フォルダを作る」の手順で、出た資料の id・公募回・URL を直した一覧を作り、同じ案件（`--case`）で取り直す。
   前の回の資料は、資料の一覧の「前の回の資料」に移る（本文も残る）。まだ出ていない資料は、直近回のまま使う（道具の案内をそのまま伝える）。
2. 変わったページを見る（書き換えない）。頁の番号のずれと、目次の頁の番号だけの違いは除かれる。

```
python3 -B "${CLAUDE_PLUGIN_ROOT}/skills/junbi/scripts/kaitei.py" --folder "${CLAUDE_PROJECT_DIR}" --case "<案件>" --pages
```

3. 引き継ぐ：章ごとの読み取りの出典を今の資料に付け替え、今の資料の本文で裏取りし直す。結果に、章ごとの「読み直すもの」（変わったページと、外れた値）が出る。

```
python3 -B "${CLAUDE_PLUGIN_ROOT}/skills/junbi/scripts/kaitei.py" --folder "${CLAUDE_PROJECT_DIR}" --case "<案件>" --carry
```

4. 読み直す：「読み直すもの」の章ごとに、読み取り役（opus）を呼ぶ。渡すのは、案件・章の名前（前の結果のとおり）・変わったページ・外れた値の件（今の結果の JSON）。
   - 件は**全部の欄**を返させる。名前が変わった件は新しい名前の件で返させ、前の名前を「消す件」に入れさせる。変わったページに、その章の項目に当たる新しい定めがあれば、件を足させる。
   - HTML のページ（スケジュールなど）の値が外れたときは、その項目（決まった期日など）を、今の版のページで読ませる（HTML は頁の差を出せない）。
   - 返った JSON を、そのまま Write で `記録/一時/読み直し.json` に置いて渡す（道具は、件の名前で同じ件だけを差し替え、ほかの件は残す）。形は
     `{"読み取り": {"章": "<章>", "読んだページ": [...], "回目": 1}, "制度データ": {"<項目>": [<件>]}, "消す件": {"<項目>": ["<前の件の名前>"]}, "メモ": ["..."]}`。

```
python3 -B "${CLAUDE_PLUGIN_ROOT}/skills/junbi/scripts/kaitei.py" --folder "${CLAUDE_PROJECT_DIR}" --case "<案件>" --apply 記録/一時/読み直し.json
```

5. まとめる：上の `seido_data.py --merge` で、新しい回の制度データ（`記録/制度データ/<略称>_<公募回>.json`）を置く。前の回の制度データは残る。
6. 差を示す：前と後の制度データの差と、自社の申請で影響するところを出し、社長に平易に伝える。

```
python3 -B "${CLAUDE_PLUGIN_ROOT}/skills/junbi/scripts/kaitei.py" --folder "${CLAUDE_PROJECT_DIR}" --case "<案件>" --diff
```

   - 変わった項目ごとに、前の値と新しい値、それぞれの出典（資料・回・ページ）を示す。「変更なし」と出たら、そのまま伝える。
   - 終了コード 1 は、出典のページのない変わった項目がある。その項目の章を、4. の手順で読み直してから、もう一度まとめて差を出す。
   - 影響するところ（期限の台帳の出来事から決まる期限、概要と流れ.docx・申請書・財務モデルの見直す所、そろえる書類）を伝え、
     概要と流れ.docx を作り直す。期限は `stage_switch.py --show` で出し直す（日付を頭で計算しない）。申請書は、社長の了承を得てから直す。

## 採択後に、次の手続きの段階へ切り替える（F12、F6）

「採択された」「交付決定が来た」「次の手続きに進みたい」と言われたら、道具で次の段階（2_交付申請 など）へ切り替える。
段階のフォルダ、その段階の書類の一覧、期限は、どれも道具が制度データの手続きの段階から作る。Claude は日付を頭で計算しない。

1. 出来事の日付を確かめる。期限は「採択発表日から2か月」のように出来事から決まるので、その日付が要る。
   - 通知の原本（`原本/役所からの通知/` の採択の通知など）があれば、日付を読み取り、社長に「この日付でよいか」を確かめる。
   - なければ、社長に聞く（選択肢の画面で、理由「交付申請の期限は採択発表日から決まるため」を添える）。推測で日付を入れない。
2. 道具を動かす。出来事は `--event <出来事の名前>=<日付>`、出典は `--source`（通知の原本の、会社のフォルダからの場所。社長の答えなら渡さなくてよい）。

```
python3 -B "${CLAUDE_PLUGIN_ROOT}/skills/junbi/scripts/stage_switch.py" --folder "${CLAUDE_PROJECT_DIR}" --case "<案件>" --event 採択発表日=2027-03-10 --source "原本/役所からの通知/<通知のファイル>"
```

   - 次の段階は、今の段階の次の、フォルダのある段階（道具が決める）。別の段階にするときだけ `--stage 3_実績報告` のように渡す。
   - 今の段階の期限の決め方にある出来事（交付申請の段階の採択発表日など）の日付だけを渡したときは、道具は段階を進めない（期限が出なかった後の流し直しや、日付の直し）。
   - 段階は変えずに日付だけ残すとき（交付申請の段階で交付決定日が分かったときなど）は、今の段階を `--stage` に渡す。
   - 書かずに、今の段階の書類の一覧と期限を見るだけのときは `--show`（「交付申請の書類は？」「期限はいつ？」と聞かれたとき）。
3. 道具の結果を、社長に平易に伝える。日付と「あと何日」は、結果の値をそのまま使う（今日の日付は差し替えられていることがあるため）。
   - 期限（もとにした日と出典）、必須の書類、条件付きの書類（条件に当たるかを、会社の記録で分からなければ社長に聞く）、様式で作る書類。
   - 「特に注意（交付決定の前）」があれば、交付決定より前に発注・契約すると補助の対象外になることを、強く伝える。
   - 「知らせること」（前の段階の提出版がない、制度データの回が案件の回と違う、日付の差し替えを確かめる など）も伝える。
4. 終了コードで次を決める。
   - 0：切り替えた（か、もうその段階だった）。期限の日付も出た。
   - 1：切り替えたが、期限の日付がまだ出せない。手順1で出来事の日付を確かめ、`--event` で渡し直す（同じ段階のまま、何度流してもよい）。
   - 2：何も書いていない（制度データにない出来事、今日より後の日付、今の段階より前の段階、書く先が別名 など）。結果のとおりに直して流し直す。
     「今日より後」と出たら、通知の日付の読み違いか、今日の日付の差し替えを確かめる。
   - 3：補助プログラムが動かないか、途中で止まった。プラグインを入れ直してから、もう一度試す。
5. 道具は、出来事の日付を期限の台帳（`記録/期限の台帳.json`）に残す。開いたときの期限と今の状態.html も、その日付から出る。日付を直すときは、正しい日付で流し直す（前の日付は版の履歴に残る）。

## 期限と、外部への依頼と待ち（F6）

期限と作業の一覧、人に頼む書類（外部への依頼）、近い締切の日数は、道具で扱う。日付・日数・始める日は道具の値をそのまま伝える（頭で計算しない）。
期限の台帳（`記録/期限の台帳.json`）は道具だけが書く。Claude が Write・Edit で書き換えない。

```
python3 -B "${CLAUDE_PLUGIN_ROOT}/skills/junbi/scripts/kigen.py" --folder "${CLAUDE_PROJECT_DIR}" --show
python3 -B "${CLAUDE_PLUGIN_ROOT}/skills/junbi/scripts/kigen.py" --folder "${CLAUDE_PROJECT_DIR}" --case "<案件>" --requests
python3 -B "${CLAUDE_PLUGIN_ROOT}/skills/junbi/scripts/kigen.py" --folder "${CLAUDE_PROJECT_DIR}" --case "<案件>" --add "<書類>" --days "<書類>=14日" --who "<書類>=社長"
```

- 「締切はいつ？」「今は何をすればいい？」：`--show` の一覧（期限切れ・今日やること・近い締切・遅れている作業、それより先、外部への依頼と待ち）を、この順に伝える。
- 「よそに頼む書類はある？」「いつまでに頼めばいい？」と聞かれたとき（書類の一覧を示すときも）：
  1. `--requests` で、今の段階と次の段階の、人に頼む書類の候補を出す。条件付きの書類は、会社の記録で条件に当たるかを確かめ、分からなければ社長に聞く。当たるものだけを頼む書類にする。
  2. 頼む書類を `--add "<書類>"` で台帳に足す（目安の日数がまだ分からなくても足す。聞いている間も一覧に出るため）。書類の名前は、結果のとおり（制度データの名前）に書く。
  3. 目安の日数が「まだ分かりません」の書類だけ、頼んでから届くまでの日数を社長に聞く（理由：締切から逆算して、頼む日を出すため）。だれが頼むか（社長か担当者）も聞く。
     目安に「会社の記録（前に社長に聞いた日数）」「制度データ」と出た書類は、聞き直さずにその日数を使う。推測で日数を入れない。
  4. 社長の答えを `--days "<書類>=14日"`・`--who "<書類>=社長"`（依頼先が分かれば `--to "<書類>=信用金庫"`）で残す。日数は会社の記録にも残り、次の案件でも使う。結果の始める日（頼む日）と締切を伝える。
- 社長が「頼みました」と言ったら `--status "<書類>=依頼した"`、「まだ届かない」は `--status "<書類>=待っている"`。
- 「届いた」と言われたら：書類が会社のフォルダに入っていれば、先に shorui の手順で整理し、整理した後の原本の場所を `--received "<書類>=原本/…"` で渡す。書類がなければ `--status "<書類>=届いた"`。
- 「近い締切は60日にして」と言われたら `--near-days 60`（`.hojokin/設定.json` に残り、開いたときの一覧と今の状態.html もその日数で分ける）。
- 終了コード：0 できた。1 できたが、目安の日数がまだ分からない依頼がある（上の 3.）。2 何も書いていない（制度データにない書類の名前、値の形が違う、案件を決められない など。結果のとおりに直して流し直す）。3 補助プログラムが動かない。

## 概要と流れ.docx を作る（F3）

制度データをまとめたら（上の終了コード 0 か、直せない値を要確認・読み取れないのまま）、案件ごとに `案件/<案件>/概要と流れ.docx` を作る。
数字・期限・一覧は、道具が制度データと会社の記録（`記録/会社の記録.json`）から入れる。補助額の見込みも道具が計算する。
Claude が書くのは、説明の文と、会社に当てはめた判断だけ。数字や一覧を JSON に書き写さない。

1. 制度データ（`--check` の結果や、制度データのファイル）で、補助額の区分と特例の名前、要件と加点の名前を確かめる。
2. 会社の記録と聞き取りから、判断を決める。分からないことは推測で決めず、判定を「確かめが要る」にするか、その要件・加点を渡さない。
   - 補助額の区分（従業員の数え方は制度データの定義で）と、使う特例（同じ特例は1回だけ書く。補助率と上限の置き換えは、それぞれ1つまで）。
     補助の対象にする経費の額は、会社の記録の事実（円の金額）の id で渡す。
     会社の記録にまだなければ、社長に聞いて会社の記録に残してから渡す。
   - 要件ごとに「満たす」「満たさない見込み」「確かめが要る」、加点ごとに「取れる見込み」「今回は取れない」「確かめが要る」。
     理由を一言添え、使った会社の記録の id を並べる（Word の出典に出る）。
3. 制度の概要を平易な文で書く（2〜4段落。何のための制度か、だれが使えるか、何に補助が出るか、申請から効果報告までの大まかな流れ）。
   金額・割合・日付などの数字は文に書かない（道具が制度データから表に入れる。文に書くと、表と食い違っても道具が見つけられない）。
   必要なら流れの説明も書く（同じく数字は書かない）。
4. 次の形の JSON を Write で `記録/一時/概要と流れ.json` に置き、道具に渡す。名前は制度データ・会社の記録のとおりに書く。

```
python3 -B "${CLAUDE_PLUGIN_ROOT}/skills/junbi/scripts/gaiyou_word.py" --folder "${CLAUDE_PROJECT_DIR}" --case "<案件>" --input 記録/一時/概要と流れ.json
```

```
{
  "制度の概要": ["…", "…"],
  "流れの説明": "…",
  "要件の判定": [{"要件": "<要件の名前>", "判定": "満たす", "理由": "…", "会社の記録": ["<id>"]}],
  "加点の判定": [{"加点": "<加点の名前>", "判定": "今回は取れない", "理由": "…", "会社の記録": ["<id>"]}],
  "補助額の見込み": {"区分": "<補助額の区分>", "特例": ["<特例の名前>"], "補助の対象にする経費": "<会社の記録の事実の id>",
                     "理由": "…", "会社の記録": ["<id>"]}
}
```

5. 道具の結果で次を決める。
   - 終了コード 0：書いた。結果の行（要件・義務と返還の条件・補助額の見込み・流れと期限・加点・必要書類の件数）を社長に平易に伝え、
     ファイルの場所を示す。読み取れなかった値と要確認の値があれば、Word の「資料で分からなかったこと」と問い合わせ文の案を示す。
   - 終了コード 2：何も書いていない。直す所の一覧のとおりに、名前を制度データ・会社の記録のとおりに直すか、足りない事実を社長に聞いて会社の記録に残してから、もう一度渡す。
     制度データがない・形が合わないと出たら、上の手順で制度データをまとめ直す。
   - 終了コード 3：補助プログラムが動かないか、途中で止まった。プラグインを入れ直してから、もう一度試す。
6. 作り直すときも同じファイルを直す（「_v2」などの別のファイルは作らない。前の版は版の履歴に残る）。
   会社の記録や判断が変わったとき、制度データを作り直したときは、作り直す。
