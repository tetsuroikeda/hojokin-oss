# 実験 E1 の結果（2026-11-03）

ブラウザの道具の呼び出しを hook が受け取り、画面入力の守り（DESIGN 5章）を作れるかを確かめた。手順は `手順.md`、試しのプラグインは `e1-probe/`、試しの申請画面は `page/` と `serve.py`。

## 試し方

- 試しの会社のフォルダ `~/hojokin-e1/会社/` に、e1-probe を CLI で local の範囲で入れた。試しの申請画面（架空の2画面）は 127.0.0.1:8765 に出した。
- 内蔵ブラウザ：デスクトップアプリのセッション（auto モード、Sonnet 5.5）で流した。
- Claude in Chrome：ターミナルの `claude -p --chrome`（Sonnet 5.5）で、作者の Chrome を使って流した。
- 記録：`~/.hojokin-e1/hooks.jsonl`（道具の入力と結果）、`~/.hojokin-e1/server.jsonl`（画面に届いた値・添付・押したボタン）。

## つまずいた所（1回目）

- 試しの hook の matcher を `Claude_Browser|claude-in-chrome|computer-use` と書いたら、どの道具にも合わず、hook が1回も動かなかった。Claude Code は、英字・数字・`_`・`-`・`|` だけの matcher を、正規表現ではなく名前そのものの一覧として扱う（公式文書の hooks）。`(Claude_Browser|claude-in-chrome|computer-use)__` に直して流し直した。
- 製品の `hooks/hooks.json` の PostToolUse の matcher（`Claude_Browser|claude-in-chrome`）にも同じ誤りがあったので直した（4991ff8）。テストも Claude Code と同じ規則で確かめる形にした。

## 13.2 の手を取るか

- **添付：取る。** 内蔵ブラウザでは添付できないので、添付は Claude in Chrome（`file_upload`）で行う。守りは、書類フォルダの「添付する書類」の写しだけを通す（DESIGN 5章の Claude in Chrome の行のとおり）。
- **見分けられないもの：取る。** 名前の読めない欄（ラベルのない欄、名前の空の選択欄）は、担当者が入れる。チェック欄とラジオボタンが入ったかは読み取れないので、Claude は入れた欄を担当者に示し、画面で確かめてもらう（DESIGN 5章の「チェックが入っていることを読み取って確かめてから続ける」は、このままでは成り立たない）。
- **hook がブラウザの道具を受け取れないとき：取らない。** 受け取れた（matcher を正しく書けば）。

## 骨組み（S4）と DESIGN（S0）に使うこと

1. matcher は正規表現の形で書く（`(Claude_Browser|claude-in-chrome)__` など）。英字などだけの形は名前そのものの一覧になり、何にも合わない。
2. 番号は画面ごとに振り直されるので、クリックや移動の後は控えを捨て、読み直させる（DESIGN 5章のとおり）。`browser_batch` の中は1つずつ見られるので、DESIGN 5章の「クリックは1回までで最後の動作に限る」を作れる。
3. チェック欄・ラジオボタンの名前は、欄そのものではなく、囲むラベルから取る（DESIGN 5章のとおり）。選択欄は、ラベルの名前が空になる形があるので、名前の読めない欄として扱う。
4. 入れたチェック欄・ラジオボタンの状態は、読み取りで確かめられない。DESIGN 5章の「チェックが入っていることを読み取って確かめる」を、担当者に画面で確かめてもらう形に直す（S0）。
5. 添付は Claude in Chrome で行う。内蔵ブラウザで画面入力を進める場合も、添付の場面だけは Claude in Chrome か担当者の手になる（S0 で DESIGN 3章のデモの筋と5章を直す）。
