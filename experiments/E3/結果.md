# 実験 E3 の結果（2026-11-03）

plugin eval の仕組みを、試しのプラグイン `e3-probe/` で確かめた。Claude Code は 2.1.317。

## 試し方

- 試しのプラグイン `e3-probe/`（このフォルダの中だけ。user の範囲には入れていない）
  - skill `kakunin`：スクリプト `scripts/kakunin.py` を Bash で動かす。続けて、hook に拒ませるコマンドと、設定の deny で止まるはずのファイルの読み取りを試す。
  - hook：SessionStart・UserPromptSubmit・PreToolUse・PostToolUse・PostToolUseFailure・PermissionDenied・SubagentStart・SubagentStop・Stop・SessionEnd。どれも `hooks/run.sh` → `hooks/probe.py` で、作業フォルダの `.e3/hooks.jsonl` に1行ずつ書く。SessionStart は合言葉を Claude に渡し、PreToolUse は `E3_DENY` を含む Bash を JSON で拒む。
  - subagent `shinsa-mitate`：審査役に見立てたもの（E3b）。
- eval のケース（`e3-probe/evals/`）
  - `a-kakunin`（タグ e3a）。scaffold が `evals/状態/E3の会社/`（架空の会社のフォルダ）を戻し、`downloads/shoryokuka_ippan/` の公募要領・様式を `案件/2026_省力化（一般型）第8回/公式資料/` に写し、git で版を1つ作る。
  - 採点は regex・tool_used・file_exists だけ（AI の判定は使わない）。
- 流したコマンド（TASKS 10章の eval に、`--keep-temp`・`--no-publish`・出力先を足した）

  ```
  claude plugin eval experiments/E3/e3-probe --scaffold --trust-plugin --allow-tools Bash Write Edit --threshold 1.0 --json <scratch>/run1.json --tag e3a --runs 1 --ablation none --max-cost-usd 3 --keep-temp --no-publish --output-dir <scratch>/run1
  ```

  2回目は `--runs 1 --ablation none` を `--ablation with-without --runs 1` に替えた（Δ）。
- eval の出力（JSON、trace、report.html）と `--keep-temp` のフォルダは、会話の記録とパスを含むのでリポに入れない。下には抜き書きだけを載せる（`/tmp/e-XXXX` は eval が作った一時のフォルダ）。

## E3a で分かった、設計に関わること

- **会社のフォルダの設定は、eval では効かない。** scaffold が置いた `.claude/settings.json` の deny は読み込まれず、Claude は `記録/秘密.txt` を読めた（trace に中身が出た）。文書の「workspace の中の `.claude/` は読み込まない」のとおり。外を読み書きさせない設定、Edit の deny、allow（4.7、E6）は eval では確かめられない。pytest とデスクトップで確かめる。hook（PreToolUse）による守りは eval でも効く。
- **eval の中の権限のモードは `dontAsk`。** hook の入力の `permission_mode` も、trace の init も `dontAsk` だった。デスクトップの default・auto とは違う。モードで変わる振る舞い（auto モードの SubagentHandback など。E3b）は、eval の結果だけでは決められない。
- **HOME と `CLAUDE_PLUGIN_DATA` は、実行のたびに新しい一時の場所になる。** `CLAUDE_PLUGIN_DATA` は `/tmp/e-XXXX/config/plugins/data/e3-probe-inline`。初回の準備でここに何かを入れる作り（E5）だと、eval の実行のたびに準備が走る。Bash の sandbox はネットワークを許さない（`allowedDomains: []`）ので、Bash の中では取りに行けない（hook は sandbox の外で動く）。
- **Bash の sandbox からプラグインの根が読める。** eval の設定の `allowRead` にプラグインの根が入り、`evals/` とホームの下は `denyRead` だった。製品ではプラグインの根がリポの根なので、`testdata/`（正解を含む）と `downloads/` も Bash から読める形になる（設定から読み取ったこと。実際に読ませてはいない）。正解を読まれないようにするかは、M13 で考える。
- **プラグインなしの側にも、組み込みのプラグインが入る。** 両方の側で `cc-plugin-agents-md`・`cc-plugin-privacy`・`cc-plugin-plugin-authoring` が読み込まれていた。Δ は、それらに対する差になる。
- **hook とスクリプトが作ったファイルも、file_exists が数える。** scaffold が作ったファイルは数えない（文書どおり）。

## E3a の 13.2 の手を取るか

取らない。scaffold・公式資料の写し・Δ・`--keep-temp`・費用・hook・スクリプトは、どれも eval の中で動いた。自前の `claude -p` の仕組みに広げる必要はなく、公式資料も scaffold で写せる（eval の前に写すスクリプトは要らない）。

S0 で扱うとよいこと：会社のフォルダの設定が eval では効かないこと（11章のテストの分け方に書き足す）、eval のモードが `dontAsk` であること、`--keep-temp` のフォルダを pytest で読むには `chmod 700` が要ること、プラグインの根（`testdata/` を含む）が Bash から読めること。
