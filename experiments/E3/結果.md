## E3a で分かった、設計に関わること

- **会社のフォルダの設定は、eval では効かない。** scaffold が置いた `.claude/settings.json` の deny は読み込まれず、Claude は `記録/秘密.txt` を読めた（trace に中身が出た）。文書の「workspace の中の `.claude/` は読み込まない」のとおり。外を読み書きさせない設定、Edit の deny、allow（4.7、E6）は eval では確かめられない。pytest とデスクトップで確かめる。hook（PreToolUse）による守りは eval でも効く。
- **eval の中の権限のモードは `dontAsk`。** hook の入力の `permission_mode` も、trace の init も `dontAsk` だった。デスクトップの default・auto とは違う。モードで変わる振る舞い（auto モードの SubagentHandback など。E3b）は、eval の結果だけでは決められない。
- **HOME と `CLAUDE_PLUGIN_DATA` は、実行のたびに新しい一時の場所になる。** `CLAUDE_PLUGIN_DATA` は `/tmp/e-XXXX/config/plugins/data/e3-probe-inline`。初回の準備でここに何かを入れる作り（E5）だと、eval の実行のたびに準備が走る。Bash の sandbox はネットワークを許さない（`allowedDomains: []`）ので、Bash の中では取りに行けない（hook は sandbox の外で動く）。
- **Bash の sandbox からプラグインの根が読める。** eval の設定の `allowRead` にプラグインの根が入り、`evals/` とホームの下は `denyRead` だった。製品ではプラグインの根がリポの根なので、`testdata/`（正解を含む）と `downloads/` も Bash から読める形になる（設定から読み取ったこと。実際に読ませてはいない）。正解を読まれないようにするかは、M13 で考える。
- **プラグインなしの側にも、組み込みのプラグインが入る。** 両方の側で `cc-plugin-agents-md`・`cc-plugin-privacy`・`cc-plugin-plugin-authoring` が読み込まれていた。Δ は、それらに対する差になる。
- **hook とスクリプトが作ったファイルも、file_exists が数える。** scaffold が作ったファイルは数えない（文書どおり）。

## E3b で分かった、設計に関わること

- **審査役の結果の保存（DESIGN 8章、M7）は、hook を2つの場面に付ければ、本体を通さずにできる。**
  - default・`dontAsk`（eval）：SubagentStop の `last_assistant_message`。
  - auto：PreToolUse か PostToolUse（matcher `SubagentHandback`）の `tool_input.message`。SubagentStop には報告が来ない。
  - 社長がどちらのモードで使っても取りこぼさないよう、両方に付ける。eval は `dontAsk` なので、auto モードの経路は eval では確かめられない（pytest で入力を渡して確かめるか、デスクトップで確かめる）。
- **報告は、前後に json の囲み（3つのバッククォート）が付いたまま届く。** 保存する道具か hook は、囲みを外してから JSON として読む。
- **auto モードの `claude -p` では、subagent が後ろで動いた。** Agent の結果は `status: "async_launched"` で、本体は報告を待たずに1度応答を終え、報告が届いてから続きの応答を書いた（result が3つ出た）。デスクトップでも同じなら、kaku が審査役の結果を待つ作りに気を付ける（M7）。
- **AskUserQuestion は、eval でも `claude -p` でも使えない。** 選択肢で聞く作りの skill は、eval では文で聞く形になるか、聞かずに進む。選べる案は下の「止まって作者に聞きたいこと」に書いた。

## つまずいた所

- 3回目の `b-shinsa` で保存の2項目が落ちたのは、私の hook の書き方の誤り。matcher を `shinsa-mitate` と書いたが、英字と `-` だけの matcher は完全一致として扱われる（文書の hooks の matcher の表）。実際の `agent_type` は `e3-probe:shinsa-mitate` なので合わなかった。`^e3-probe:shinsa-mitate$` に直した4回目で通った。製品の matcher も、プラグインの名前付きで書く。

## 止まって作者に聞きたいこと（S0 で）

AskUserQuestion が画面のない実行で使えないことについて、テストの作り方と、社長に見える聞き方に関わるので、私は決めていない。

- 関わる章：DESIGN 11章（振る舞いテストと、会話を続けるテストの仕組み）、SPEC 8章の「振る舞いテストの細部」の行。
- 関わるテスト：会話を続けるテストの T13-2（聞き直しがないか）・T13-3（初稿までの質問の数）・T3-6・T12-1・デモの通し。ほかに、振る舞いテストのうち、skill が社長に聞く場面のあるもの。
- DESIGN と SPEC には、選択肢の画面で聞くという前提は書かれていない（`AskUserQuestion` と「選択肢」が出るのは、DESIGN 13.2 の E3 の行と SPEC 8章の行だけ）。そのため、案1を選んでも DESIGN を変える必要はない。

選べる案：

1. skill の質問はいつも文で聞く（選択肢の画面を使わない）。eval・`claude -p` とデスクトップで振る舞いがそろい、会話を続けるテストの社長役が文で答えられる。
2. デスクトップでは AskUserQuestion を使い、道具がないときは文で聞く。テストで確かめられるのは文で聞く側だけになる。
3. 会話を続けるテストの仕組みに、答えを受け取る相手（`--permission-prompt-tool` の MCP の道具、または PreToolUse の `defer` と `--resume`）を作り、AskUserQuestion に答える。文書にある形だが、今回は試していない。
