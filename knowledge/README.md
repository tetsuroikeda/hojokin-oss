# 同梱の知見（knowledge/）

プラグインに入れて配る、制度や会社をまたぐ知見です（SPEC 6章「同梱の知見」、DESIGN 4.5）。作者が 2026-11-03 の聞き取りで答えた内容を、Claude が書き起こしました（TASKS A1）。Claude の案の所と不備の重さを含め、作者が同じ日に中身を確かめました。

## ファイル

| ファイル | 中身 | 使う所 |
|---|---|---|
| 審査の観点.json | 審査で差がつく所を「確かめる問い」にしたもの。共通の観点と、省力化・持続化の観点 | 書く（kaku）、審査役 |
| 構成の型.json | 「現状と目標 → 課題 → 解決策 → 効果」の段ごとに入れる事実の種類、よく切れるつなぎ、様式の項目への割り当ての目安、図表を置く所 | 書く（kaku）、審査役（T8-8） |
| 不備の型.json | 書類の不備の型。確かめること、重さとその決め手、見つけ方、直し方 | 書類（shorui、B12） |

例年公募がある制度の一覧も、あとでこのフォルダに入れます（B21）。

## 渡し方

製品の skill と subagent は、会社のフォルダの外を読ませない設定のため、プラグインの中のファイルを Read で読めません（実験 E6）。中身はスクリプトが出力して渡します。そのため、スクリプトで読みやすい JSON にしました。どのファイルも、先頭の「説明」に、何に使うかを書いています。

## 入れないもの

- 計画書の例文や定型文（そのまま使える段落）。観点も型も「確かめる問い」と「入れる事実の種類」の形で持ちます（SPEC F8、T8-6）。
- 公募要領や採択事例の文の写し。
- 特定の会社・人・地名の情報（SPEC 6章「同梱の知見」）。
- 審査項目、加点項目、様式の項目、期限・期数・金額の基準などの値。これらは制度データにあり、公募回で変わるためです。

## 採択事例の扱い（作者が決めた線引き）

- 参考にするのは、作者が公開されている採択事例を読んで書き起こした、次の2つだけにします。
  - どの審査項目に、どんな種類の事実で応えていたか（観点）
  - 項目の並べ方と、分量の配分（構成）
- 文、数字、社名、事業名、地名は持ちません。採択事例の文章は流用しません（SPEC F8、DESIGN 8.2）。
- 製品は、採択事例そのものを読みに行きません。このフォルダに書き起こした要点だけを使います。
- 書き起こしは、ハッカソンの期間中に行い、コミットの履歴で期間中に作ったと分かるようにします（SPEC 4章「既存の資産」）。
- 今の版には、採択事例から書き起こした要点はまだありません。書き起こしたら、その項目の出どころを「採択事例（作者が書き起こし）」とします。
